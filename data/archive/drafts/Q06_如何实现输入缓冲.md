# 如何实现输入缓冲

## 问题背景

输入缓冲（Input Buffer）在 Minecraft 数据包开发中，通常指：玩家在短时间内连续按下某个键（如攻击、跳跃、使用物品），但游戏刻（tick）的固定节奏（20 tick/s）可能导致部分输入被"吞掉"（即两次输入发生在同一 tick 内，或输入发生在 tick 间隙但被下一 tick 覆盖）。输入缓冲机制允许将输入"排队"，确保每个输入都能被正确处理，常用于连击系统、技能释放、节奏游戏等场景。

核心挑战：
- Minecraft 的输入检测（如 `predicate`、`advancement`）是**基于 tick 的**，无法直接感知 tick 内的多次输入
- 原版没有内置的"事件队列"机制，需要自行用 scoreboard、storage 或 advancement 模拟
- 不同输入类型（攻击、跳跃、使用物品）的检测方式不同，缓冲策略需分别适配

---

## 方案一：基于 Scoreboard 的 Tick 级缓冲（最通用）

### 原理

利用 `scoreboard` 的 `add` 操作，在每次检测到输入时给一个虚拟分数加 1，然后在后续 tick 中逐次消耗（减 1）。这样即使同一 tick 内多次输入，分数也会累加，不会丢失。

### 版本要求

1.13+（scoreboard 基础功能），1.20.5+（推荐，因为 1.20.5 后 `execute on` 和 `items` 命令更强大，但本方案不依赖这些新特性）

### 完整实现

#### 1. 初始化 (load)

```mcfunction
# load.mcfunction
scoreboard objectives add input_buffer dummy
scoreboard objectives add input_consume dummy
```

#### 2. 输入检测（以攻击键为例）

攻击键（左键）无法直接通过 `predicate` 检测，但可以通过 `minecraft:player_interacted_with_entity` 或 `minecraft:player_hurt_entity` 进度间接检测。这里使用更通用的方法：检测玩家是否在攻击冷却中（即 `attack_time` 变化）。

```mcfunction
# tick.mcfunction
execute as @a at @s run function namespace:input/detect_attack
```

```mcfunction
# namespace:input/detect_attack.mcfunction
# 检测攻击冷却是否刚被重置（即玩家按下了攻击键）
# 原理：attack_time 在攻击后变为 1.0，然后逐渐减少
execute if score @s attack_time matches 1.0 run scoreboard players add @s input_buffer 1
```

> ⚠️ 需验证：`attack_time` 是 NBT 路径 `player.attack_time`，在 1.20.5+ 中可通过 `data get entity @s player.attack_time` 获取。但 `scoreboard` 不能直接读取 NBT，需要先用 `execute store result score` 存储。更可靠的方式是使用 `predicate` 检测 `player.attack_time` 的变化，但 `predicate` 不支持 `attack_time` 字段。因此上述代码仅作示意，实际需用 `execute store result score @s attack_time run data get entity @s player.attack_time` 先读取。

**更可靠的攻击检测方式（1.20.5+）：**

```mcfunction
# namespace:input/detect_attack.mcfunction
# 将 attack_time 存入 scoreboard
execute store result score @s attack_time run data get entity @s player.attack_time 100
# 如果 attack_time 为 100（即 1.0 * 100），说明刚攻击
execute if score @s attack_time matches 100 run scoreboard players add @s input_buffer 1
```

#### 3. 缓冲消耗

```mcfunction
# namespace:input/consume.mcfunction
# 每 tick 消耗一个缓冲
execute if score @s input_buffer matches 1.. run scoreboard players remove @s input_buffer 1
execute if score @s input_buffer matches 1.. run function namespace:input/on_attack
```

#### 4. 完整 tick 函数

```mcfunction
# tick.mcfunction
execute as @a at @s run function namespace:input/tick
```

```mcfunction
# namespace:input/tick.mcfunction
function namespace:input/detect_attack
function namespace:input/consume
```

### 陷阱与注意事项

1. **攻击检测的精度**：`attack_time` 在 1 tick 内可能变化多次（如果玩家在 tick 间隙内多次点击），但 `data get` 只能获取当前值，无法区分同一 tick 内的多次攻击。因此本方案**无法保证 100% 捕获所有输入**，只能减少丢失概率。
2. **分数溢出**：如果玩家疯狂点击，`input_buffer` 可能无限增长。建议设置上限（如 10），超过则不再累加。
3. **多输入类型**：如果需要同时缓冲攻击、跳跃、使用物品等，需要为每种输入创建独立的 scoreboard 目标。
4. **性能**：每 tick 对每个玩家执行 `data get` 和 `scoreboard` 操作，开销较低（约 0.01ms/玩家），适合 20 人以下服务器。

## 方案二：基于 Advancement 的事件驱动缓冲（更精确）

### 原理

利用 `advancement` 的 `inventory_changed`、`player_hurt_entity` 等 trigger，在输入发生时立即触发函数，将输入信息存入 `storage` 队列。然后每 tick 从队列头部取出一个输入进行处理。由于 advancement 是事件驱动的，理论上可以捕获同一 tick 内的多次输入（只要它们触发不同的 advancement 或同一 advancement 多次触发）。

### 版本要求

1.13+（advancement 基础功能），1.20.5+（推荐，因为 `storage` 和 `data modify` 更强大）

### 完整实现

#### 1. 初始化 (load)

```mcfunction
# load.mcfunction
# 创建 storage 队列
data modify storage namespace:input_queue queue set value []
# 创建 scoreboard 用于标记队列长度
scoreboard objectives add queue_length dummy
```

#### 2. 输入检测 advancement

```json
// namespace:advancement/attack_detect.json
{
  "criteria": {
    "attack": {
      "trigger": "minecraft:player_hurt_entity",
      "conditions": {}
    }
  },
  "rewards": {
    "function": "namespace:input/on_attack"
  }
}
```

```json
// namespace:advancement/jump_detect.json
{
  "criteria": {
    "jump": {
      "trigger": "minecraft:tick",
      "conditions": {
        "player": {
          "flags": {
            "is_on_ground": false
          }
        }
      }
    }
  },
  "rewards": {
    "function": "namespace:input/on_jump"
  }
}
```

> ⚠️ 需验证：`tick` trigger 的 `conditions` 是否支持 `flags.is_on_ground`。如果不支持，跳跃检测需改用其他方式（如检测 `motion` 变化）。

#### 3. 输入处理函数

```mcfunction
# namespace:input/on_attack.mcfunction
# 将攻击事件加入队列
data modify storage namespace:input_queue queue append value {type:"attack", time:0}
# 更新队列长度
execute store result score #queue_length input_queue run data get storage namespace:input_queue queue
# 撤销 advancement，以便下次触发
advancement revoke @s only namespace:attack_detect
```

```mcfunction
# namespace:input/on_jump.mcfunction
data modify storage namespace:input_queue queue append value {type:"jump", time:0}
execute store result score #queue_length input_queue run data get storage namespace:input_queue queue
advancement revoke @s only namespace:jump_detect
```

#### 4. 每 tick 消耗队列

```mcfunction
# tick.mcfunction
# 检查队列是否非空
execute if data storage namespace:input_queue queue[0] run function namespace:input/consume
```

```mcfunction
# namespace:input/consume.mcfunction
# 取出第一个元素
data modify storage namespace:input_queue current set from storage namespace:input_queue queue[0]
# 根据 type 执行对应逻辑
execute if data storage namespace:input_queue current{type:"attack"} run function namespace:input/on_attack_processed
execute if data storage namespace:input_queue current{type:"jump"} run function namespace:input/on_jump_processed
# 移除已处理的元素
data remove storage namespace:input_queue queue[0]
# 更新队列长度
execute store result score #queue_length input_queue run data get storage namespace:input_queue queue
```

### 陷阱与注意事项

1. **Advancement 触发频率**：`player_hurt_entity` 每次攻击都会触发，但 `tick` trigger 每 tick 只触发一次，无法捕获同一 tick 内的多次跳跃。因此跳跃检测仍需依赖 tick 级检测。
2. **队列持久化**：`storage` 在服务器重启后会清空，如果需要持久化，需改用 `scoreboard` 或写入文件（但数据包无法直接写文件）。
3. **性能**：`data modify` 和 `data remove` 操作开销较低，但 advancement 的触发和撤销有一定开销。适合中等规模（50人以下）服务器。
4. **多玩家支持**：上述代码使用全局 `storage`，所有玩家的输入混在一起。如果需要按玩家区分，需在队列元素中加入 `uuid` 字段，并在消耗时根据 `@s` 过滤。

## 方案三：基于 Predicate 的 Tick 级缓冲（最轻量）

### 原理

利用 `predicate` 的 `input` 条件检测玩家是否按下了某个键（如跳跃、前进），然后通过 `execute if predicate` 在 tick 中检测，并将结果累加到 scoreboard 中。这种方法不需要 advancement，性能开销最低。

### 版本要求

1.16+（predicate 的 `input` 条件）

### 完整实现

#### 1. 创建 predicate

```json
// namespace:predicate/jump_pressed.json
{
  "condition": "minecraft:entity_properties",
  "entity": "this",
  "predicate": {
    "player": {
      "input": {
        "jump": true
      }
    }
  }
}
```

#### 2. 初始化 (load)

```mcfunction
# load.mcfunction
scoreboard objectives add jump_buffer dummy
```

#### 3. Tick 检测

```mcfunction
# tick.mcfunction
execute as @a at @s if predicate namespace:jump_pressed run scoreboard players add @s jump_buffer 1
execute as @a at @s run function namespace:input/consume_jump
```

```mcfunction
# namespace:input/consume_jump.mcfunction
execute if score @s jump_buffer matches 1.. run scoreboard players remove @s jump_buffer 1
execute if score @s jump_buffer matches 1.. run function namespace:input/on_jump
```

### 陷阱与注意事项

1. **支持的键有限**：`predicate` 只支持 `forward`、`backward`、`left`、`right`、`jump`、`sneak`、`sprint`，不支持攻击、使用物品等。
2. **无法区分多次按下**：如果玩家在 1 tick 内多次按下并松开跳跃键，`predicate` 只能检测到"当前是否按下"，无法知道按下了几次。因此本方案只能缓冲"持续按住"的情况，无法处理快速连点。
3. **性能**：开销极低（约 0.001ms/玩家），适合大型服务器。

## 方案对比

| 方案 | 版本要求 | 输入类型支持 | 精度 | 性能 | 适用场景 |
|------|----------|--------------|------|------|----------|
| 方案一：Scoreboard 缓冲 | 1.13+ | 攻击、跳跃等（需适配） | 中（可能丢失同 tick 内多次输入） | 低 | 通用，适合大多数数据包 |
| 方案二：Advancement 事件驱动 | 1.13+（推荐 1.20.5+） | 攻击、交互等（事件驱动） | 高（可捕获同 tick 内多次事件） | 中 | 需要精确输入检测的复杂系统 |
| 方案三：Predicate 缓冲 | 1.16+ | 仅移动键和跳跃 | 低（无法区分多次按下） | 极低 | 简单移动控制，如跑步检测 |

---

## 总结与建议

- **如果只需要检测跳跃或移动键**：方案三最简单，性能最好。
- **如果需要检测攻击或使用物品**：方案一或方案二。方案一更简单，但可能丢失输入；方案二更精确，但实现复杂。
- **如果对精度要求极高**（如节奏游戏）：方案二 + 方案一的混合方案：用 advancement 捕获事件，用 scoreboard 做缓冲队列。
