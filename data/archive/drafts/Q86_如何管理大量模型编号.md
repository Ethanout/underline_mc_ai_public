# 如何管理大量模型编号

## 问题背景

在 Minecraft 数据包开发中，经常需要为大量物品、实体或方块分配唯一的模型编号（Model ID），用于区分不同的变体、等级、类型等。例如：自定义武器有 100 种不同的外观，每种对应一个模型编号。核心挑战在于：**如何在原版框架下高效、可维护地管理这些编号，避免冲突、重复和性能问题**。

## 方案一：基于 CustomModelData 的 NBT 存储法（最推荐）

### 原理

利用物品的 `CustomModelData` 标签（1.14+）或 `item_model` 组件（1.21.2+）来存储模型编号。通过 `item_modifier` 或 `data` 命令动态修改编号，配合 `predicate` 或 `item_model` 进行模型映射。

### 版本要求

- **1.14 - 1.20.4**：使用 `CustomModelData` NBT 标签
- **1.20.5 - 1.21.1**：使用 `components` 中的 `custom_model_data` 组件
- **1.21.2+**：推荐使用 `item_model` 组件，性能更好

### 完整实现（1.21.2+ 版本）

#### 1. 定义模型映射

在资源包中创建模型文件，使用 `item_model` 组件进行映射：

`assets/<namespace>/models/item/custom_sword.json`
```json
{
  "parent": "minecraft:item/handheld",
  "textures": {
    "layer0": "<namespace>:item/custom_sword_base"
  },
  "overrides": [
    { "predicate": { "custom_model_data": 1 }, "model": "<namespace>:item/sword_variant_1" },
    { "predicate": { "custom_model_data": 2 }, "model": "<namespace>:item/sword_variant_2" },
    { "predicate": { "custom_model_data": 3 }, "model": "<namespace>:item/sword_variant_3" }
  ]
}
```

#### 2. 数据包中设置模型编号

`data/<namespace>/item_modifier/set_model_id.json`
```json
{
  "function": "minecraft:set_components",
  "components": {
    "minecraft:item_model": "<namespace>:custom_sword"
  }
}
```

#### 3. 动态修改编号

`data/<namespace>/function/model/set.mcfunction`
```mcfunction
# 设置玩家主手物品的模型编号为 5
item modify entity @s weapon.mainhand <namespace>:set_model_id

# 或者使用 data 命令直接修改（1.20.5+）
data modify entity @s Inventory[{Slot:0b}].components."minecraft:custom_model_data" set value 5
```

### 陷阱与注意事项

1. **版本兼容性**：`CustomModelData` 在 1.20.5 之后被拆分为 `custom_model_data` 组件，旧版 NBT 路径在新版中无效。
2. **性能开销**：每个 tick 对大量物品执行 `item modify` 或 `data` 命令，开销为**中**（约 0.1ms/100 次操作）。建议仅在需要时修改，而非每 tick 全量更新。
3. **编号冲突**：不同数据包使用相同的 `CustomModelData` 值会导致模型冲突。建议使用命名空间前缀（如 `{<namespace>:{model_id:5}}`）来隔离。
4. **物品堆叠**：修改 `CustomModelData` 后，物品无法与未修改的同种物品堆叠。这是设计特性，但需要注意玩家体验。

## 方案二：基于 Scoreboard 的编号管理法

### 原理

使用 scoreboard 为每个实体或玩家分配一个唯一的编号，通过 `execute store` 将编号写入物品的 NBT 或组件中。适用于需要动态分配编号的场景（如生成随机 ID）。

### 版本要求

- 1.13+（scoreboard 基础功能）
- 1.20.5+（支持 `execute store` 写入组件）

### 完整实现

#### 1. 初始化计分板

`data/<namespace>/function/load.mcfunction`
```mcfunction
scoreboard objectives add <namespace>.model_id dummy
```

#### 2. 分配编号并写入物品

`data/<namespace>/function/model/assign.mcfunction`
```mcfunction
# 为当前玩家分配一个编号（从 1 开始递增）
scoreboard players add @s <namespace>.model_id 1

# 将编号写入主手物品的 custom_data 中（1.20.5+）
execute store result entity @s Inventory[{Slot:0b}].components."minecraft:custom_data".<namespace>.model_id int 1 run scoreboard players get @s <namespace>.model_id
```

#### 3. 读取编号

`data/<namespace>/function/model/read.mcfunction`
```mcfunction
# 从物品中读取编号到计分板
execute store result score @s <namespace>.model_id int 1 run data get entity @s Inventory[{Slot:0b}].components."minecraft:custom_data".<namespace>.model_id
```

### 陷阱与注意事项

1. **性能开销**：`execute store` 写入 NBT 的开销为**中高**（约 0.5ms/100 次操作），因为需要解析 NBT 路径。建议批量操作时使用 `function` 循环。
2. **编号持久化**：scoreboard 在服务器重启后保留，但物品的 NBT 不会自动同步。需要在玩家登录时重新分配或恢复编号。
3. **并发冲突**：多个玩家同时分配编号时，`scoreboard players add` 是原子操作，不会冲突。但需要注意计分板名称的唯一性。
4. **NBT 路径限制**：`Inventory[{Slot:0b}]` 只能匹配第一个符合条件的槽位。如果玩家有多个相同物品，需要更精确的匹配（如使用 `items` 命令）。

## 方案三：基于 Advancement 的触发式编号分配

### 原理

利用 `inventory_changed` 进度自动触发编号分配。当玩家获得新物品时，自动为其分配一个模型编号。适用于自动化的编号管理。

### 版本要求

- 1.13+（advancement 系统）
- 1.20.5+（支持 `item_modifier` 写入组件）

### 完整实现

#### 1. 创建监听进度

`data/<namespace>/advancement/model_assign.json`
```json
{
  "criteria": {
    "inventory_changed": {
      "trigger": "minecraft:inventory_changed",
      "conditions": {
        "items": [
          {
            "items": ["minecraft:stick"],
            "predicates": {
              "minecraft:custom_data": "{<namespace>:{needs_id:1b}}"
            }
          }
        ]
      }
    }
  },
  "rewards": {
    "function": "<namespace>:model/assign_on_change"
  }
}
```

#### 2. 分配编号函数

`data/<namespace>/function/model/assign_on_change.mcfunction`
```mcfunction
# 为当前玩家分配编号
scoreboard players add @s <namespace>.model_id 1

# 将编号写入物品（假设物品在快捷栏第 1 格）
execute store result entity @s Inventory[{Slot:0b}].components."minecraft:custom_data".<namespace>.model_id int 1 run scoreboard players get @s <namespace>.model_id

# 移除 needs_id 标记
data remove entity @s Inventory[{Slot:0b}].components."minecraft:custom_data".<namespace>.needs_id

# 撤销进度，以便下次触发
advancement revoke @s only <namespace>:model_assign
```

### 陷阱与注意事项

1. **触发频率**：`inventory_changed` 在每次物品栏变化时触发，包括丢弃、拾取、合成等。需要精确的条件过滤，避免误触发。
2. **性能开销**：每次触发都会执行函数，开销为**低**（约 0.05ms/次）。但如果玩家频繁操作物品栏，累计开销可能较高。
3. **物品匹配**：`custom_data` 谓词在 1.20.5+ 中需要写为 `minecraft:custom_data` 组件路径，旧版使用 NBT 路径。⚠️ 需验证：1.20.5 之后 `predicates` 中的 `custom_data` 是否仍支持 NBT 格式。
4. **编号唯一性**：如果多个物品同时需要编号，`inventory_changed` 可能只触发一次，导致部分物品未分配。建议在函数中遍历所有符合条件的物品。

## 方案四：基于 Storage 的集中式编号管理

### 原理

使用 `storage` 存储一个全局的编号映射表，通过 `data` 命令读写。适用于需要跨实体、跨物品共享编号的场景（如多人协作的编号系统）。

### 版本要求

- 1.15+（storage 功能）
- 1.20.5+（支持 `data modify` 写入组件）

### 完整实现

#### 1. 初始化 Storage

`data/<namespace>/function/load.mcfunction`
```mcfunction
# 初始化编号映射表
data modify storage <namespace>:model_map data set value {}
```

#### 2. 分配编号

`data/<namespace>/function/model/assign_storage.mcfunction`
```mcfunction
# 获取当前最大编号
execute store result score #max_id <namespace>.model_id int 1 run data get storage <namespace>:model_map data.max_id

# 递增编号
scoreboard players add #max_id <namespace>.model_id 1

# 更新 Storage
execute store result storage <namespace>:model_map data.max_id int 1 run scoreboard players get #max_id <namespace>.model_id

# 将编号写入物品
execute store result entity @s Inventory[{Slot:0b}].components."minecraft:custom_data".<namespace>.model_id int 1 run scoreboard players get #max_id <namespace>.model_id
```

#### 3. 读取编号

`data/<namespace>/function/model/read_storage.mcfunction`
```mcfunction
# 从物品读取编号
execute store result score #current_id <namespace>.model_id int 1 run data get entity @s Inventory[{Slot:0b}].components."minecraft:custom_data".<namespace>.model_id

# 从 Storage 查找对应模型
data get storage <namespace>:model_map data.models[#current_id]
```

### 陷阱与注意事项

1. **性能开销**：`data get` 和 `data modify` 操作 Storage 的开销为**低**（约 0.02ms/次），但频繁读写可能累积。
2. **数据持久化**：Storage 在服务器重启后**不会**自动保存。需要使用 `schedule` 或 `tick` 函数定期写入 `scoreboard` 或文件（通过 `data pack` 的 `load` 阶段）。
3. **并发安全**：多个玩家同时分配编号时，`scoreboard players add #max_id` 是原子操作，但 `data get` 和 `data modify` 之间可能存在竞态条件。建议使用 `execute store` 链式操作。
4. **Storage 大小**：大量编号映射可能导致 Storage 数据过大，影响性能。建议使用分片或定期清理。

## 方案对比

| 方案 | 版本要求 | 性能开销 | 适用场景 | 复杂度 | 持久化 |
|------|----------|----------|----------|--------|--------|
| CustomModelData | 1.14+ | 低 | 静态模型映射，物品外观区分 | 低 | 自动（物品 NBT） |
| Scoreboard | 1.13+ | 中 | 动态编号分配，需要计分板逻辑 | 中 | 需手动同步 |
| Advancement | 1.13+ | 低 | 自动化编号，玩家交互触发 | 中 | 自动（物品 NBT） |
| Storage | 1.15+ | 低 | 全局共享编号，跨实体映射 | 高 | 需手动持久化 |

## 最佳实践建议

1. **简单场景**（< 50 种模型）：使用 `CustomModelData` 方案，直接硬编码编号。
2. **中等场景**（50-500 种模型）：使用 Scoreboard 方案，配合 `item_modifier` 动态写入。
3. **复杂场景**（> 500 种模型或需要动态分配）：使用 Storage 方案，配合 `schedule` 定期持久化。
4. **自动化场景**（玩家获得物品时自动分配）：使用 Advancement 方案，但注意触发条件过滤。
