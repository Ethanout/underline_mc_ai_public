# 如何清理临时对象

## 问题背景

在 Minecraft 数据包开发中，我们经常需要创建临时实体（如标记实体、盔甲架、区域效果云）来存储数据、计时、或作为占位符。如果不及时清理，这些实体将永久存在于世界中，导致：
- 性能下降（实体数量过多）
- 存档体积膨胀
- 干扰其他系统的实体选择器

核心挑战：**如何可靠地检测临时对象何时不再需要，并在不影响其他系统的情况下将其移除？**

---

## 方案一：基于计时的自动清理（最常用）

### 原理

为临时实体设置一个 `Age` 标签（或自定义计分板），在 tick 函数中递减，当值归零时执行清理。这是最直观、最可控的方案。

### 适用版本

1.13+（所有版本通用）

### 完整实现

#### 1. 创建临时实体时初始化

`data/<namespace>/function/spawn_temp.mcfunction`
```mcfunction
# 生成一个标记实体作为临时对象
summon minecraft:marker ~ ~ ~ {Tags:["temp_obj"]}

# 为实体设置计分板初始值
scoreboard players set @e[type=minecraft:marker,tag=temp_obj,limit=1,sort=nearest] temp_lifetime 100
```

#### 2. 在 load 中初始化计分板

`data/<namespace>/function/load.mcfunction`
```mcfunction
scoreboard objectives add temp_lifetime dummy
```

#### 3. 每 tick 递减并清理

`data/<namespace>/function/tick.mcfunction`
```mcfunction
# 递减所有临时对象的寿命
scoreboard players remove @e[type=minecraft:marker,tag=temp_obj] temp_lifetime 1

# 清理寿命归零的对象
execute as @e[type=minecraft:marker,tag=temp_obj,scores={temp_lifetime=0}] run function <namespace>:cleanup_temp
```

`data/<namespace>/function/cleanup_temp.mcfunction`
```mcfunction
# 执行清理逻辑（如掉落物、粒子效果等）
# ...

# 移除实体
kill @s
```

### 陷阱与注意事项

1. **计分板初始化时机**：必须在 `#minecraft:load` 标签中初始化计分板，否则首次 tick 会报错。
2. **选择器性能**：`@e[type=minecraft:marker,tag=temp_obj]` 在实体数量较多时性能开销中等。如果临时对象数量超过 1000，建议使用更精确的选择器（如按距离筛选）。
3. **Age 标签 vs 计分板**：原版实体有 `Age` 标签（盔甲架、区域效果云等），但标记实体（marker）没有。使用计分板更通用。
4. **清理顺序**：如果临时对象之间有依赖关系（如 A 引用了 B），需要确保先清理被依赖的对象，否则可能导致数据不一致。

## 方案二：基于区块卸载的自动清理（被动清理）

### 原理

利用 Minecraft 的实体卸载机制：当实体所在的区块被卸载时，实体也会被移除。通过将临时实体放置在不会被加载的区块中，或利用 `Persistent` 标签控制是否在区块卸载时保留。

### 适用版本

1.16+（`Persistent` 标签在 1.16 引入）

### 完整实现

#### 1. 创建非持久化临时实体

`data/<namespace>/function/spawn_temp_nonpersist.mcfunction`
```mcfunction
# 生成一个非持久化的标记实体
summon minecraft:marker ~ ~ ~ {Tags:["temp_obj","non_persist"],Persistent:0b}
```

#### 2. 在 tick 中检查并清理已卸载的实体

`data/<namespace>/function/tick.mcfunction`
```mcfunction
# 清理所有非持久化且不在加载区块中的临时对象
# 注意：这个命令本身不会触发，因为实体不在加载区块中时无法被选择
# 实际清理发生在实体所在的区块被重新加载时
```

### 陷阱与注意事项

1. **⚠️ 需验证**：`Persistent:0b` 的实体在区块卸载时是否一定会被移除？根据 Minecraft Wiki，`Persistent` 为 `false` 的实体在区块卸载时会被移除，但标记实体（marker）的行为可能不同。
2. **不可靠性**：如果玩家从未离开过临时实体所在的区块，实体将永远不会被清理。因此此方案只能作为辅助手段，不能作为主要清理机制。
3. **无法控制清理时机**：你无法精确控制实体何时被清理，只能依赖区块卸载事件。
4. **性能开销**：低，因为不需要每 tick 检查。

## 方案三：基于进度触发的条件清理（事件驱动）

### 原理

利用进度（advancement）的 `tick` 触发器或自定义触发器，在特定条件满足时触发清理函数。适用于"当玩家离开某个区域时清理"或"当某个任务完成时清理"等场景。

### 适用版本

1.13+（进度系统）

### 完整实现

#### 1. 创建进度监听

`data/<namespace>/advancement/cleanup_on_leave.json`
```json
{
  "criteria": {
    "left_area": {
      "trigger": "minecraft:location",
      "conditions": {
        "player": {
          "location": {
            "structure": "minecraft:stronghold"
          }
        }
      }
    }
  },
  "rewards": {
    "function": "<namespace>:cleanup_area_temps"
  }
}
```

#### 2. 清理函数

`data/<namespace>/function/cleanup_area_temps.mcfunction`
```mcfunction
# 清理特定区域内的临时对象
kill @e[type=minecraft:marker,tag=temp_obj,distance=..10]

# 撤销进度，以便下次再次触发
advancement revoke @s only <namespace>:cleanup_on_leave
```

### 陷阱与注意事项

1. **进度触发延迟**：进度检测不是实时的，可能有 1-2 tick 的延迟。
2. **条件复杂度**：进度条件有限，无法表达复杂的逻辑（如"玩家离开区域且时间超过 5 秒"）。
3. **性能开销**：低，因为进度只在条件变化时触发。
4. **撤销进度**：必须记得撤销进度，否则只会触发一次。

## 方案四：基于实体标签的批量清理（手动触发）

### 原理

为所有临时对象添加统一的标签（如 `temp_obj`），在需要清理时通过 `kill @e[tag=temp_obj]` 批量移除。适用于"游戏阶段切换"或"重置场景"等场景。

### 适用版本

1.13+（标签系统）

### 完整实现

#### 1. 创建临时实体时添加标签

`data/<namespace>/function/spawn_temp_tagged.mcfunction`
```mcfunction
summon minecraft:marker ~ ~ ~ {Tags:["temp_obj","spawned_by_player"]}
```

#### 2. 批量清理函数

`data/<namespace>/function/cleanup_all_temps.mcfunction`
```mcfunction
# 清理所有临时对象
kill @e[tag=temp_obj]

# 可选：清理其他类型的临时对象
kill @e[type=minecraft:area_effect_cloud,tag=temp_effect]
```

### 陷阱与注意事项

1. **标签冲突**：确保 `temp_obj` 标签不会被其他系统意外使用。建议使用命名空间前缀，如 `<namespace>_temp`。
2. **误删风险**：如果某个实体被错误地添加了 `temp_obj` 标签，它会被误删。建议在创建时严格管理标签。
3. **性能开销**：低，但 `kill` 命令本身在实体数量较多时（>1000）会有中等开销。
4. **无法精确控制**：无法区分"应该保留的临时对象"和"应该清理的临时对象"，除非使用更细粒度的标签。

## 方案五：基于数据存储的引用计数清理（高级）

### 原理

在 storage 中维护一个引用计数表，记录每个临时对象被引用的次数。当引用计数归零时，自动清理该对象。适用于复杂的依赖关系场景。

### 适用版本

1.20.5+（storage 系统完善）

### 完整实现

#### 1. 初始化 storage

`data/<namespace>/function/load.mcfunction`
```mcfunction
data modify storage <namespace>:temp_refs refs set value {}
```

#### 2. 创建临时对象并注册引用

`data/<namespace>/function/spawn_temp_refcounted.mcfunction`
```mcfunction
# 生成临时对象
summon minecraft:marker ~ ~ ~ {Tags:["temp_obj","ref_counted"]}

# 获取实体 UUID
data modify storage <namespace>:temp_refs refs append value {uuid:"<uuid>",count:1}
```

#### 3. 增加/减少引用

`data/<namespace>/function/increment_ref.mcfunction`
```mcfunction
# 增加引用计数
data modify storage <namespace>:temp_refs refs[{uuid:"<uuid>"}].count set value 1
```

`data/<namespace>/function/decrement_ref.mcfunction`
```mcfunction
# 减少引用计数
data modify storage <namespace>:temp_refs refs[{uuid:"<uuid>"}].count set value -1

# 检查是否归零
execute if data storage <namespace>:temp_refs refs[{uuid:"<uuid>",count:0}] run function <namespace>:cleanup_by_uuid
```

#### 4. 清理函数

`data/<namespace>/function/cleanup_by_uuid.mcfunction`
```mcfunction
# 根据 UUID 清理实体
kill @e[type=minecraft:marker,tag=ref_counted]

# 从 storage 中移除引用记录
data remove storage <namespace>:temp_refs refs[{uuid:"<uuid>"}]
```

### 陷阱与注意事项

1. **⚠️ 需验证**：`data modify` 的 `set value 1` 和 `set value -1` 语法是否正确？在 1.20.5+ 中，`data modify` 支持算术运算吗？如果不支持，需要使用 `scoreboard` 进行计数。
2. **UUID 管理**：获取实体的 UUID 需要 `data get entity @s UUID`，但 UUID 是数组格式 `[I;1,2,3,4]`，在 storage 中存储和比较时需要注意格式。
3. **性能开销**：高，因为需要维护 storage 中的引用计数表，且每次引用变化都需要查询和修改。
4. **复杂度**：实现复杂，容易出错。仅在确实需要引用计数的场景下使用。

## 方案对比

| 方案 | 版本要求 | 性能开销 | 可靠性 | 适用场景 |
|------|---------|---------|--------|---------|
| 计时清理 | 1.13+ | 中（每 tick 递减） | 高 | 通用场景，如粒子效果、临时标记 |
| 区块卸载清理 | 1.16+ | 低 | 低（依赖区块卸载） | 辅助清理，防止实体残留 |
| 进度触发清理 | 1.13+ | 低 | 中（有延迟） | 事件驱动场景，如玩家离开区域 |
| 批量标签清理 | 1.13+ | 低 | 高（但可能误删） | 游戏阶段切换、重置场景 |
| 引用计数清理 | 1.20.5+ | 高 | 高 | 复杂依赖关系场景 |

---

## 最佳实践建议

1. **默认使用计时清理**：简单可靠，适用于大多数场景。
2. **结合区块卸载清理**：作为兜底机制，防止计时器失效导致的实体残留。
3. **避免引用计数**：除非确实需要，否则不要引入不必要的复杂度。
4. **统一标签命名**：使用 `<namespace>_temp` 格式，避免标签冲突。
5. **在 load 中初始化**：所有计分板、storage 等资源必须在 `#minecraft:load` 中初始化。
