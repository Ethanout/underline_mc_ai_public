# 如何处理友方和敌方

## 问题核心

在 Minecraft 数据包开发中，"友方/敌方"系统面临的核心挑战是：**原版没有内置的阵营系统**。你需要自己设计一套机制来区分哪些实体是"自己人"、哪些是"敌人"。这通常涉及：

1. **如何标记阵营**（给实体打标签）
2. **如何检测阵营**（判断两个实体是否敌对）
3. **如何实现攻击/交互限制**（防止误伤友军）

## 方案一：基于 Team 的阵营系统（推荐，1.13+）

### 原理

Minecraft 原版的 `team` 系统提供了内置的友军伤害控制、碰撞检测和颜色标记。通过将实体分配到不同队伍，可以：
- 同一队伍的实体之间默认无友军伤害（`friendlyFire` 设为 false）
- 不同队伍的实体可以互相攻击
- 队伍有颜色前缀，方便玩家识别

### 完整实现

#### 1. 创建队伍（在 load 函数中执行一次）

```mcfunction
# load.mcfunction
team add friendly "§a友军"
team add enemy "§c敌军"

# 设置友军队伍：禁止友军伤害
team modify friendly friendlyFire false
# 设置友军队伍：显示队伍颜色前缀
team modify friendly color green
# 设置友军队伍：允许碰撞
team modify friendly collisionRule always

# 设置敌军队伍：允许友军伤害（虽然通常不会把敌军和自己人放一个队）
team modify enemy friendlyFire true
team modify enemy color red
team modify enemy collisionRule always
```

#### 2. 将实体加入队伍

```mcfunction
# 将玩家加入友军队伍
team join friendly @a

# 将特定实体加入敌军队伍（例如：生成的僵尸）
team join enemy @e[type=zombie,tag=spawned_by_system]
```

#### 3. 检测阵营关系

```mcfunction
# 检测玩家是否与某个实体敌对
# 方法：检查实体是否在敌军队伍中
execute as @a at @s if entity @e[type=zombie,tag=spawned_by_system,team=enemy,distance=..10] run say 发现敌军！

# 检测两个实体是否在同一队伍
# 需要借助 scoreboard 或 storage 比较
# 方案：将队伍名写入 scoreboard
scoreboard objectives add team_id dummy

# 在 tick 中更新队伍 ID（示例：将队伍名映射为数字）
execute as @e[team=friendly] run scoreboard players set @s team_id 1
execute as @e[team=enemy] run scoreboard players set @s team_id 2
execute as @e[team=] run scoreboard players set @s team_id 0

# 然后比较两个实体的 team_id 是否相等
execute as @a at @s if entity @e[type=zombie,team=enemy,distance=..10] run say 敌军接近！
```

#### 4. 实现攻击限制（防止误伤友军）

```mcfunction
# 在玩家攻击时检测目标是否为友军
# 使用 advancements 监听玩家攻击实体
# advancements/player/hurt_entity.json
{
  "criteria": {
    "hurt_enemy": {
      "trigger": "minecraft:player_hurt_entity",
      "conditions": {
        "entity": {
          "type": "#minecraft:skeletons",
          "team": "friendly"
        }
      }
    }
  },
  "rewards": {
    "function": "namespace:punish_friendly_fire"
  }
}
```

```mcfunction
# punish_friendly_fire.mcfunction
# 撤销伤害（通过设置伤害为0，但原版无法直接撤销）
# 替代方案：给攻击者惩罚
title @s actionbar "§c不要攻击友军！"
effect give @s slowness 3 2 true
# 或者：将攻击者传送走
# tp @s ~ ~ ~
```

### 陷阱与注意事项

1. **Team 的局限性**：Team 只能管理实体，不能管理"抽象阵营"。例如，一个 NPC 可能在不同情境下是友军或敌军，需要动态切换队伍。
2. **队伍数量限制**：Minecraft 最多支持 256 个队伍（0-255），但实际使用中建议不超过 10 个。
3. **玩家默认无队伍**：新加入的玩家需要手动加入队伍，否则无法享受队伍保护。
4. **实体死亡后队伍保留**：实体死亡后队伍信息会丢失（除非使用 `@e[type=...]` 重新加入）。
5. **性能开销**：每 tick 更新所有实体的 team_id 可能开销较高，建议只在需要时更新。

## 方案二：基于 Tag 的阵营系统（1.13+，更灵活）

### 原理

使用 `tag` 命令给实体打上阵营标签，然后通过 `@e[tag=friendly]` 或 `@e[tag=enemy]` 选择器检测。这种方式比 Team 更灵活，但需要手动管理友军伤害。

### 完整实现

#### 1. 标记阵营

```mcfunction
# 在实体生成时打标签
summon zombie ~ ~ ~ {Tags:["enemy"]}
summon villager ~ ~ ~ {Tags:["friendly"]}

# 给玩家打标签
tag @a add friendly
```

#### 2. 检测阵营

```mcfunction
# 检测玩家附近的敌军
execute as @a[tag=friendly] at @s if entity @e[tag=enemy,distance=..10] run say 发现敌军！

# 检测两个实体是否敌对
# 需要比较标签，可以使用 scoreboard 或 storage
scoreboard objectives add is_enemy dummy

# 在 tick 中更新
execute as @e[tag=enemy] run scoreboard players set @s is_enemy 1
execute as @e[tag=friendly] run scoreboard players set @s is_enemy 0
execute as @e[tag=!friendly,tag=!enemy] run scoreboard players set @s is_enemy -1
```

#### 3. 实现攻击限制

```mcfunction
# 使用 advancements 监听攻击事件
# advancements/player/hurt_entity.json
{
  "criteria": {
    "hurt_friendly": {
      "trigger": "minecraft:player_hurt_entity",
      "conditions": {
        "entity": {
          "type": "#minecraft:entities",
          "nbt": "{Tags:[\"friendly\"]}"
        }
      }
    }
  },
  "rewards": {
    "function": "namespace:punish_friendly_fire"
  }
}
```

```mcfunction
# punish_friendly_fire.mcfunction
title @s actionbar "§c不要攻击友军！"
effect give @s slowness 3 2 true
```

### 陷阱与注意事项

1. **Tag 无法控制友军伤害**：原版 `friendlyFire` 只对 Team 有效。使用 Tag 时，你需要自己实现伤害检测和惩罚。
2. **Tag 选择器性能**：`@e[tag=...]` 在大量实体时性能较好，但 `nbt={Tags:...}` 在 advancement 条件中可能较慢。
3. **标签冲突**：确保标签名称唯一，避免与其他数据包冲突。
4. **实体死亡后标签丢失**：实体死亡后标签会丢失，需要在重生时重新添加。

## 方案三：基于 Scoreboard 的阵营系统（1.13+，最灵活）

### 原理

使用 `scoreboard` 为每个实体分配一个阵营 ID（数字），然后通过比较 ID 来判断阵营关系。这种方式最灵活，可以支持多阵营、动态切换、阵营等级等复杂逻辑。

### 完整实现

#### 1. 创建阵营计分板

```mcfunction
# load.mcfunction
scoreboard objectives add faction dummy
# 定义阵营 ID：
# 0 = 无阵营
# 1 = 友军
# 2 = 敌军
# 3 = 中立
```

#### 2. 分配阵营

```mcfunction
# 给玩家分配阵营
scoreboard players set @a faction 1

# 给实体分配阵营
execute as @e[type=zombie] run scoreboard players set @s faction 2
execute as @e[type=villager] run scoreboard players set @s faction 1
```

#### 3. 检测阵营关系

```mcfunction
# 检测玩家附近的敌军（faction == 2）
execute as @a at @s if entity @e[type=zombie,scores={faction=2},distance=..10] run say 发现敌军！

# 检测两个实体是否在同一阵营
# 需要比较分数，可以使用 execute store 或 storage
# 方案：将攻击者的阵营分数存储到 storage，然后比较
execute as @a at @s store result storage namespace:temp attacker_faction int 1 run scoreboard players get @s faction
execute as @e[type=zombie] at @s store result storage namespace:temp target_faction int 1 run scoreboard players get @s faction
execute if data storage namespace:temp {attacker_faction:1,target_faction:1} run say 友军攻击友军！
```

#### 4. 实现攻击限制

```mcfunction
# 使用 advancements 监听攻击事件，并在函数中比较阵营
# advancements/player/hurt_entity.json
{
  "criteria": {
    "hurt_entity": {
      "trigger": "minecraft:player_hurt_entity"
    }
  },
  "rewards": {
    "function": "namespace:check_faction"
  }
}
```

```mcfunction
# check_faction.mcfunction
# 获取攻击者和目标的阵营
execute store result storage namespace:temp attacker_faction int 1 run scoreboard players get @s faction
execute as @e[type=#minecraft:entities,sort=nearest,limit=1] store result storage namespace:temp target_faction int 1 run scoreboard players get @s faction

# 比较阵营
execute if data storage namespace:temp {attacker_faction:1,target_faction:1} run function namespace:punish_friendly_fire
execute if data storage namespace:temp {attacker_faction:2,target_faction:2} run function namespace:punish_friendly_fire
```

### 陷阱与注意事项

1. **分数范围限制**：`scoreboard` 的分数范围是 -2,147,483,648 到 2,147,483,647，足够使用。
2. **实体死亡后分数保留**：与 Tag 不同，`scoreboard` 分数在实体死亡后仍然保留（除非使用 `scoreboard players reset`）。
3. **性能开销**：每 tick 更新所有实体的分数可能开销较高，建议只在需要时更新。
4. **分数比较的复杂性**：使用 `execute store` 和 `data` 比较分数需要额外的 storage 操作，可能增加复杂度。

## 方案对比

| 方案 | 版本要求 | 性能开销 | 灵活性 | 友军伤害控制 | 适用场景 |
|------|---------|---------|--------|-------------|---------|
| Team | 1.13+ | 低 | 中 | 原生支持 | 简单的友军/敌军系统，需要原生友军伤害控制 |
| Tag | 1.13+ | 低 | 高 | 需手动实现 | 需要动态切换阵营，或需要多个阵营标签 |
| Scoreboard | 1.13+ | 中 | 最高 | 需手动实现 | 复杂阵营系统，需要阵营等级、动态关系等 |

## 推荐方案

### 简单场景（如 PvE 地图）
使用 **Team 方案**，因为原生支持友军伤害控制，实现简单。

### 中等复杂度（如 RPG 地图）
使用 **Tag 方案**，因为灵活性高，且性能开销低。

### 复杂场景（如多阵营战争）
使用 **Scoreboard 方案**，因为可以支持阵营等级、动态关系、阵营切换等复杂逻辑。

## 进阶技巧：动态阵营关系

### 实现阵营间的关系矩阵

```mcfunction
# 使用 storage 存储阵营关系矩阵
data modify storage namespace:faction_relations set value {friendly:[1],enemy:[2],neutral:[3]}

# 检测两个阵营的关系
# 假设 attacker_faction = 1, target_faction = 2
execute if data storage namespace:faction_relations {enemy:[2]} run say 敌对关系！
```

### 实现阵营切换

```mcfunction
# 玩家切换阵营
scoreboard players set @s faction 2
# 或者
tag @s remove friendly
tag @s add enemy
```

## 陷阱总结

1. **Team 的 friendlyFire 只对同一队伍有效**：不同队伍的实体之间总是可以互相伤害。
2. **Tag 和 Scoreboard 需要手动处理友军伤害**：原版不会自动阻止友军攻击。
3. **实体死亡后状态丢失**：Tag 和 Team 在实体死亡后会丢失，需要在重生时重新设置。
4. **性能考虑**：每 tick 更新所有实体的阵营信息可能开销较高，建议使用 advancement 触发更新。
5. **多数据包冲突**：确保阵营名称/ID 唯一，避免与其他数据包冲突。
