# 如何防止状态互相打架

## 问题背景

在 Minecraft 数据包开发中，"状态打架"指多个独立的状态系统（如潜行、飞行、游泳、爬行、状态效果等）同时作用于玩家时，由于原版状态机本身的优先级和互斥规则，导致玩家行为异常、动画冲突或状态切换失败。例如：玩家在飞行时尝试游泳，或潜行时被强制进入爬行状态。

## 一、状态优先级系统（推荐方案）

### 原理

Minecraft 原版状态机有固定的优先级层级。通过理解并利用这些优先级，可以设计一个"状态管理器"，确保高优先级状态覆盖低优先级状态，避免冲突。

核心优先级规则（从高到低）：
1. 死亡（最高优先级）
2. 飞行（`abilities.mayfly` + `flying`）
3. 游泳（`swimming`）
4. 爬行（`pose:swimming` + 高度条件）
5. 潜行（`sneaking`）
6. 站立/行走（最低优先级）

### 完整实现

#### 1. 状态注册系统

`data/<namespace>/function/state/register.mcfunction`
```mcfunction
# 初始化玩家状态存储
scoreboard objectives add <namespace>.state dummy
scoreboard objectives add <namespace>.state_priority dummy

# 为每个玩家创建状态记录
execute as @a run scoreboard players set @s <namespace>.state 0
execute as @a run scoreboard players set @s <namespace>.state_priority 0
```

#### 2. 状态优先级检查

`data/<namespace>/function/state/check_priority.mcfunction`
```mcfunction
# 检查当前状态优先级是否允许切换
# 输入：@s 为玩家，$state_id 为要切换的状态ID，$priority 为优先级
# 输出：如果允许切换，设置 score $allow 为 1

# 获取当前状态优先级
scoreboard players operation $current_priority <namespace>.state_priority = @s <namespace>.state_priority

# 如果新状态优先级 >= 当前优先级，允许切换
execute if score $priority <namespace>.state_priority >= $current_priority <namespace>.state_priority run scoreboard players set $allow <namespace>.state 1
execute if score $priority <namespace>.state_priority < $current_priority <namespace>.state_priority run scoreboard players set $allow <namespace>.state 0
```

#### 3. 状态切换函数

`data/<namespace>/function/state/switch.mcfunction`
```mcfunction
# 切换到指定状态
# 输入：@s 为玩家，$state_id 为状态ID，$priority 为优先级

# 先检查优先级

# 如果允许切换
execute if score $allow <namespace>.state matches 1 run {
    # 更新状态记录
    scoreboard players operation @s <namespace>.state = $state_id <namespace>.state
    scoreboard players operation @s <namespace>.state_priority = $priority <namespace>.state_priority
    
    # 执行状态切换逻辑
    function <namespace>:state/apply with entity @s
}
```

#### 4. 状态应用函数（使用宏）

`data/<namespace>/function/state/apply.mcfunction`
```mcfunction

# 输入：$state_id

$execute if score $state_id <namespace>.state matches 4 run function <namespace>:state/sneaking
```

### 陷阱与注意事项

1. **原版状态覆盖**：即使你的系统设置了优先级，原版状态机仍然会强制执行自己的规则。例如，当玩家在1格高的空间时，原版会强制进入爬行状态，无论你的系统如何设置。

2. **状态切换延迟**：使用 `execute` 链进行状态检查时，可能存在1 tick的延迟。对于需要即时响应的场景（如飞行切换），建议在 `tick` 函数中每 tick 检查一次。

3. **优先级数值冲突**：确保不同状态使用不同的优先级数值，避免两个状态优先级相同导致不确定行为。

4. **状态ID管理**：建议使用独立的 scoreboard 或 storage 来管理状态ID映射，避免硬编码。

## 二、状态互斥表（进阶方案）

### 原理

建立一个状态互斥矩阵，明确哪些状态不能共存。当尝试进入新状态时，检查互斥表，如果与当前状态冲突，则拒绝切换或自动退出冲突状态。

### 完整实现

#### 1. 互斥表定义

`data/<namespace>/function/state/mutex_table.mcfunction`
```mcfunction
# 互斥表：每个状态ID映射到它不能共存的状态ID列表
# 格式：$state_id -> $mutex_state_ids (逗号分隔)

# 飞行(1) 不能与 游泳(2) 共存
scoreboard players set $mutex_1 <namespace>.state 2

# 游泳(2) 不能与 飞行(1)、潜行(4) 共存
scoreboard players set $mutex_2 <namespace>.state 1,4

# 爬行(3) 不能与 飞行(1)、游泳(2) 共存
scoreboard players set $mutex_3 <namespace>.state 1,2

# 潜行(4) 不能与 游泳(2)、爬行(3) 共存
scoreboard players set $mutex_4 <namespace>.state 2,3
```

#### 2. 互斥检查函数

`data/<namespace>/function/state/check_mutex.mcfunction`
```mcfunction
# 检查新状态是否与当前状态互斥
# 输入：@s 为玩家，$new_state 为新状态ID
# 输出：如果互斥，设置 $mutex_conflict 为 1

# 获取当前状态
scoreboard players operation $current_state <namespace>.state = @s <namespace>.state

# 获取当前状态的互斥列表
scoreboard players operation $mutex_list <namespace>.state = $mutex_$current_state <namespace>.state

# 检查新状态是否在互斥列表中
# ⚠️ 需验证：scoreboard 的字符串比较功能
execute if score $new_state <namespace>.state = $mutex_list <namespace>.state run scoreboard players set $mutex_conflict <namespace>.state 1
```

#### 3. 自动退出冲突状态

`data/<namespace>/function/state/auto_resolve.mcfunction`
```mcfunction
# 当检测到互斥时，自动退出冲突状态
# 输入：@s 为玩家，$new_state 为新状态ID

# 如果互斥，先退出当前状态
execute if score $mutex_conflict <namespace>.state matches 1 run {
    # 退出当前状态
    function <namespace>:state/exit with entity @s
    
    # 然后进入新状态
    function <namespace>:state/switch with entity @s
}
```

### 陷阱与注意事项

1. **互斥表维护成本**：随着状态数量增加，互斥表会变得复杂。建议使用脚本生成互斥表，而不是手动维护。

2. **循环互斥**：确保互斥关系是单向的，避免 A 互斥 B 且 B 互斥 A 导致死循环。

3. **状态退出副作用**：退出状态时，需要清理该状态的所有副作用（如移除状态效果、重置属性等）。

## 三、状态机事件队列（防冲突终极方案）

### 原理

使用事件队列机制，所有状态变更请求先进入队列，由中央调度器按优先级和互斥规则处理。这样可以避免多个状态同时修改玩家状态导致的冲突。

### 完整实现

#### 1. 事件队列存储

`data/<namespace>/function/state/queue_init.mcfunction`
```mcfunction
# 初始化事件队列
scoreboard objectives add <namespace>.event_queue dummy
scoreboard objectives add <namespace>.event_priority dummy

# 创建队列存储实体
summon minecraft:marker ~ ~ ~ {Tags:["<namespace>.event_queue"]}
```

#### 2. 事件入队

`data/<namespace>/function/state/enqueue.mcfunction`
```mcfunction
# 将状态变更请求加入队列
# 输入：@s 为玩家，$state_id 为状态ID，$priority 为优先级

# 创建事件实体
summon minecraft:marker ~ ~ ~ {Tags:["<namespace>.event_item"]}

# 存储事件数据
data modify entity @e[tag=<namespace>.event_item,limit=1] data.<namespace>.player set from entity @s UUID
data modify entity @e[tag=<namespace>.event_item,limit=1] data.<namespace>.state_id set value $state_id
data modify entity @e[tag=<namespace>.event_item,limit=1] data.<namespace>.priority set value $priority

# 将事件加入队列
tag @e[tag=<namespace>.event_item,limit=1] add <namespace>.queued
```

#### 3. 事件调度器

`data/<namespace>/function/state/dispatch.mcfunction`
```mcfunction
# 每 tick 执行的事件调度器
# 处理队列中的事件

# 获取队列中优先级最高的事件
execute as @e[tag=<namespace>.queued,sort=arbitrary,limit=1] run {
    # 获取事件数据
    data get entity @s data.<namespace>.state_id
    data get entity @s data.<namespace>.priority
    
    # 检查互斥
    execute store result score $player <namespace>.state run data get entity @s data.<namespace>.player
    execute store result score $state_id <namespace>.state run data get entity @s data.<namespace>.state_id
    execute store result score $priority <namespace>.state run data get entity @s data.<namespace>.priority
    
    # 执行状态切换
    execute as @s[type=!minecraft:player] run function <namespace>:state/switch
    
    # 移除已处理的事件
    kill @s
}
```

### 陷阱与注意事项

1. **队列积压**：如果事件产生速度超过处理速度，队列会无限增长。建议设置最大队列长度。

2. **事件优先级反转**：高优先级事件可能被低优先级事件阻塞。需要实现优先级抢占机制。

3. **实体数量限制**：使用 marker 实体存储事件，大量事件可能导致实体数量过多。建议定期清理过期事件。

## 方案对比

| 方案 | 版本要求 | 性能开销 | 适用场景 | 复杂度 |
|------|---------|---------|---------|--------|
| 状态优先级系统 | 1.13+ | 低 | 简单状态管理，如飞行/潜行切换 | 低 |
| 状态互斥表 | 1.13+ | 中 | 复杂状态系统，如RPG状态效果 | 中 |
| 事件队列 | 1.16+（需要marker实体） | 高 | 高并发状态变更，如多人游戏 | 高 |

## 最佳实践建议

1. **优先使用原版状态机**：对于简单的状态切换（如潜行、飞行），尽量利用原版机制，避免重复造轮子。

2. **状态ID标准化**：使用统一的 scoreboard 或 storage 存储状态ID，避免不同系统使用不同的标识方式。

3. **状态切换原子化**：确保状态切换操作是原子的，避免在切换过程中被其他系统中断。

4. **日志记录**：在关键状态切换点添加日志，便于调试状态冲突问题。

5. **性能监控**：对于高频状态切换（如每 tick 检查），注意性能开销，必要时使用 `schedule` 降低频率。
