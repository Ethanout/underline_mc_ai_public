# 如何让实体朝另一个实体移动

## 核心挑战

让实体朝另一个实体移动，本质上是**计算方向向量并沿该方向施加运动**。原版 Minecraft 数据包没有直接的“朝向目标移动”命令，需要利用 `execute` 的旋转机制、`tp` 的相对坐标、或 `Motion` NBT 来实现。不同方案在精度、性能、版本兼容性上差异显著。

---

## 方案一：基于 `execute rotated` + `tp ^ ^ ^`（推荐，1.13+）

### 原理

利用 `execute rotated` 将执行者的视角旋转到目标方向，然后使用 `tp ^ ^ ^<距离>`（局部坐标，即“前方向”）让实体沿该方向移动。局部坐标 `^ ^ ^` 始终以执行者的朝向为基准：`^0 ^0 ^1` 表示正前方 1 格。

### 完整代码

文件结构：
```
data/<namespace>/function/move/
├── toward.mcfunction          # 主函数：让实体朝目标移动
├── toward_entity.mcfunction   # 被调用的子函数（每个实体执行一次）
```

`data/<namespace>/function/move/toward.mcfunction`（主函数，在 tick 中调用）：
```mcfunction
# 用法：让 @e[tag=follow] 朝最近的玩家移动
# 参数：$speed 为移动速度（格/ tick），通过 storage 传入
execute as @e[tag=follow] at @s run function <namespace>:move/toward_entity
```

`data/<namespace>/function/move/toward_entity.mcfunction`：
```mcfunction
# 假设目标为最近的玩家（可替换为任意实体选择器）
# 步骤1：将执行者的旋转设为朝向目标
execute rotated as @p run tp @s ^ ^ ^0.1
# 注意：这里 tp 的距离就是移动速度，0.1 格/tick = 2 格/秒（20 tick）
```

### 陷阱与注意事项

1. **`tp` 会触发位置同步**：`tp` 命令会立即将实体移动到新位置，并同步给客户端。如果每 tick 都执行，会产生明显的“瞬移”感，而非平滑移动。适合低速或低频移动（如每 2-3 tick 执行一次）。
2. **`execute rotated as` 的朝向问题**：`rotated as @p` 会将执行者的旋转设为与 `@p` 完全相同，但 `@p` 的旋转是**视角方向**，而非“从执行者指向目标”的方向。**这个方案实际上让实体朝目标玩家的视线方向移动，而非朝目标位置移动**——这是一个常见的误解。
3. **正确做法**：应使用 `execute rotated as @s facing entity @p` 来让执行者朝向目标，然后再 `tp ^ ^ ^`。

### 修正后的正确代码

`data/<namespace>/function/move/toward_entity.mcfunction`：
```mcfunction
# 正确：先让执行者朝向目标，再沿局部前方移动
execute facing entity @p feet run tp @s ^ ^ ^0.1
```

## 方案二：基于 `Motion` NBT 修改（1.13+，平滑移动）

### 原理

直接修改实体的 `Motion` 标签（`[dx, dy, dz]`），赋予其朝向目标的速度向量。需要计算方向向量并归一化，但原版数据包没有 `sqrt` 或向量归一化命令，因此需要**近似方法**。

### 方案二A：固定速度 + 朝向修正（推荐，精度可接受）

原理：不计算精确方向向量，而是利用 `execute facing` 改变实体朝向，然后通过 `data modify` 设置 `Motion` 为固定值（如 `[0.0, 0.0, 0.2]`），再配合 `execute rotated` 将速度旋转到目标方向。

#### 完整代码

`data/<namespace>/function/move/toward_motion.mcfunction`：
```mcfunction
# 让实体朝最近的玩家移动，速度 0.2 格/tick
# 步骤1：保存当前朝向
execute store result score @s temp_x run data get entity @s Rotation[0]
execute store result score @s temp_y run data get entity @s Rotation[1]

# 步骤2：朝向目标（这会改变实体的 Rotation）
execute facing entity @p feet run data modify entity @s Rotation set from entity @s Rotation

# 步骤3：设置 Motion 为局部前方方向（^ ^ ^ 的近似）
# 注意：Motion 是世界坐标，不是局部坐标，所以需要旋转
# 这里使用一个技巧：先 tp 一个标记实体来获取方向向量
summon minecraft:marker ~ ~ ~ {Tags:["dir_calc"]}
execute as @e[tag=dir_calc,limit=1] at @s run tp @s ^ ^ ^1
execute as @e[tag=dir_calc,limit=1] at @s run data modify entity @s Pos set from entity @s Pos
# ⚠️ 需验证：能否通过标记实体的位置差计算方向向量？
# 实际上，更简单的方法是利用 execute rotated 直接设置 Motion

# 更简洁的方案：直接使用 execute rotated 将 Motion 旋转到目标方向
execute facing entity @p feet rotated as @s run data modify entity @s Motion set value [0.0, 0.0, 0.2]
```

**⚠️ 需验证**：`data modify entity @s Motion set value [0.0, 0.0, 0.2]` 后，Motion 是世界坐标的 Z 正方向，但 `execute rotated as @s` 不会自动旋转 Motion。Motion 始终是世界坐标，不受实体 Rotation 影响。

### 方案二B：基于 `tp` 计算位移向量（1.13+，精确但复杂）

原理：每 tick 记录实体位置，计算与目标位置的差值，然后通过 `data modify` 设置 Motion 为差值乘以速度系数。

#### 完整代码

`data/<namespace>/function/move/toward_motion_precise.mcfunction`：
```mcfunction
# 前提：在 storage 中存储了目标位置
# 假设目标位置在 storage <namespace>:target Pos

# 步骤1：获取实体当前位置
execute store result score @s pos_x run data get entity @s Pos[0] 1000
execute store result score @s pos_y run data get entity @s Pos[1] 1000
execute store result score @s pos_z run data get entity @s Pos[2] 1000

# 步骤2：获取目标位置（从 storage 读取）
execute store result score @s target_x run data get storage <namespace>:target Pos[0] 1000
execute store result score @s target_y run data get storage <namespace>:target Pos[1] 1000
execute store result score @s target_z run data get storage <namespace>:target Pos[2] 1000

# 步骤3：计算差值（target - pos）
scoreboard players operation @s diff_x = @s target_x
scoreboard players operation @s diff_x -= @s pos_x
scoreboard players operation @s diff_y = @s target_y
scoreboard players operation @s diff_y -= @s pos_y
scoreboard players operation @s diff_z = @s target_z
scoreboard players operation @s diff_z -= @s pos_z

# 步骤4：归一化（近似：除以最大分量）
# 先找出最大绝对值分量
scoreboard players operation @s max_abs = @s diff_x
execute if score @s diff_y > @s max_abs run scoreboard players operation @s max_abs = @s diff_y
execute if score @s diff_z > @s max_abs run scoreboard players operation @s max_abs = @s diff_z
# 取绝对值（简化处理，实际需要 abs 操作）
execute if score @s max_abs < 0 run scoreboard players operation @s max_abs *= -1

# 步骤5：计算归一化后的速度分量（速度 = 差值 / 最大绝对值 * 速度系数）
# 使用分数运算：先乘以速度系数（如 100），再除以 max_abs
scoreboard players set @s speed 100  # 速度系数，0.1 格/tick
scoreboard players operation @s vel_x = @s diff_x
scoreboard players operation @s vel_x *= @s speed
scoreboard players operation @s vel_x /= @s max_abs
# 同理计算 vel_y, vel_z

# 步骤6：将速度写回 Motion
execute store result entity @s Motion[0] double 0.001 run scoreboard players get @s vel_x
execute store result entity @s Motion[1] double 0.001 run scoreboard players get @s vel_y
execute store result entity @s Motion[2] double 0.001 run scoreboard players get @s vel_z
```

### 陷阱与注意事项

1. **精度问题**：scoreboard 只能存储整数，因此需要放大系数（如 1000）来模拟小数。`execute store result entity @s Motion[0] double 0.001` 中的 `0.001` 是缩放因子，表示 scoreboard 值除以 1000 后写入。
2. **归一化不精确**：用最大分量归一化会导致方向偏差，尤其当目标在斜对角时。更精确的归一化需要欧几里得距离（`sqrt(dx²+dy²+dz²)`），但原版无法直接计算平方根。
3. **性能开销**：每个实体每 tick 执行约 20 条命令，100 个实体时约 2000 条命令/tick，开销中等。
4. **Motion 重置**：如果实体着地或碰撞，Motion 会被游戏重置，需要每 tick 重新设置。

## 方案三：基于 `teleport` 的平滑移动（1.13+，最简单）

### 原理

使用 `tp` 命令的 `^ ^ ^` 局部坐标，配合 `execute facing` 让实体朝向目标，然后每 tick 移动一小段距离。与方案一类似，但强调平滑性。

### 完整代码

`data/<namespace>/function/move/toward_smooth.mcfunction`：
```mcfunction
# 每 tick 移动 0.05 格（1 格/秒）
execute as @e[tag=follow] at @s run tp @s ^ ^ ^0.05
```

### 陷阱与注意事项

1. **`tp` 的朝向问题**：`tp @s ^ ^ ^0.05` 使用的是执行者当前的朝向。如果实体没有朝向目标，移动方向就是错的。因此需要先执行 `execute facing entity @p feet`。
2. **碰撞检测**：`tp` 会忽略碰撞箱，实体可能穿墙。如果需要碰撞检测，应使用 `Motion` 方案。
3. **客户端平滑**：`tp` 每 tick 移动小距离时，客户端会插值，看起来是平滑的。但网络延迟高时可能出现“瞬移”感。

### 修正后的正确代码

`data/<namespace>/function/move/toward_smooth.mcfunction`：
```mcfunction
# 先朝向目标，再移动
execute as @e[tag=follow] at @s facing entity @p feet run tp @s ^ ^ ^0.05
```

## 方案四：基于 `ride` 的“牵引”移动（1.13+，特殊场景）

### 原理

让目标实体骑乘一个标记实体，然后移动标记实体。利用 `ride` 命令让实体跟随。

### 完整代码

`data/<namespace>/function/move/toward_ride.mcfunction`：
```mcfunction
# 步骤1：让目标骑乘一个标记实体
execute as @p at @s run ride @s mount @e[tag=follow,limit=1]

# 步骤2：移动标记实体（标记实体朝目标移动）
execute as @e[tag=follow] at @s facing entity @p feet run tp @s ^ ^ ^0.1

# 步骤3：解除骑乘（如果需要）
execute as @p run ride @s dismount
```

### 陷阱与注意事项

1. **骑乘状态**：骑乘时，被骑乘实体的移动会带动骑乘者，但骑乘者的位置是相对于被骑乘实体的。如果被骑乘实体移动，骑乘者会跟随。
2. **适用场景**：适合让玩家被实体“拉”着走，或让实体“拖”着另一个实体移动。
3. **版本要求**：`ride` 命令在 1.13 引入，1.19+ 有 `ride @s mount` 语法。

## 方案对比

| 方案 | 版本要求 | 平滑度 | 精度 | 性能开销 | 适用场景 |
|------|---------|--------|------|---------|---------|
| 方案一：`tp ^ ^ ^` | 1.13+ | 中（有瞬移感） | 高（方向精确） | 低（1条命令/实体） | 简单跟随、弹幕 |
| 方案二A：Motion + 朝向 | 1.13+ | 高（物理引擎） | 中（方向近似） | 中（3-5条命令/实体） | 生物AI、平滑移动 |
| 方案二B：Motion + 向量计算 | 1.13+ | 高 | 高（但归一化有误差） | 高（20+条命令/实体） | 需要精确速度控制 |
| 方案三：`tp` 平滑 | 1.13+ | 高（客户端插值） | 高 | 低 | 玩家跟随、简单移动 |
| 方案四：`ride` 牵引 | 1.13+ | 高 | 中（受骑乘机制限制） | 低 | 牵引、拖拽 |

## 总结与推荐

- **最推荐**：方案一（`tp ^ ^ ^`）或方案三（`tp` 平滑），简单高效，适合大多数场景。
- **需要物理碰撞**：方案二A（Motion + 朝向），利用游戏物理引擎处理碰撞。
- **需要精确速度向量**：方案二B，但注意归一化误差和性能开销。
- **特殊牵引场景**：方案四（`ride`）。

**通用陷阱**：
- 所有方案都需要确保实体在 tick 循环中被正确执行（使用 `schedule` 或 `tick.json`）。
- 目标实体消失时，需要处理异常（如 `execute if entity @p` 前置判断）。
- 高频移动（每 tick）可能对服务器造成压力，建议根据实体数量调整频率。
