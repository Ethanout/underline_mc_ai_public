# 如何做一个简单的状态机

## 一、什么是状态机？为什么在数据包中需要它？

状态机（State Machine）是一种编程模式：实体或系统在有限个状态之间切换，每个状态有特定的行为，状态转换由事件或条件触发。

在 Minecraft 数据包开发中，状态机的典型应用场景包括：
- 自定义 Boss 战（阶段切换：待机 → 攻击 → 狂暴 → 死亡）
- 交互式 NPC（对话状态：空闲 → 对话中 → 任务完成）
- 自定义方块/物品行为（如：未激活 → 充能中 → 已激活 → 冷却中）

核心挑战：原版 Minecraft 没有内置的状态机系统，需要利用 scoreboard、storage、advancement 等机制手动实现。

## 二、方案一：基于 scoreboard 的整数状态机（最推荐）

### 原理

使用 `scoreboard` 存储一个整数作为状态值，通过 `execute if score` 判断当前状态，通过 `scoreboard players set/operation` 改变状态。这是最直接、性能最好、版本兼容性最广的方案。

### 完整实现

#### 1. 初始化 (load)

```mcfunction
# load.mcfunction
scoreboard objectives add state_machine dummy
scoreboard objectives add state_timer dummy

# 为每个需要状态机的实体初始化状态
# 这里以玩家为例，实际可以是任何实体
scoreboard players set @a state_machine 0
scoreboard players set @a state_timer 0
```

#### 2. 状态机核心逻辑 (tick)

```mcfunction
# tick.mcfunction
execute as @a at @s run function namespace:state_machine/tick
```

```mcfunction
# namespace:state_machine/tick.mcfunction
# 根据当前状态执行不同逻辑
execute if score @s state_machine matches 0 run function namespace:state_machine/state_idle
execute if score @s state_machine matches 1 run function namespace:state_machine/state_active
execute if score @s state_machine matches 2 run function namespace:state_machine/state_cooldown
```

#### 3. 各状态函数

```mcfunction
# namespace:state_machine/state_idle.mcfunction
# 空闲状态：检测条件，满足则切换到活跃状态
say 当前状态：空闲

# 示例条件：检测玩家是否按下前进键
execute if predicate namespace:is_moving run scoreboard players set @s state_machine 1
```

```mcfunction
# namespace:state_machine/state_active.mcfunction
# 活跃状态：执行动作，启动计时器
say 当前状态：活跃！

# 设置计时器（20 ticks = 1 秒）
scoreboard players set @s state_timer 100

# 切换到冷却状态
scoreboard players set @s state_machine 2
```

```mcfunction
# namespace:state_machine/state_cooldown.mcfunction
# 冷却状态：倒计时，结束后回到空闲
say 当前状态：冷却中...

# 计时器减1
scoreboard players remove @s state_timer 1

# 计时器归零时回到空闲
execute if score @s state_timer matches 0 run scoreboard players set @s state_machine 0
```

#### 4. 谓词文件（用于检测移动）

```json
# namespace:predicate/is_moving.json
{
  "condition": "minecraft:entity_properties",
  "entity": "this",
  "predicate": {
    "flags": {
      "is_moving": true
    }
  }
}
```

### 陷阱与注意事项

1. **scoreboard 名称冲突**：`state_machine` 和 `state_timer` 是全局名称，建议使用命名空间前缀如 `namespace.state` 避免冲突。
2. **实体选择器**：`@a` 只选择玩家。如果要对其他实体（如 armor_stand）使用状态机，需要用 `@e[type=minecraft:armor_stand,tag=my_npc]`。
3. **状态值范围**：scoreboard 支持 -2,147,483,648 到 2,147,483,647 的整数，足够大多数场景使用。
4. **计时器精度**：基于 tick 的计时器在服务器 TPS 下降时会变慢，如果需要精确时间，考虑使用 `schedule` 命令。

## 三、方案二：基于 advancement 的事件驱动状态机

### 原理

利用 advancement 的 `tick` 触发器和 `rewards` 功能，将状态转换逻辑绑定到 advancement 上。当满足特定条件时，advancement 自动触发并执行对应的函数。

适用版本：1.13+（advancement 系统引入）

### 完整实现

#### 1. 定义状态 advancement

```json
# namespace:advancement/state_idle.json
{
  "criteria": {
    "check_state": {
      "trigger": "minecraft:tick",
      "conditions": {
        "player": [
          {
            "condition": "minecraft:entity_scores",
            "entity": "this",
            "scores": {
              "namespace.state": 0
            }
          }
        ]
      }
    }
  },
  "rewards": {
    "function": "namespace:state_machine/state_idle"
  }
}
```

```json
# namespace:advancement/state_active.json
{
  "criteria": {
    "check_state": {
      "trigger": "minecraft:tick",
      "conditions": {
        "player": [
          {
            "condition": "minecraft:entity_scores",
            "entity": "this",
            "scores": {
              "namespace.state": 1
            }
          }
        ]
      }
    }
  },
  "rewards": {
    "function": "namespace:state_machine/state_active"
  }
}
```

```json
# namespace:advancement/state_cooldown.json
{
  "criteria": {
    "check_state": {
      "trigger": "minecraft:tick",
      "conditions": {
        "player": [
          {
            "condition": "minecraft:entity_scores",
            "entity": "this",
            "scores": {
              "namespace.state": 2
            }
          }
        ]
      }
    }
  },
  "rewards": {
    "function": "namespace:state_machine/state_cooldown"
  }
}
```

#### 2. 状态函数

```mcfunction
# namespace:state_machine/state_idle.mcfunction
say 当前状态：空闲（通过 advancement 触发）

# 检测条件，切换到活跃状态
execute if predicate namespace:is_moving run scoreboard players set @s namespace.state 1

# 撤销自身 advancement，以便下次 tick 再次触发
advancement revoke @s only namespace:state_idle
```

```mcfunction
# namespace:state_machine/state_active.mcfunction
say 当前状态：活跃！（通过 advancement 触发）

# 设置计时器
scoreboard players set @s namespace.timer 100
scoreboard players set @s namespace.state 2

advancement revoke @s only namespace:state_active
```

```mcfunction
# namespace:state_machine/state_cooldown.mcfunction
say 当前状态：冷却中...（通过 advancement 触发）

scoreboard players remove @s namespace.timer 1
execute if score @s namespace.timer matches 0 run scoreboard players set @s namespace.state 0

advancement revoke @s only namespace:state_cooldown
```

#### 3. 初始化

```mcfunction
# load.mcfunction
scoreboard objectives add namespace.state dummy
scoreboard objectives add namespace.timer dummy

# 授予所有玩家初始 advancement
advancement grant @a only namespace:state_idle
```

### 陷阱与注意事项

1. **性能开销**：每个 tick 每个玩家都会触发 advancement 检查，如果有大量玩家，性能开销比方案一高。建议只在需要事件驱动的场景使用。
2. **advancement 撤销**：必须在每个状态函数末尾撤销对应的 advancement，否则下次 tick 不会重新触发。
3. **状态切换延迟**：advancement 触发是在 tick 结束时，状态切换可能有 1 tick 的延迟。
4. **版本要求**：advancement 的 `tick` 触发器在 1.13 引入，1.16+ 支持 `entity_scores` 条件。

## 四、方案三：基于 storage 的复杂状态机（适合多属性状态）

### 原理

使用 `storage` 存储复杂的状态数据（如 JSON 对象），通过 `data modify` 和 `data get` 操作状态。适合需要存储多个属性（如血量、阶段、计时器、冷却时间等）的复杂状态机。

适用版本：1.15+（storage 引入）

### 完整实现

#### 1. 初始化

```mcfunction
# load.mcfunction
scoreboard objectives add state_owner dummy

# 初始化 storage
data modify storage namespace:state_machine states set value []
```

#### 2. 注册实体状态

```mcfunction
# namespace:state_machine/register.mcfunction
# 为当前实体注册状态
# 参数：@s 是要注册的实体
# 使用 UUID 作为唯一标识
data modify storage namespace:state_machine states append value {uuid:"",state:0,timer:0,health:100}

# 获取实体 UUID 并写入 storage
execute store result storage namespace:state_machine states[-1].uuid string 1 run data get entity @s UUID

# 记录实体与 storage 的关联
scoreboard players set @s state_owner 1
```

#### 3. 状态机核心逻辑

```mcfunction
# tick.mcfunction
execute as @a at @s run function namespace:state_machine/tick
```

```mcfunction
# namespace:state_machine/tick.mcfunction
# 获取当前实体的状态数据
execute store result score #index state_owner run data get storage namespace:state_machine states[0].state

# 根据状态执行不同逻辑
execute if score #index state_owner matches 0 run function namespace:state_machine/state_idle
execute if score #index state_owner matches 1 run function namespace:state_machine/state_active
execute if score #index state_owner matches 2 run function namespace:state_machine/state_cooldown
```

```mcfunction
# namespace:state_machine/state_idle.mcfunction
say 当前状态：空闲（storage 驱动）

# 更新 storage 中的状态
data modify storage namespace:state_machine states[0].state set value 1
```

```mcfunction
# namespace:state_machine/state_active.mcfunction
say 当前状态：活跃！（storage 驱动）

# 更新多个属性
data modify storage namespace:state_machine states[0].state set value 2
data modify storage namespace:state_machine states[0].timer set value 100
```

```mcfunction
# namespace:state_machine/state_cooldown.mcfunction
say 当前状态：冷却中...（storage 驱动）

# 计时器减1
data modify storage namespace:state_machine states[0].timer set value 0
execute store result storage namespace:state_machine states[0].timer int 1 run data get storage namespace:state_machine states[0].timer
scoreboard players remove #temp state_owner 1
execute if data storage namespace:state_machine states[0]{timer:0} run data modify storage namespace:state_machine states[0].state set value 0
```

### 陷阱与注意事项

1. **⚠️ 需验证**：`data get` 返回值的存储方式在不同版本可能有差异。1.15-1.20.4 使用 `execute store result score` 配合 `data get` 时，需要确保数据类型匹配。
2. **⚠️ 需验证**：storage 的数组索引操作（如 `states[-1]`）在 1.15 中可能不支持，建议使用 `states[0]` 并手动管理索引。
3. **性能开销**：storage 操作比 scoreboard 慢，不适合高频 tick 调用。建议只在状态切换时使用 storage，日常状态判断仍用 scoreboard。
4. **数据持久化**：storage 不会自动保存到世界文件，需要在 `save` 事件中手动保存到 scoreboard 或实体 NBT。

## 五、方案对比

| 特性 | 方案一：scoreboard | 方案二：advancement | 方案三：storage |
|------|-------------------|-------------------|----------------|
| **最低版本** | 1.13 | 1.13 | 1.15 |
| **性能开销** | 低 | 中 | 中高 |
| **状态数量限制** | 无（整数范围） | 无 | 无 |
| **复杂状态支持** | 差（仅整数） | 差（仅整数） | 好（JSON 对象） |
| **事件驱动** | 手动实现 | 自动触发 | 手动实现 |
| **调试难度** | 低 | 中 | 高 |
| **适用场景** | 大多数情况 | 需要自动触发的场景 | 需要存储复杂属性的场景 |

## 六、最佳实践建议

1. **优先使用方案一**：对于 90% 的状态机需求，scoreboard 方案足够且性能最好。
2. **混合使用**：用 scoreboard 存储状态值，用 storage 存储状态的附加属性（如血量、冷却时间等）。
3. **命名规范**：始终使用命名空间前缀，如 `namespace.state`、`namespace.timer`。
4. **状态枚举**：在文档中维护状态值与含义的映射表，如：
   - 0 = IDLE（空闲）
   - 1 = ACTIVE（活跃）
   - 2 = COOLDOWN（冷却）
   - 3 = DEAD（死亡）
