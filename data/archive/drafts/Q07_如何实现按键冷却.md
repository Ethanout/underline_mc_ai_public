# 如何实现按键冷却

## 核心挑战

在 Minecraft 数据包中实现按键冷却（Cooldown）的核心挑战在于：**原版没有内置的按键冷却系统**。玩家可以以任意频率触发按键检测逻辑（如 F 键、攻击键、使用键等），如果不加限制，会导致：
1. 性能问题：高频触发复杂函数
2. 逻辑问题：技能/功能被滥用（如连续瞬移、连续发射弹射物）

因此，我们需要利用原版机制自行构建冷却系统。

## 方案一：基于 scoreboard 的计时器冷却（最通用）

### 原理

利用 `scoreboard` 存储每个玩家的冷却剩余时间（以 tick 为单位），在 tick 函数中递减，当冷却为 0 时允许触发按键逻辑。

### 适用版本

1.13+（scoreboard 系统稳定版本）

### 完整实现

#### 1. 初始化 (Load)

`data/<namespace>/function/load.mcfunction`
```mcfunction
# 创建冷却计分板
scoreboard objectives add <namespace>.cooldown dummy
```

#### 2. 按键检测（以 F 键为例）

`data/<namespace>/function/fkey/on_press.mcfunction`
```mcfunction
# 检查冷却
scoreboard players get @s <namespace>.cooldown
execute if score @s <namespace>.cooldown matches 0 run function <namespace>:fkey/execute
```

`data/<namespace>/function/fkey/execute.mcfunction`
```mcfunction
# 设置冷却（例如 20 ticks = 1 秒）
scoreboard players set @s <namespace>.cooldown 20

# 执行实际功能
say F 键被按下！冷却 1 秒。
```

#### 3. 冷却递减 (Tick)

`data/<namespace>/function/tick.mcfunction`
```mcfunction
# 对所有有冷却的玩家递减
scoreboard players remove @a[scores={<namespace>.cooldown=1..}] <namespace>.cooldown 1
```

### 陷阱与注意事项

1. **玩家离线问题**：如果玩家在冷却期间离线，冷却时间会暂停（因为 tick 函数只对在线玩家执行）。解决方案：在玩家重新加入时重置冷却，或使用 `@a[scores=...]` 选择器确保只处理在线玩家。
2. **多按键共享冷却**：如果多个按键共享同一个 scoreboard，它们会互相影响。解决方案：为每个按键创建独立的 scoreboard。
3. **精度限制**：最小冷却单位是 1 tick（1/20 秒），无法实现更精细的冷却。
4. **性能开销**：较低。每个 tick 执行一次 `scoreboard players remove` 操作，复杂度 O(n)，n 为在线玩家数。

## 方案二：基于 advancement 的触发式冷却（精确控制）

### 原理

利用 `advancement` 的 `tick` 触发条件，结合 `scoreboard` 实现精确的冷却计时。当按键触发时，授予玩家一个临时 advancement，该 advancement 的 `tick` 条件会在指定 tick 数后触发，执行冷却结束逻辑。

### 适用版本

1.13+（advancement 系统稳定版本）

### 完整实现

#### 1. 创建冷却 advancement

`data/<namespace>/advancement/cooldown/fkey.json`
```json
{
  "criteria": {
    "cooldown_end": {
      "trigger": "minecraft:tick",
      "conditions": {
        "player": [
          {
            "condition": "minecraft:entity_scores",
            "entity": "this",
            "scores": {
              "<namespace>.fkey_cooldown": 0
            }
          }
        ]
      }
    }
  },
  "rewards": {
    "function": "<namespace>:cooldown/fkey_end"
  }
}
```

#### 2. 冷却结束函数

`data/<namespace>/function/cooldown/fkey_end.mcfunction`
```mcfunction
# 冷却结束，移除 advancement 以便下次触发
advancement revoke @s only <namespace>:cooldown/fkey

# 执行冷却结束逻辑（可选）
say F 键冷却已结束！
```

#### 3. 按键检测（修改版）

`data/<namespace>/function/fkey/on_press.mcfunction`
```mcfunction
# 检查是否在冷却中（通过 advancement 是否存在）
execute unless advancement @s <namespace>:cooldown/fkey run function <namespace>:fkey/execute
```

`data/<namespace>/function/fkey/execute.mcfunction`
```mcfunction
# 设置冷却（例如 20 ticks）
scoreboard players set @s <namespace>.fkey_cooldown 20

# 授予 advancement，开始冷却计时
advancement grant @s only <namespace>:cooldown/fkey

# 执行实际功能
say F 键被按下！冷却 1 秒。
```

#### 4. 冷却递减 (Tick)

`data/<namespace>/function/tick.mcfunction`
```mcfunction
# 递减冷却计分板
scoreboard players remove @a[scores={<namespace>.fkey_cooldown=1..}] <namespace>.fkey_cooldown 1
```

### 陷阱与注意事项

1. **advancement 触发延迟**：`tick` 触发条件在 tick 结束时检查，因此冷却结束可能有 1 tick 的延迟。
2. **advancement 管理**：需要确保 advancement 在冷却结束后被正确撤销，否则下次按键检测会失效。
3. **多玩家并发**：每个玩家独立拥有 advancement 实例，不会互相干扰。
4. **性能开销**：中等。每个 tick 需要检查 advancement 条件，但只对拥有 advancement 的玩家执行。
5. **⚠️ 需验证**：`tick` 触发条件中的 `entity_scores` 条件是否支持动态计分板名称？上述示例假设计分板名称是固定的。

## 方案三：基于 NBT 存储的冷却（1.20.5+ 推荐）

### 原理

利用 1.20.5 引入的 `item.components."minecraft:custom_data"` 或 `storage` 中的 NBT 数据存储冷却时间。通过 `data` 命令操作 NBT，实现更灵活的冷却管理。

### 适用版本

1.20.5+（NBT 组件系统）

### 完整实现

#### 1. 初始化 (Load)

`data/<namespace>/function/load.mcfunction`
```mcfunction
# 创建全局 storage 用于存储冷却数据
data modify storage <namespace>:cooldown cooldowns set value {}
```

#### 2. 按键检测（以 F 键为例）

`data/<namespace>/function/fkey/on_press.mcfunction`
```mcfunction
# 检查冷却
execute store result score @s <namespace>.temp run data get storage <namespace>:cooldown cooldowns[<@s>]
execute if score @s <namespace>.temp matches 0 run function <namespace>:fkey/execute
```

`data/<namespace>/function/fkey/execute.mcfunction`
```mcfunction
# 设置冷却（例如 20 ticks）
data modify storage <namespace>:cooldown cooldowns[<@s>] set value 20

# 执行实际功能
say F 键被按下！冷却 1 秒。
```

#### 3. 冷却递减 (Tick)

`data/<namespace>/function/tick.mcfunction`
```mcfunction
# 递减所有冷却值
data modify storage <namespace>:cooldown cooldowns[] set value 0
# 注意：上述命令不正确，需要逐个处理

# 正确做法：遍历所有玩家
execute as @a run function <namespace>:cooldown/tick_player
```

`data/<namespace>/function/cooldown/tick_player.mcfunction`
```mcfunction
# 获取当前冷却值
execute store result score @s <namespace>.temp run data get storage <namespace>:cooldown cooldowns[<@s>]

# 如果冷却大于 0，递减
execute if score @s <namespace>.temp matches 1.. run data modify storage <namespace>:cooldown cooldowns[<@s>] set value 0
# 注意：上述命令无法直接递减，需要更复杂的逻辑
```

### 陷阱与注意事项

1. **NBT 路径复杂性**：使用 UUID 作为键名时，NBT 路径需要正确处理特殊字符（如 `-`）。
2. **性能开销**：较高。每次操作都需要解析 NBT 路径，且 `data get` 和 `data modify` 操作比 scoreboard 操作慢。
3. **数据持久化**：`storage` 数据在服务器重启后会丢失，如需持久化需使用 `data modify entity` 或 `data modify block`。
4. **⚠️ 需验证**：上述示例中的 `cooldowns[<@s>]` 语法是否正确？实际上，NBT 数组索引必须是整数，不能使用 UUID 字符串。正确做法是使用 NBT 复合标签（如 `{uuid: "xxx", cooldown: 20}`）并遍历查找。

## 方案四：基于物品组件的冷却（1.20.5+ 高级用法）

### 原理

利用 1.20.5 引入的物品组件系统，在物品的 `custom_data` 中存储冷却信息。当玩家持有该物品时，通过 `item` 命令读取冷却数据。

### 适用版本

1.20.5+

### 完整实现

#### 1. 按键检测（以使用物品为例）

`data/<namespace>/function/use_item/on_use.mcfunction`
```mcfunction
# 检查主手物品的冷却
execute store result score @s <namespace>.temp run data get entity @s weapon.mainhand.components."minecraft:custom_data".<namespace>.cooldown 1

# 如果冷却为 0 或不存在，允许使用
execute if score @s <namespace>.temp matches 0 run function <namespace>:use_item/execute
```

`data/<namespace>/function/use_item/execute.mcfunction`
```mcfunction
# 设置冷却（例如 20 ticks）
data modify entity @s weapon.mainhand.components."minecraft:custom_data".<namespace>.cooldown set value 20

# 执行实际功能
say 物品被使用！冷却 1 秒。
```

#### 2. 冷却递减 (Tick)

`data/<namespace>/function/tick.mcfunction`
```mcfunction
# 遍历所有玩家，递减主手物品冷却
execute as @a run function <namespace>:cooldown/tick_player
```

`data/<namespace>/function/cooldown/tick_player.mcfunction`
```mcfunction
# 获取当前冷却值
execute store result score @s <namespace>.temp run data get entity @s weapon.mainhand.components."minecraft:custom_data".<namespace>.cooldown 1

# 如果冷却大于 0，递减
execute if score @s <namespace>.temp matches 1.. run data modify entity @s weapon.mainhand.components."minecraft:custom_data".<namespace>.cooldown set value 0
# 注意：无法直接递减，需要更复杂的逻辑
```

### 陷阱与注意事项

1. **物品依赖**：冷却绑定在物品上，如果玩家切换物品，冷却会丢失。
2. **物品堆叠问题**：如果物品堆叠，修改一个物品的 `custom_data` 会导致整个堆叠的物品数据不一致。
3. **性能开销**：高。每个 tick 需要读取和修改每个玩家的物品 NBT。
4. **⚠️ 需验证**：`data get entity @s weapon.mainhand.components."minecraft:custom_data".<namespace>.cooldown` 语法是否正确？1.20.5 后物品组件路径是否支持直接访问？

## 方案对比

| 方案 | 版本要求 | 性能开销 | 精度 | 复杂度 | 适用场景 |
|------|---------|---------|------|-------|---------|
| scoreboard 计时器 | 1.13+ | 低 | 1 tick | 低 | 通用，简单冷却需求 |
| advancement 触发式 | 1.13+ | 中 | 1 tick | 中 | 需要精确控制冷却结束事件 |
| NBT storage 存储 | 1.20.5+ | 高 | 1 tick | 高 | 需要复杂冷却逻辑（如多阶段冷却） |
| 物品组件冷却 | 1.20.5+ | 高 | 1 tick | 高 | 物品绑定冷却，如武器技能 |

## 推荐方案

对于大多数场景，**方案一（scoreboard 计时器）** 是最推荐的选择，原因如下：
- 版本兼容性好（1.13+）
- 性能开销最低
- 实现简单，易于维护
- 支持多按键独立冷却

如果需要精确控制冷却结束事件（如播放音效、显示提示），可以考虑**方案二（advancement 触发式）**。
