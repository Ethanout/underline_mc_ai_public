# 如何处理失败和重试

在 Minecraft 数据包开发中，“失败和重试”通常指两种情况：
1. **命令执行失败**：如 `execute` 条件不满足、`item` 操作目标不存在、`function` 被 `return fail` 中断
2. **逻辑流程重试**：如随机数生成未达到期望值、资源不足时等待、异步操作完成后重试

原版数据包没有 try-catch 或 while 循环，但可以通过 `return`、`schedule`、`advancement` 和 `scoreboard` 组合实现可靠的失败处理和重试机制。

---

## 方案一：`return fail` + 条件分支（最基础）

**适用版本**：1.20.2+（`return fail` 引入于 1.20.2）
**原理**：`return fail` 会立即终止当前函数并向上层返回失败状态。调用方可以通过 `execute if function <func>` 检测被调用函数是否成功返回（即没有执行 `return fail`）。

### 完整示例：尝试给玩家一个物品，背包满则重试

**目录结构**：
```
data/
  example/
    function/
      try_give_item.mcfunction
      give_item.mcfunction
      retry_give.mcfunction
    advancement/
      inventory_changed_trigger.json
```

#### 1. 被调用函数：尝试给物品，失败则 `return fail`

`data/example/function/give_item.mcfunction`
```mcfunction
# 尝试给玩家一个钻石
give @s diamond 1

# 检查是否成功（背包未满时 give 成功，满时 give 失败但不会报错）
# 通过检测物品栏是否真的增加了钻石来判断
execute if items entity @s inventory.* diamond run return pass
# 如果没拿到钻石，返回失败
return fail
```

**陷阱**：
- `give` 命令在背包满时**不会报错**，只是物品掉在地上。所以不能靠 `execute` 的 success count 判断，必须检查物品栏。
- 如果玩家在掉落物范围内，`give` 失败时物品会掉在地上，此时 `items` 检测可能仍然成功（因为掉在地上的物品不属于玩家）。需要额外检测掉落物实体。

#### 2. 调用方：根据返回值决定是否重试

`data/example/function/try_give_item.mcfunction`
```mcfunction
# 尝试给物品
execute as @a run function example:give_item

# 如果 give_item 返回 fail，则安排重试
execute as @a if function example:give_item run say 成功给了物品
execute as @a unless function example:give_item run schedule function example:retry_give 1s
```

**陷阱**：
- `execute if function <func>` 会**执行两次**函数（一次用于检测，一次用于实际执行）。上面的写法会导致 `give_item` 被调用两次，第一次给物品，第二次又给一次。正确做法是：

```mcfunction
# 正确写法：只执行一次，用 scoreboard 记录结果
scoreboard players set @s example.give_result 0
execute as @a run function example:give_item_with_result

# 根据结果决定是否重试
execute as @a[scores={example.give_result=0}] run schedule function example:retry_give 1s
```

`data/example/function/give_item_with_result.mcfunction`
```mcfunction
give @s diamond 1
execute if items entity @s inventory.* diamond run scoreboard players set @s example.give_result 1
```

## 方案二：`schedule` 延迟重试（推荐）

**适用版本**：1.14+
**原理**：当操作失败时，使用 `schedule` 在若干 tick 后重新执行尝试函数。配合 `scoreboard` 记录重试次数，防止无限循环。

### 完整示例：随机数生成直到满足条件

假设我们需要生成一个 1-100 的随机数，直到它大于 80 才继续。

`data/example/function/random_retry.mcfunction`
```mcfunction
# 生成随机数 1-100
scoreboard players random @s example.random 1 100

# 检查是否满足条件
execute if score @s example.random matches 81.. run return pass
# 不满足则重试（延迟 1 tick 避免死循环）
schedule function example:random_retry 1t
```

**陷阱**：
- 如果不加延迟直接递归调用，会在同一 tick 内无限递归，导致游戏卡死或崩溃。
- `schedule` 的最小单位是 1 tick（50ms），不能在同一 tick 内重试。
- 如果玩家离线，`schedule` 仍然会执行，但 `@s` 会失效。需要检查玩家是否在线：

```mcfunction
execute if entity @s run schedule function example:random_retry 1t
```

### 带重试次数限制的版本

`data/example/function/random_retry_limited.mcfunction`
```mcfunction
# 增加重试计数
scoreboard players add @s example.retry_count 1

# 超过最大重试次数则放弃
execute if score @s example.retry_count matches 10.. run return fail

# 生成随机数
scoreboard players random @s example.random 1 100

# 检查条件
execute if score @s example.random matches 81.. run scoreboard players set @s example.retry_count 0
execute if score @s example.random matches 81.. run return pass

# 延迟重试
schedule function example:random_retry_limited 1t
```

## 方案三：`advancement` 事件驱动重试（高级）

**适用版本**：1.13+
**原理**：利用 `advancement` 的 `inventory_changed` 或 `tick` 触发器，在特定事件发生时自动重试。适合需要等待外部条件满足的场景（如等待玩家背包有空位）。

### 完整示例：等待背包有空位后自动重试

#### 1. 创建触发进度

`data/example/advancement/retry_on_inventory_change.json`
```json
{
  "criteria": {
    "inventory_changed": {
      "trigger": "minecraft:inventory_changed"
    }
  },
  "rewards": {
    "function": "example:retry_handler"
  }
}
```

#### 2. 重试处理函数

`data/example/function/retry_handler.mcfunction`
```mcfunction
# 撤销进度，使其可以再次触发
advancement revoke @s only example:retry_on_inventory_change

# 尝试执行之前失败的操作
function example:try_give_item

# 如果仍然失败，进度会在下次物品栏变化时再次触发
# 如果成功，不需要额外操作
```

#### 3. 初始触发

`data/example/function/start_retry_chain.mcfunction`
```mcfunction
# 给玩家授予进度，触发第一次重试
advancement grant @s only example:retry_on_inventory_change
```

**陷阱**：
- `inventory_changed` 触发器在**任何**物品栏变化时都会触发，包括玩家自己移动物品。这可能导致频繁触发。
- 必须及时 `revoke` 进度，否则进度只会触发一次（默认情况下进度触发后不会再次触发）。
- 如果多个玩家同时使用此机制，需要确保进度是每个玩家独立的（`@s` 上下文）。

## 方案四：`execute store` 捕获命令结果（1.20.5+）

**适用版本**：1.20.5+（`execute store` 增强）
**原理**：使用 `execute store success score` 或 `execute store result score` 捕获命令的执行结果，根据结果决定是否重试。

### 完整示例：尝试放置方块，失败则重试

`data/example/function/place_block.mcfunction`
```mcfunction
# 尝试在玩家脚下放置石头
execute store success score @s example.place_success run setblock ~ ~-1 ~ stone

# 如果放置失败（方块位置被阻挡或超出世界边界），重试
execute if score @s example.place_success matches 0 run schedule function example:place_block 1t
```

**陷阱**：
- `setblock` 在目标位置已有相同方块时返回 success（1），在目标位置被阻挡时返回 0。但 `setblock` 会直接替换方块，不会检查是否可放置。
- 更可靠的检测是使用 `execute if block ~ ~-1 ~ air` 先检查是否为空。

## 方案对比

| 方案 | 最低版本 | 性能开销 | 适用场景 | 优点 | 缺点 |
|------|---------|---------|---------|------|------|
| `return fail` + 条件分支 | 1.20.2 | 低 | 简单的一次性失败检测 | 实现简单，无延迟 | 不能处理需要等待的场景 |
| `schedule` 延迟重试 | 1.14 | 中 | 需要等待或限制重试次数 | 可控延迟，可限制次数 | 最小延迟 1 tick |
| `advancement` 事件驱动 | 1.13 | 中高 | 等待外部条件（如背包变化） | 响应及时，无需轮询 | 实现复杂，可能误触发 |
| `execute store` 捕获结果 | 1.20.5 | 低 | 需要精确知道命令是否成功 | 精确捕获 success/result | 版本要求高 |

## 陷阱总结

1. **无限递归**：函数直接调用自己（无 `schedule`）会导致同一 tick 内无限递归，游戏崩溃。必须使用 `schedule` 或 `return` 中断。
2. **`execute if function` 双重执行**：`execute if function <func>` 会执行两次函数，一次用于检测，一次用于实际执行。应避免这种写法，改用 scoreboard 记录结果。
3. **玩家离线**：`schedule` 在玩家离线后仍然会执行，此时 `@s` 可能指向不存在的玩家。应使用 `execute if entity @s` 检查。
4. **进度触发一次**：`advancement` 默认只触发一次，必须 `revoke` 后才能再次触发。
5. **`give` 失败不报错**：背包满时 `give` 不会报错，物品会掉在地上。必须通过 `items` 检测物品栏来确认是否成功。
