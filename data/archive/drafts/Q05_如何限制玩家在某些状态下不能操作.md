# 如何限制玩家在某些状态下不能操作

## 核心挑战

在 Minecraft 原版数据包开发中，"限制玩家操作"面临两个核心挑战：
1. **原版没有通用的"操作拦截"API**——你不能像插件那样直接取消事件
2. **不同操作有不同的触发机制**——移动、攻击、使用物品、打开界面等各有各的拦截方式
3. **玩家可以绕过部分限制**——例如通过快捷键、宏、模组等方式

## 方案一：效果（Effect）限制法——最推荐

### 原理

利用原版效果对玩家行为的天然限制：
- `minecraft:mining_fatigue`（挖掘疲劳）：大幅降低挖掘速度（每级-20%，5级时几乎无法挖掘）
- `minecraft:weakness`（虚弱）：降低近战伤害（每级-4点伤害）
- `minecraft:slowness`（缓慢）：降低移动速度（每级-15%）
- `minecraft:jump_boost`（跳跃提升）的负效果：降低跳跃能力（通过 `effect give` 无法直接给负值，需用 `attribute` 修改）
- `minecraft:blindness`（失明）：限制视野，间接阻止远距离交互
- `minecraft:instant_damage`（瞬间伤害）：持续造成伤害，迫使玩家无法专注操作

### 完整代码

#### 1. 给玩家施加限制效果

`<namespace>/function/restrict/apply.mcfunction`
```mcfunction
# 施加挖掘疲劳（5级，几乎无法挖掘）
effect give @s minecraft:mining_fatigue 1000000 4 true

# 施加虚弱（255级，近战伤害归零）
effect give @s minecraft:weakness 1000000 254 true

# 施加缓慢（4级，移动速度极慢）
effect give @s minecraft:slowness 1000000 3 true

# 施加失明（限制视野）
effect give @s minecraft:blindness 1000000 0 true

# 施加反胃（干扰操作）
effect give @s minecraft:nausea 1000000 0 true
```

#### 2. 移除限制效果

`<namespace>/function/restrict/remove.mcfunction`
```mcfunction
effect clear @s minecraft:mining_fatigue
effect clear @s minecraft:weakness
effect clear @s minecraft:slowness
effect clear @s minecraft:blindness
effect clear @s minecraft:nausea
```

#### 3. 在 tick 中持续应用（防止玩家喝牛奶解除）

`<namespace>/function/restrict/tick.mcfunction`
```mcfunction
# 每 20 tick 重新施加一次，防止牛奶解除
execute as @a[predicate=<namespace>:restricted] run function <namespace>:restrict/apply
```

### 陷阱与注意事项

1. **牛奶可以解除效果**：玩家喝牛奶会清除所有效果，必须通过 tick 函数重新施加
2. **不死图腾**：如果玩家持有不死图腾，`instant_damage` 效果会被抵消，且会触发图腾效果
3. **创造模式玩家**：创造模式下挖掘速度不受挖掘疲劳影响，需要额外处理
4. **跳跃限制**：原版无法直接给负值跳跃提升效果，需通过 `attribute` 修改 `minecraft:generic.jump_strength` 属性
5. **无法阻止物品使用**：效果无法阻止玩家吃食物、投掷药水、使用工具等操作

## 方案二：谓词（Predicate）+ 进度（Advancement）拦截法

### 原理

利用进度系统监听特定操作，然后通过 `revoke` 和 `grant` 机制实现"操作后立即撤销"的效果。核心思路：
1. 创建一个进度，其触发条件为"玩家执行了被禁止的操作"
2. 当进度触发时，执行撤销函数（如移除物品、传送回原位等）
3. 立即撤销该进度，使其可以再次触发

### 完整代码

#### 1. 禁止玩家使用特定物品

`<namespace>/advancement/restrict/use_item.json`
```json
{
  "criteria": {
    "used_forbidden_item": {
      "trigger": "minecraft:using_item",
      "conditions": {
        "item": {
          "items": [
            "minecraft:ender_pearl",
            "minecraft:chorus_fruit"
          ]
        }
      }
    }
  },
  "rewards": {
    "function": "<namespace>:restrict/on_use_forbidden_item"
  }
}
```

`<namespace>/function/restrict/on_use_forbidden_item.mcfunction`
```mcfunction
# 移除玩家正在使用的物品
clear @s minecraft:ender_pearl 1
clear @s minecraft:chorus_fruit 1

# 发送提示消息
tellraw @s {"text":"你不能在限制状态下使用这个物品！","color":"red"}

# 撤销进度，使其可以再次触发
advancement revoke @s only <namespace>:restrict/use_item
```

#### 2. 禁止玩家攻击特定实体

`<namespace>/advancement/restrict/attack_entity.json`
```json
{
  "criteria": {
    "attacked_forbidden": {
      "trigger": "minecraft:player_hurt_entity",
      "conditions": {
        "entity": {
          "type": "minecraft:villager"
        }
      }
    }
  },
  "rewards": {
    "function": "<namespace>:restrict/on_attack_forbidden"
  }
}
```

`<namespace>/function/restrict/on_attack_forbidden.mcfunction`
```mcfunction
# 将玩家传送回原位（需要预先存储位置）
# 假设在 storage 中存储了玩家的限制前位置
execute at @s run tp @s ~ ~ ~

# 发送提示
tellraw @s {"text":"你不能攻击村民！","color":"red"}

# 撤销进度
advancement revoke @s only <namespace>:restrict/attack_entity
```

#### 3. 禁止玩家移动

`<namespace>/advancement/restrict/move.json`
```json
{
  "criteria": {
    "moved": {
      "trigger": "minecraft:location",
      "conditions": {
        "player": {
          "location": {
            "position": {
              "x": {
                "min": -1,
                "max": 1
              },
              "y": {
                "min": -1,
                "max": 1
              },
              "z": {
                "min": -1,
                "max": 1
              }
            }
          }
        }
      }
    }
  },
  "rewards": {
    "function": "<namespace>:restrict/on_move"
  }
}
```

⚠️ **需验证**：`location` trigger 的 `position` 条件是否支持相对坐标？实际上 `location` trigger 使用的是绝对坐标，无法直接检测"玩家是否离开了某个位置"。更可行的方案是使用 `execute` 命令在 tick 中检测。

### 陷阱与注意事项

1. **进度触发有延迟**：进度触发不是即时的，玩家可能在触发前完成操作
2. **无法拦截所有操作**：`using_item` trigger 只能检测物品使用开始，无法检测使用完成后的效果
3. **性能开销**：高频触发的进度（如 `location`）会带来性能压力
4. **创造模式绕过**：创造模式下部分操作（如无限物品）无法通过 `clear` 命令有效拦截
5. **多玩家并发问题**：进度是全局的，多个玩家同时触发可能导致进度状态混乱

## 方案三：命令循环检测 + 即时修正法

### 原理

在 tick 函数中持续检测玩家状态，当发现玩家处于"被限制"状态时，立即执行修正命令。这种方法最直接，但性能开销也最大。

### 完整代码

#### 1. 限制玩家移动范围

`<namespace>/function/restrict/move_limit.mcfunction`
```mcfunction
# 检测玩家是否离开了允许区域（以原点为中心，半径10格）
execute as @a[predicate=<namespace>:restricted] at @s if entity @s[distance=..10] run function <namespace>:restrict/pull_back

# 检测玩家是否在限制状态下尝试使用物品
execute as @a[predicate=<namespace>:restricted] at @s if entity @s[nbt={SelectedItem:{id:"minecraft:ender_pearl"}}] run clear @s minecraft:ender_pearl 1
```

`<namespace>/function/restrict/pull_back.mcfunction`
```mcfunction
# 将玩家传送回原点
tp @s 0 64 0

# 发送提示
tellraw @s {"text":"你不能离开这个区域！","color":"red"}
```

#### 2. 限制玩家攻击

`<namespace>/function/restrict/attack_limit.mcfunction`
```mcfunction
# 检测玩家是否在限制状态下攻击了实体
# 通过检测玩家手持武器且最近攻击时间在1 tick内
execute as @a[predicate=<namespace>:restricted] at @s if entity @s[nbt={AttackTime:10s}] run function <namespace>:restrict/on_attack
```

⚠️ **需验证**：`AttackTime` NBT 路径是否正确？在 1.20.5+ 中，玩家 NBT 中的攻击冷却时间可能已改为 `attackStrengthTicker` 或其他字段。

`<namespace>/function/restrict/on_attack.mcfunction`
```mcfunction
# 移除玩家武器
clear @s #minecraft:swords 1
clear @s #minecraft:axes 1

# 发送提示
tellraw @s {"text":"你不能在限制状态下攻击！","color":"red"}
```

### 陷阱与注意事项

1. **性能开销高**：每 tick 对所有玩家进行 NBT 检测，性能开销较大
2. **NBT 路径可能变化**：不同版本间玩家 NBT 结构可能变化，需要持续维护
3. **无法拦截瞬间操作**：命令执行有延迟，玩家可能在命令执行前完成操作
4. **选择器限制**：`nbt=` 选择器参数不能用于高频检测（性能问题），应使用 `predicate` 替代

## 方案四：记分板（Scoreboard）+ 条件执行法

### 原理

利用记分板记录玩家的"限制状态"，然后在所有可能触发操作的命令前添加条件判断。这种方法不是"拦截"操作，而是"让操作命令在限制状态下不执行"。

### 完整代码

#### 1. 设置限制状态记分板

`<namespace>/function/restrict/init.mcfunction`
```mcfunction
# 创建记分板
scoreboard objectives add <namespace>.restricted dummy
scoreboard objectives add <namespace>.restrict_type dummy

# 设置玩家限制状态
scoreboard players set @a <namespace>.restricted 0
```

#### 2. 在操作命令前添加条件判断

假设你有一个让玩家传送的命令：

`<namespace>/function/teleport/execute.mcfunction`
```mcfunction
# 只有在非限制状态下才执行传送
execute if score @s <namespace>.restricted matches 0 run function <namespace>:teleport/do_teleport
```

假设你有一个给予玩家物品的命令：

`<namespace>/function/give_item/execute.mcfunction`
```mcfunction
# 只有在非限制状态下才给予物品
execute if score @s <namespace>.restricted matches 0 run function <namespace>:give_item/do_give
```

#### 3. 设置和解除限制

`<namespace>/function/restrict/set.mcfunction`
```mcfunction
# 设置限制状态
scoreboard players set @s <namespace>.restricted 1
scoreboard players set @s <namespace>.restrict_type 1
```

`<namespace>/function/restrict/clear.mcfunction`
```mcfunction
# 解除限制状态
scoreboard players set @s <namespace>.restricted 0
scoreboard players set @s <namespace>.restrict_type 0
```

### 陷阱与注意事项

1. **需要修改所有相关命令**：这种方法要求你在所有可能被限制的操作命令前都添加条件判断，维护成本高
2. **无法拦截外部命令**：如果其他数据包或命令方块直接执行操作，无法被拦截
3. **玩家可以绕过**：如果玩家通过其他方式（如模组、直接修改 NBT）执行操作，无法被限制
4. **记分板值可能被篡改**：玩家可以通过命令修改自己的记分板值（如果他们有权限）

## 方案对比

| 方案 | 版本要求 | 性能开销 | 适用场景 | 优点 | 缺点 |
|------|---------|---------|---------|------|------|
| 效果限制法 | 所有版本 | 低 | 限制移动、挖掘、攻击 | 原生支持，性能好 | 无法限制物品使用，可被牛奶解除 |
| 进度拦截法 | 1.13+ | 中 | 拦截特定操作（使用物品、攻击实体） | 可以精确拦截 | 有延迟，无法拦截所有操作 |
| 命令循环检测法 | 所有版本 | 高 | 需要即时修正的场景 | 即时响应 | 性能开销大，NBT 路径可能变化 |
| 记分板条件法 | 1.13+ | 低 | 控制自己的数据包命令执行 | 性能好，可控性强 | 需要修改所有相关命令，无法拦截外部操作 |

## 综合推荐

1. **首选方案**：效果限制法 + 记分板条件法组合使用
   - 用效果限制法处理移动、挖掘、攻击等原生支持的操作
   - 用记分板条件法控制自己的数据包命令执行
   - 性能开销低，实现简单

2. **次选方案**：进度拦截法
   - 当需要精确拦截特定物品使用时
   - 注意处理延迟问题

3. **不推荐**：命令循环检测法
   - 除非你确实需要即时修正且无法使用其他方案
   - 注意性能优化（使用 predicate 替代 nbt= 选择器）
