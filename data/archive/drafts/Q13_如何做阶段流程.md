# 如何做阶段流程

## 一、问题概述

在 Minecraft 数据包开发中，“阶段流程”指的是让游戏进程按照设计好的顺序推进，例如：玩家完成 A 任务后才能进入 B 区域，击败 BOSS 后才能解锁 C 奖励。核心挑战在于：

1. **状态持久化**：玩家退出重进后阶段不能丢失
2. **顺序控制**：必须严格按设计顺序推进，不能跳过
3. **触发时机**：在正确的时机（如击杀、进入区域、合成物品）推进阶段
4. **版本兼容**：不同 Minecraft 版本提供的机制不同

## 二、方案一：基于进度（Advancement）的阶段流程

**适用版本**：1.13+（所有现代版本）
**推荐程度**：⭐⭐⭐⭐⭐（最推荐，原版原生支持）

### 原理

利用 Minecraft 的进度系统作为阶段容器。每个阶段对应一个进度，进度之间通过 `requirements` 和 `parent` 字段形成依赖链。玩家完成某个进度时，通过 `rewards.function` 触发阶段推进逻辑。

### 完整实现

#### 目录结构
```
data/
  <namespace>/
    advancement/
      stages/
        stage1_start.json
        stage1_complete.json
        stage2_start.json
        stage2_complete.json
    function/
      stages/
        on_stage1_complete.mcfunction
        on_stage2_complete.mcfunction
        check_stage.mcfunction
```

#### 2. 阶段推进函数

`data/<namespace>/function/stages/on_stage1_start.mcfunction`
```mcfunction

# 设置记分板标记

```

# 解锁第二阶段进度（自动触发，因为parent关系）
# 注意：进度系统会自动检测parent是否完成，无需手动操作

# 奖励
give @s minecraft:iron_ingot 3
tellraw @s {"text":"第一阶段完成！现在可以进入地下城了。","color":"gold"}
```

`data/<namespace>/function/stages/on_stage2_start.mcfunction`

```

#### 3. 阶段检查函数（用于命令方块或其他逻辑）

`data/<namespace>/function/stages/check_stage.mcfunction`
```mcfunction
# 检查玩家是否处于特定阶段
# 用法：execute as @a at @s run function <namespace>:stages/check_stage

# 检查是否完成stage1_start（即是否已进入第一阶段）
execute if entity @s[advancements={<namespace>:stages/stage1_start=true}] run say 我已进入第一阶段

# 检查是否完成stage1_complete
execute if entity @s[advancements={<namespace>:stages/stage1_complete=true}] run say 我已完成第一阶段

# 检查是否未完成stage1_start（即尚未开始）
execute unless entity @s[advancements={<namespace>:stages/stage1_start=true}] run say 我还没开始
```

### 陷阱与注意事项

1. **进度自动授予问题**：如果玩家通过作弊或其他方式直接获得了某个进度，阶段会被跳过。解决方案：在关键阶段使用 `revoke` 命令在 load 时重置进度。
   ```mcfunction
   advancement revoke @a only <namespace>:stages/stage1_start
   ```

2. **进度显示**：如果 `display` 字段不为 `hidden: true`，玩家会在进度界面看到阶段信息，可能破坏沉浸感。

3. **parent 依赖**：进度系统要求子进度必须在父进度完成后才能触发。但注意：如果父进度被 revoke，子进度仍然保持完成状态（进度系统不会级联撤销）。

4. **性能**：进度检测是原生的，性能开销极低。但 `rewards.function` 中的逻辑应尽量轻量。

## 三、方案二：基于记分板（Scoreboard）的阶段流程

**适用版本**：1.13+（所有现代版本）
**推荐程度**：⭐⭐⭐⭐（灵活但需要手动管理）

### 原理

使用记分板存储阶段数值，通过 tick 函数或事件触发函数来检查条件并推进阶段。完全由数据包开发者控制逻辑流程。

### 完整实现

#### 1. 初始化记分板

`data/<namespace>/function/load.mcfunction`
```mcfunction
scoreboard objectives add stage_progress dummy 阶段进度
scoreboard objectives add stage_trigger dummy 阶段触发标记
```

#### 2. 阶段推进逻辑

`data/<namespace>/function/stages/tick.mcfunction`
```mcfunction
# 每 tick 执行，检查所有玩家的阶段状态
execute as @a run function <namespace>:stages/check_progress
```

`data/<namespace>/function/stages/check_progress.mcfunction`
```mcfunction
# 获取当前阶段
scoreboard players operation @s stage_trigger = @s stage_progress

# 阶段0：未开始 → 自动进入阶段1
execute if score @s stage_trigger matches 0 run function <namespace>:stages/enter_stage1

# 阶段1：等待击杀Boss
execute if score @s stage_trigger matches 1 run function <namespace>:stages/stage1_tick

# 阶段2：等待进入区域
execute if score @s stage_trigger matches 2 run function <namespace>:stages/stage2_tick

# 阶段3：最终阶段
execute if score @s stage_trigger matches 3 run function <namespace>:stages/stage3_tick
```

`data/<namespace>/function/stages/enter_stage1.mcfunction`
```mcfunction
# 进入阶段1
scoreboard players set @s stage_progress 1
scoreboard players set @s stage_trigger 1

# 给予初始物品
give @s minecraft:wooden_sword
give @s minecraft:bread 5

tellraw @s {"text":"第一阶段开始！击败僵尸Boss以继续。","color":"green"}
```

`data/<namespace>/function/stages/stage1_tick.mcfunction`
```mcfunction
# 阶段1的tick逻辑：检测是否击杀Boss
# 使用谓词检测附近是否有Boss实体
execute if entity @e[type=minecraft:zombie,tag=stage1_boss,distance=..10] run say Boss还在附近

# 检测Boss是否被击杀（通过记分板标记）
execute if entity @e[type=minecraft:zombie,tag=stage1_boss_dead] run function <namespace>:stages/complete_stage1
```

`data/<namespace>/function/stages/complete_stage1.mcfunction`
```mcfunction
# 完成阶段1
scoreboard players set @s stage_progress 2
scoreboard players set @s stage_trigger 2

# 清除Boss死亡标记
scoreboard players reset @e[type=minecraft:zombie,tag=stage1_boss_dead] stage_progress

# 奖励
give @s minecraft:iron_ingot 3
tellraw @s {"text":"第一阶段完成！现在可以进入地下城了。","color":"gold"}
```

#### 3. Boss死亡检测（在Boss实体上）

`data/<namespace>/function/boss/on_death.mcfunction`
```mcfunction
# 当Boss死亡时，为所有在范围内的玩家推进阶段
execute as @a[distance=..20] run scoreboard players set @s stage_trigger 2
```

### 陷阱与注意事项

1. **tick 函数性能**：如果玩家数量多，每 tick 执行复杂逻辑可能导致性能问题。建议使用 `schedule` 函数降低频率。
   ```mcfunction
   schedule function <namespace>:stages/tick 1s replace
   ```

2. **记分板持久化**：记分板值会自动保存，但注意：如果使用 `dummy` 类型，只能通过命令修改。

3. **条件检测**：使用 `execute if entity` 检测实体时，如果实体被移除（如死亡），检测会失败。需要确保在正确的时机触发。

4. **玩家重进**：新玩家加入时，记分板初始值为0，需要处理初始状态。

## 四、方案三：基于 Storage 和宏（Macro）的阶段流程

**适用版本**：1.20.2+（宏功能引入）
**推荐程度**：⭐⭐⭐（适合复杂状态管理）

### 原理

使用 `storage` 存储阶段数据，通过宏函数动态生成命令。适合需要存储大量玩家状态或复杂阶段数据的场景。

### 完整实现

#### 1. 初始化 Storage

`data/<namespace>/function/load.mcfunction`
```mcfunction
# 初始化阶段存储
data modify storage <namespace>:stages players set value []
```

#### 2. 玩家加入处理

`data/<namespace>/function/stages/on_join.mcfunction`
```mcfunction
# 玩家加入时，检查是否已有阶段数据
execute store result score @s stage_exists run data get storage <namespace>:stages players[{uuid:"<UUID>"}].stage

# 如果没有，初始化
execute if score @s stage_exists matches 0 run function <namespace>:stages/init_player with entity @s
```

`data/<namespace>/function/stages/init_player.mcfunction`
```mcfunction
# 宏函数，接收玩家数据
$data modify storage <namespace>:stages players append value {uuid:"$(UUID)",stage:0,sub_stage:0}
```

#### 3. 阶段推进（使用宏）

`data/<namespace>/function/stages/advance.mcfunction`
```mcfunction
# 推进玩家阶段
# 用法：execute as @a run function <namespace>:stages/advance with entity @s

$data modify storage <namespace>:stages players[{uuid:"$(UUID)"}].stage set value 1
$data modify storage <namespace>:stages players[{uuid:"$(UUID)"}].sub_stage set value 0

# 触发阶段进入逻辑
execute if data storage <namespace>:stages players[{uuid:"$(UUID)"}].stage{stage:1} run function <namespace>:stages/on_stage1 with entity @s
```

`data/<namespace>/function/stages/on_stage1.mcfunction`
```mcfunction
$tellraw @s {"text":"进入第一阶段！UUID: $(UUID)","color":"green"}
```

### 陷阱与注意事项

1. **UUID 获取**：在宏中获取玩家 UUID 需要使用 `$(UUID)` 变量，但注意：UUID 是数组格式 `[I;1,2,3,4]`，不能直接用于字符串比较。⚠️ 需验证：`data get entity @s UUID` 返回的格式是否可以直接用于宏。

2. **Storage 性能**：频繁修改 storage 可能比记分板慢，但适合存储复杂数据结构。

3. **宏函数限制**：宏函数不能直接调用其他宏函数（除非通过 `function` 命令传递参数）。

## 五、方案对比

| 特性 | 进度方案 | 记分板方案 | Storage+宏方案 |
|------|---------|-----------|---------------|
| **最低版本** | 1.13 | 1.13 | 1.20.2 |
| **性能开销** | 极低（原生） | 低（需tick） | 中（需解析JSON） |
| **状态持久化** | 自动（进度系统） | 自动（记分板） | 自动（Storage） |
| **复杂度** | 低 | 中 | 高 |
| **灵活性** | 中（受限于进度触发） | 高（完全控制） | 极高（可存复杂数据） |
| **调试难度** | 低 | 中 | 高 |
| **推荐场景** | 简单线性流程 | 中等复杂度流程 | 复杂多分支流程 |

## 六、最佳实践建议

1. **简单流程（3-5个阶段）**：使用进度方案，代码量少，性能好
2. **中等流程（5-15个阶段）**：使用记分板方案，灵活且易于调试
3. **复杂流程（15+阶段，有分支）**：使用 Storage+宏方案，但注意版本要求

## 七、通用陷阱

1. **阶段回退**：所有方案都不支持自动回退。如果需要玩家可以重新选择阶段，需要手动实现回退逻辑。
2. **多人游戏**：阶段是玩家独立的，但某些全局事件（如Boss击杀）需要广播给所有玩家。
3. **版本迁移**：如果数据包需要支持多个版本，建议使用记分板方案（兼容性最好）。
