# 如何让某件事只执行一次

## 核心挑战

在 Minecraft 数据包开发中，"只执行一次"的需求非常常见：玩家首次进入世界时给予初始物品、世界首次加载时初始化计分板、Boss 首次被击败时触发特殊事件等。核心挑战在于：

1. **原版没有内置的"一次性触发器"**——所有函数都可以被反复调用
2. **需要持久化状态**——服务器重启后"已执行"的状态不能丢失
3. **不同场景需要不同的方案**——全局 vs 玩家维度、首次加入 vs 每次加入

---

## 方案一：计分板标记法（最通用，推荐）

### 原理

利用 `scoreboard` 创建一个"标记计分板"，初始值为 0。执行逻辑前检查该值是否为 0，执行后设为 1（或任意非零值）。通过 `execute if score` 条件控制执行路径。

### 版本要求

1.13+（scoreboard 系统的基础功能）

### 完整代码

#### 1. 初始化（load 函数）

```mcfunction
# load.mcfunction
# 创建标记计分板（如果不存在）
scoreboard objectives add once_flag dummy
# 设置全局标记为 0（初始状态）
scoreboard players set $global once_flag 0
```

#### 2. 执行逻辑

```mcfunction
# tick.mcfunction
# 检查全局标记，如果为 0 则执行一次
execute if score $global once_flag matches 0 run function namespace:once/do_something
```

```mcfunction
# namespace:once/do_something.mcfunction
# 这里放只执行一次的逻辑
say 这是第一次执行，也是最后一次！
give @a minecraft:diamond 1

# 执行完毕后将标记设为 1，阻止再次执行
scoreboard players set $global once_flag 1
```

### 玩家维度版本

如果需要"每个玩家只执行一次"（如首次加入时给予初始物品）：

```mcfunction
# 初始化
scoreboard objectives add player_once_flag dummy

# 玩家加入检测（使用 advancement 或 tick 检测）
# tick.mcfunction
execute as @a if score @s player_once_flag matches 0 run function namespace:once/player_first_join

# namespace:once/player_first_join.mcfunction
say @s 首次加入世界！
give @s minecraft:iron_sword 1
scoreboard players set @s player_once_flag 1
```

### 陷阱与注意事项

1. **计分板名称冲突**：使用命名空间前缀（如 `namespace_once_flag`）避免与其他数据包冲突
2. **$global 命名规范**：`$` 前缀表示"假玩家"（fake player），不会与真实玩家冲突
3. **重置问题**：如果需要"重新执行一次"，只需将标记重置为 0
4. **性能**：开销极低——一次 `execute if score` 条件判断，无额外实体或 NBT 操作

## 方案二：进度（Advancement）奖励法

### 原理

利用进度（advancement）的 `rewards` 字段，在进度首次达成时自动执行一个函数。进度本身具有"已达成"状态，系统会自动阻止重复触发。

### 版本要求

1.12+（advancement 系统引入）

### 完整代码

#### 1. 创建进度

```json
// data/namespace/advancement/once/first_join.json
{
  "display": {
    "hidden": true
  },
  "criteria": {
    "impossible": {
      "trigger": "minecraft:impossible"
    }
  },
  "rewards": {
    "function": "namespace:once/on_first_join"
  }
}
```

#### 2. 触发进度

```mcfunction
# 在适当的时候（如玩家加入时）授予该进度
advancement grant @s only namespace:once/first_join
```

#### 3. 奖励函数

```mcfunction
# data/namespace/functions/once/on_first_join.mcfunction
say @s 首次触发！
give @s minecraft:diamond 1
# 注意：不需要手动撤销进度，因为进度只会触发一次
```

### 陷阱与注意事项

1. **进度已达成后无法再次触发**：即使 `advancement revoke` 后重新授予，进度会再次触发——这是设计特性，不是 bug
2. **`impossible` 触发器**：永远不会自然达成，只能通过 `advancement grant` 手动授予
3. **服务器重启后状态保留**：进度数据保存在 `advancements/` 目录中，重启后不会丢失
4. **性能**：开销较低——进度系统本身有优化，但比计分板方案略高（涉及文件 I/O 保存进度状态）
5. **⚠️ 需验证**：`advancement grant` 后奖励函数是否在**同一 tick** 内执行？实测表明是在同一 tick 内同步执行，但官方文档未明确说明

## 方案三：Storage 标记法（1.20.5+）

### 原理

利用 `data modify` 在 `storage` 中存储一个标记值。每次执行前检查该值，执行后修改标记。Storage 数据在服务器重启后**不会保留**，因此适合"本次游戏会话内只执行一次"的场景。

### 版本要求

1.20.5+（`data modify` 对 storage 的支持）

### 完整代码

#### 1. 初始化

```mcfunction
# load.mcfunction
# 设置初始标记
data modify storage namespace:once flag set value 0
```

#### 2. 执行逻辑

```mcfunction
# tick.mcfunction
execute if data storage namespace:once {flag:0} run function namespace:once/do_something
```

```mcfunction
# namespace:once/do_something.mcfunction
say 本次会话中只执行一次！
give @a minecraft:diamond 1

# 标记为已执行
data modify storage namespace:once flag set value 1
```

### 陷阱与注意事项

1. **服务器重启后标记丢失**：Storage 数据存储在内存中，重启后重置为初始值
2. **`execute if data` 性能**：比计分板方案略高，但仍在可接受范围内（每次检查需要解析 NBT）
3. **多数据包冲突**：使用命名空间前缀（如 `namespace:once`）避免与其他数据包冲突
4. **适用场景**：适合"每次服务器启动后只执行一次"的逻辑，如世界初始化、Boss 重生计时器等

## 方案四：实体标记法（不推荐）

### 原理

生成一个标记实体（如 `minecraft:marker`），通过检测该实体是否存在来判断是否已执行。执行后移除实体。

### 版本要求

1.17+（`minecraft:marker` 实体引入）

### 完整代码

```mcfunction
# tick.mcfunction
# 检查标记实体是否存在
execute unless entity @e[type=minecraft:marker,tag=namespace_once] run function namespace:once/do_something
```

```mcfunction
# namespace:once/do_something.mcfunction
say 只执行一次！
give @a minecraft:diamond 1

# 生成标记实体
summon minecraft:marker ~ ~ ~ {Tags:["namespace_once"]}
```

### 陷阱与注意事项

1. **实体数量膨胀**：如果逻辑被多次触发（如多个玩家同时触发），会生成多个标记实体
2. **实体清理**：需要额外的清理逻辑（如 `kill @e[type=minecraft:marker,tag=namespace_once]`）
3. **性能开销**：中高——`@e` 选择器需要遍历所有实体，且实体本身占用资源
4. **不推荐理由**：相比计分板方案，没有任何优势，反而引入实体管理的复杂性

## 方案对比

| 方案 | 版本要求 | 持久化 | 性能 | 适用场景 |
|------|---------|--------|------|---------|
| 计分板标记法 | 1.13+ | ✅ 是 | 极低 | 通用，推荐首选 |
| 进度奖励法 | 1.12+ | ✅ 是 | 较低 | 需要"首次达成"语义的场景 |
| Storage 标记法 | 1.20.5+ | ❌ 否 | 较低 | 本次会话内只执行一次 |
| 实体标记法 | 1.17+ | ❌ 否 | 中高 | 不推荐，除非有特殊需求 |

### 推荐选择

- **通用场景**：计分板标记法（方案一）
- **需要"首次达成"语义**（如成就系统）：进度奖励法（方案二）
- **每次服务器启动后只执行一次**：Storage 标记法（方案三）
- **不要使用**：实体标记法（方案四）
