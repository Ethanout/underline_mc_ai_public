# 如何调试复杂逻辑

## 一、核心挑战

Minecraft 数据包调试面临几个独特困难：
1. **无原生断点/单步执行**：mcfunction 是逐 tick 执行的批处理脚本，无法暂停观察中间状态
2. **状态分散**：数据可能分布在 scoreboard、storage、实体 NBT、方块 NBT 等多个位置
3. **时序问题**：多个函数在同一 tick 内执行，顺序错误会导致难以追踪的 bug
4. **副作用不可逆**：一旦执行了 `setblock`、`summon`、`kill` 等命令，无法回滚

## 二、方案一：Storage 日志记录法（推荐，1.20.2+）

### 原理

利用 `data modify` 命令向 storage 中追加日志条目，配合 `tellraw` 或 `schedule` 在特定时刻输出。Storage 是全局的、不随实体消失而丢失，适合记录跨 tick 的状态变化。

### 完整实现

#### 1. 初始化日志系统

`<namespace>/function/debug/init.mcfunction`
```mcfunction
# 创建日志 storage
data modify storage <namespace>:debug log set value []
scoreboard objectives add <namespace>.debug dummy

# 设置日志级别（0=关闭，1=错误，2=警告，3=信息，4=详细）
scoreboard players set global <namespace>.debug 3
```

#### 2. 日志写入函数

`<namespace>/function/debug/log.mcfunction`
```mcfunction
# 用法：function <namespace>:debug/log {level:3,message:"玩家位置: %s",data:"{x:10,y:64,z:10}"}
# 参数通过宏传入

$scoreboard players set global <namespace>.debug_level $(level)
execute if score global <namespace>.debug_level <= global <namespace>.debug run function <namespace>:debug/log_internal
```

`<namespace>/function/debug/log_internal.mcfunction`
```mcfunction
# 构建日志条目
data modify storage <namespace>:debug temp set value {}
data modify storage <namespace>:debug temp.time set value 0
execute store result storage <namespace>:debug temp.time int 1 run time query gametime
data modify storage <namespace>:debug temp.level set value "$(level)"
data modify storage <namespace>:debug temp.message set value "$(message)"
data modify storage <namespace>:debug temp.data set value $(data)

# 追加到日志数组
data modify storage <namespace>:debug log append from storage <namespace>:debug temp

# 如果日志超过100条，移除最旧的
execute if data storage <namespace>:debug log[100] run data remove storage <namespace>:debug log[0]
```

#### 3. 输出日志

`<namespace>/function/debug/print.mcfunction`
```mcfunction

data modify storage <namespace>:debug output set from storage <namespace>:debug log
```

#### 4. 使用示例

在需要调试的函数中插入：
```mcfunction
# 记录玩家位置
function <namespace>:debug/log {level:3,message:"玩家位置",data:"{x:%s,y:%s,z:%s}"}
# ⚠️ 需验证：宏参数中 %s 是否会被正确替换？实际上宏不支持格式化，需要手动拼接
# 正确做法：

execute store result storage <namespace>:debug temp.y int 1 run data get entity @s Pos[1]
execute store result storage <namespace>:debug temp.z int 1 run data get entity @s Pos[2]
function <namespace>:debug/log_macro {level:3,message:"玩家位置"}
```

`<namespace>/function/debug/log_macro.mcfunction`
```mcfunction
$data modify storage <namespace>:debug temp set value {}
$data modify storage <namespace>:debug temp.time set value 0
$execute store result storage <namespace>:debug temp.time int 1 run time query gametime
$data modify storage <namespace>:debug temp.level set value "$(level)"
$data modify storage <namespace>:debug temp.message set value "$(message)"
$data modify storage <namespace>:debug temp.data set value '{"x":$(x),"y":$(y),"z":$(z)}'
$data modify storage <namespace>:debug log append from storage <namespace>:debug temp
```

### 陷阱与注意事项

1. **宏参数不能包含复杂 JSON**：宏参数是字符串替换，如果 data 字段包含嵌套 JSON，需要小心转义。建议使用 `$()` 在宏函数中直接构建。
2. **日志存储空间**：storage 没有大小限制，但大量日志会影响性能。建议设置上限（如100条）。
3. **输出格式**：`tellraw` 中的 `nbt` 路径如果不存在会报错，所以需要先 `execute if data` 检查。
4. **版本要求**：宏功能需要 1.20.2+。如果使用 1.20-1.20.1，需要改用 `function` 命令传递参数（但更复杂）。

## 三、方案二：实体标记追踪法（1.13+，通用）

### 原理

创建一个标记实体（`marker` 或 `area_effect_cloud`），将调试数据写入其 NBT。通过 `data get` 或 `tellraw` 读取。实体可以跟随玩家移动，适合调试与特定玩家相关的逻辑。

### 完整实现

#### 1. 创建调试实体

`<namespace>/function/debug/spawn_tracker.mcfunction`
```mcfunction
# 为每个玩家创建一个调试实体
execute as @a run function <namespace>:debug/spawn_tracker_single
```

`<namespace>/function/debug/spawn_tracker_single.mcfunction`
```mcfunction
# 检查是否已有调试实体
execute if entity @e[type=marker,tag=<namespace>.debug_tracker,limit=1] run return fail

# 创建标记实体
summon marker ~ ~ ~ {Tags:["<namespace>.debug_tracker"],CustomName:'{"text":"Debug Tracker"}',CustomNameVisible:1b}

# 初始化数据
data modify entity @e[type=marker,tag=<namespace>.debug_tracker,limit=1] data set {values:{}}
```

#### 2. 写入调试数据

`<namespace>/function/debug/set_value.mcfunction`
```mcfunction
# 用法：function <namespace>:debug/set_value {key:"player_x",value:10}
# 需要宏支持

$data modify entity @e[type=marker,tag=<namespace>.debug_tracker,limit=1] data.values.$(key) set value $(value)
```

#### 3. 读取调试数据

`<namespace>/function/debug/read_value.mcfunction`
```mcfunction
# 用法：function <namespace>:debug/read_value {key:"player_x"}
# 输出到聊天栏

$tellraw @a [{"text":"$(key) = ","color":"gray"},{"nbt":"data.values.$(key)","entity":"@e[type=marker,tag=<namespace>.debug_tracker,limit=1]","color":"yellow"}]
```

#### 4. 清理调试实体

`<namespace>/function/debug/cleanup.mcfunction`
```mcfunction
kill @e[type=marker,tag=<namespace>.debug_tracker]
```

### 陷阱与注意事项

1. **实体数量**：每个玩家一个调试实体，多人时要注意区分。可以在创建时绑定玩家 UUID。
2. **实体卸载**：如果玩家离开加载范围，调试实体可能被卸载，数据丢失。建议使用 `@s` 选择器在玩家附近创建。
3. **NBT 路径限制**：`data get` 命令的 NBT 路径不能包含特殊字符（如空格、点号）。如果 key 包含这些字符，需要转义或使用方括号表示法。
4. **性能开销**：每个 tick 都操作实体 NBT 会有一定开销。建议只在需要调试时启用。

## 四、方案三：计分板断点法（1.13+，轻量级）

### 原理

利用计分板（scoreboard）作为断点标志。在关键位置设置计分板检查，当满足条件时暂停执行或输出信息。类似传统编程中的 `assert` 或断点。

### 完整实现

#### 1. 设置断点系统

`<namespace>/function/debug/breakpoint_init.mcfunction`
```mcfunction
scoreboard objectives add <namespace>.debug_break dummy
scoreboard objectives add <namespace>.debug_step dummy

# 设置断点启用状态
scoreboard players set global <namespace>.debug_break 0  # 0=禁用, 1=启用
```

#### 2. 断点检查函数

`<namespace>/function/debug/breakpoint.mcfunction`
```mcfunction
# 用法：在需要断点的位置调用此函数
# 参数通过宏传入：{id:"step1",condition:"@s"}

$execute if score global <namespace>.debug_break matches 1 run function <namespace>:debug/breakpoint_check {id:"$(id)",condition:"$(condition)"}
```

`<namespace>/function/debug/breakpoint_check.mcfunction`
```mcfunction
# 检查条件是否满足
$execute if entity $(condition) run function <namespace>:debug/breakpoint_hit {id:"$(id)"}
```

`<namespace>/function/debug/breakpoint_hit.mcfunction`
```mcfunction
# 断点命中：输出信息并暂停（通过 schedule 延迟执行）
$tellraw @a [{"text":"[BREAKPOINT] ","color":"red"},{"text":"$(id)","color":"gold"},{"text":" hit at tick ","color":"gray"},{"nbt":"","entity":"@s","interpret":true}]

# 记录断点命中次数
$scoreboard players add $(id) <namespace>.debug_step 1

# 暂停执行（延迟1 tick后继续）
schedule function <namespace>:debug/continue 1t replace
```

`<namespace>/function/debug/continue.mcfunction`
```mcfunction
# 继续执行（可以在这里恢复被暂停的逻辑）
tellraw @a [{"text":"[DEBUG] Continuing execution","color":"green"}]
```

#### 3. 使用示例

在需要调试的函数中：
```mcfunction
# 在关键逻辑前设置断点
function <namespace>:debug/breakpoint {id:"before_teleport",condition:"@s"}

# 关键逻辑
tp @s ~ ~5 ~

# 在关键逻辑后设置断点
function <namespace>:debug/breakpoint {id:"after_teleport",condition:"@s"}
```

### 陷阱与注意事项

1. **schedule 的局限性**：`schedule` 命令只能延迟执行函数，不能真正暂停当前执行流。断点后的代码仍然会执行。
2. **条件选择器**：`condition` 参数必须是有效的实体选择器。如果条件不满足，断点不会触发。
3. **计分板名称冲突**：使用 `$(id)` 作为计分板名称时，要确保不会与现有计分板冲突。建议使用命名空间前缀。
4. **多玩家环境**：断点会同时影响所有玩家。如果需要按玩家区分，需要在条件中包含玩家选择器。

## 五、方案对比

| 特性 | Storage 日志法 | 实体标记法 | 计分板断点法 |
|------|---------------|-----------|-------------|
| 最低版本 | 1.20.2（宏） | 1.13 | 1.13 |
| 数据持久性 | 高（storage 不卸载） | 中（实体可能卸载） | 低（计分板持久但数据量小） |
| 数据容量 | 大（可存复杂 JSON） | 中（实体 NBT 有限制） | 小（仅整数） |
| 性能开销 | 中（频繁 data modify） | 中（实体操作） | 低（仅 scoreboard） |
| 调试体验 | 好（可记录历史） | 中（实时查看） | 好（类似断点） |
| 实现复杂度 | 高（需要宏） | 中 | 低 |
| 适用场景 | 复杂逻辑的长期调试 | 玩家相关数据追踪 | 快速定位问题位置 |

## 六、最佳实践建议

1. **分层调试**：先用计分板断点法快速定位问题范围，再用 Storage 日志法记录详细数据。
2. **条件编译**：使用计分板控制调试开关，发布时关闭所有调试逻辑。
3. **日志级别**：参考 log4j 的级别系统（ERROR > WARN > INFO > DEBUG），只在需要时输出详细信息。
4. **自动化测试**：编写测试函数，用 `execute if` 和 `scoreboard` 验证预期结果，自动报告失败。

## 七、陷阱总结

1. **宏参数转义**：宏参数中的特殊字符（如引号、花括号）需要转义，否则会导致 JSON 解析错误。
2. **实体选择器性能**：在 tick 函数中使用 `@e[type=marker,tag=...]` 会扫描所有实体，建议限制数量或使用 `limit=1`。
3. **schedule 的替换行为**：`schedule ... replace` 会替换同名的已调度函数，可能导致断点丢失。
4. **数据竞争**：多个函数同时修改同一 storage 或实体 NBT 时，可能出现数据不一致。建议使用原子操作或加锁（通过计分板）。
