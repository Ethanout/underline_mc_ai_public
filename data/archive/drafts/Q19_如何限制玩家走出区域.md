# 如何限制玩家走出区域

## 核心挑战

限制玩家走出指定区域在数据包开发中是一个经典需求，常见于小游戏、RPG地图或服务器保护。核心挑战在于：

1. **检测的实时性**：需要在玩家跨过边界时立即响应，而不是等到下一个 tick
2. **边界处理的平滑性**：粗暴的传送可能导致玩家卡顿或视觉跳跃
3. **性能开销**：高频检测（如每 tick 执行）可能影响服务器性能
4. **多维度处理**：需要同时考虑 X、Y、Z 三个轴向

## 方案一：基于谓词的位置检测 + 传送（最常用）

### 原理

利用 `predicate`（谓词）中的 `location_check` 检测玩家是否在允许区域外，然后在 `execute` 命令中条件执行传送。这是最直接、最灵活的方法。

### 版本要求

1.16+（谓词系统引入），1.19+ 支持更丰富的坐标检测

### 完整实现

#### 1. 创建边界检测谓词

`data/<namespace>/predicate/out_of_bounds.json`
```json
{
  "condition": "minecraft:alternative",
  "terms": [
    {
      "condition": "minecraft:entity_properties",
      "entity": "this",
      "predicate": {
        "location": {
          "position": {
            "x": {
              "min": -100.0,
              "max": 100.0
            },
            "z": {
              "min": -100.0,
              "max": 100.0
            }
          }
        }
      }
    }
  ]
}
```

⚠️ **需验证**：`alternative` 的语义是"任一条件成立"还是"所有条件不成立"？实际上 `alternative` 是 OR 逻辑，所以这里检测的是"在区域内"。我们需要的是"在区域外"，所以应该用 `inverted` 取反。

修正后的谓词：

`data/<namespace>/predicate/out_of_bounds.json`
```json
{
  "condition": "minecraft:inverted",
  "term": {
    "condition": "minecraft:entity_properties",
    "entity": "this",
    "predicate": {
      "location": {
        "position": {
          "x": {
            "min": -100.0,
            "max": 100.0
          },
          "z": {
            "min": -100.0,
            "max": 100.0
          }
        }
      }
    }
  }
}
```

#### 2. 创建传送函数

`data/<namespace>/function/boundary/pull_back.mcfunction`
```mcfunction
# 将玩家传送回区域中心（或指定安全点）
# 这里使用区域中心 (0, 64, 0)
execute as @s at @s run tp @s 0 64 0

# 可选：发送提示消息
tellraw @s {"text":"你已超出边界，已传送回安全区域","color":"red"}
```

#### 3. 在 tick 函数中执行检测

`data/<namespace>/function/tick.mcfunction`
```mcfunction
# 每 tick 检测所有玩家是否在区域外
execute as @a[predicate=<namespace>:out_of_bounds] at @s run function <namespace>:boundary/pull_back
```

### 陷阱与注意事项

1. **性能问题**：每 tick 对所有玩家执行谓词检测，当玩家数量较多时（>50）可能产生性能压力。建议使用 `@a[predicate=...]` 而不是 `execute as @a if predicate ...`，前者在谓词不匹配时不会执行后续命令。

2. **Y轴处理**：上述谓词只检测了 X 和 Z 轴。如果需要限制 Y 轴（如防止玩家飞出世界），需要添加 Y 轴条件：

```json
{
  "condition": "minecraft:inverted",
  "term": {
    "condition": "minecraft:entity_properties",
    "entity": "this",
    "predicate": {
      "location": {
        "position": {
          "x": { "min": -100.0, "max": 100.0 },
          "y": { "min": 0.0, "max": 256.0 },
          "z": { "min": -100.0, "max": 100.0 }
        }
      }
    }
  }
}
```

3. **传送时的位置偏移**：直接 `tp` 到固定点可能导致玩家卡在方块里。建议使用 `spreadplayers` 或检测安全位置后再传送。

4. **玩家在边界附近反复进出**：如果玩家在边界附近来回移动，每 tick 都会触发传送，造成"抖动"。解决方案：添加冷却机制，如使用 scoreboard 记录上次传送时间。

## 方案二：基于进度触发器 + 位置变化检测（低性能开销）

### 原理

利用 `minecraft:location` 触发器创建进度，当玩家位置满足特定条件时触发。这种方法不需要每 tick 执行命令，而是由游戏事件驱动，性能开销极低。

### 版本要求

1.16+（进度系统）

### 完整实现

#### 1. 创建边界检测进度

`data/<namespace>/advancement/boundary/out_of_bounds.json`
```json
{
  "criteria": {
    "out_of_bounds": {
      "trigger": "minecraft:location",
      "conditions": {
        "player": [
          {
            "condition": "minecraft:inverted",
            "term": {
              "condition": "minecraft:entity_properties",
              "entity": "this",
              "predicate": {
                "location": {
                  "position": {
                    "x": { "min": -100.0, "max": 100.0 },
                    "z": { "min": -100.0, "max": 100.0 }
                  }
                }
              }
            }
          }
        ]
      }
    }
  },
  "rewards": {
    "function": "<namespace>:boundary/pull_back"
  }
}
```

#### 2. 创建传送函数（同方案一）

`data/<namespace>/function/boundary/pull_back.mcfunction`
```mcfunction
execute as @s at @s run tp @s 0 64 0
tellraw @s {"text":"你已超出边界，已传送回安全区域","color":"red"}

# 关键：撤销进度，以便下次再次触发
advancement revoke @s only <namespace>:boundary/out_of_bounds
```

#### 3. 初始化（在 load 函数中）

`data/<namespace>/function/load.mcfunction`
```mcfunction
# 为所有在线玩家授予进度（使其进入"可触发"状态）
advancement grant @a only <namespace>:boundary/out_of_bounds
```

### 陷阱与注意事项

1. **进度触发频率**：`minecraft:location` 触发器每 20 tick（1秒）检测一次玩家位置，而不是每 tick。这意味着玩家可能在边界外停留最多 1 秒才会被传送。对于需要即时响应的场景（如防止玩家离开竞技场），这个延迟可能不可接受。

2. **进度撤销时机**：必须在传送函数中撤销进度，否则进度只会触发一次。但撤销后需要重新授予，否则下次无法触发。这带来了一个循环：授予 → 触发 → 撤销 → 重新授予。

3. **多人游戏中的进度同步**：如果玩家在进度触发后、撤销前断开连接，进度状态可能不一致。建议在玩家加入时重新授予进度。

4. **Y轴检测**：`minecraft:location` 触发器支持完整的坐标检测，包括 Y 轴。

## 方案三：基于命令方块 + 结构边界（简单但非数据包原生）

### 原理

利用 `/fill` 命令创建不可见的屏障方块（`barrier`）或结构空位（`structure_void`）来物理阻挡玩家。这种方法不需要任何数据包逻辑，但不够灵活。

### 版本要求

1.13+（屏障方块引入）

### 实现方式

```mcfunction
# 在区域边界创建屏障墙
fill -100 0 -100 -100 256 100 minecraft:barrier
fill 100 0 -100 100 256 100 minecraft:barrier
fill -100 0 -100 100 256 -100 minecraft:barrier
fill -100 0 100 100 256 100 minecraft:barrier
```

### 陷阱与注意事项

1. **视觉问题**：屏障方块默认不可见，但玩家在创造模式下可以看到。可以使用 `minecraft:barrier` 的粒子效果来提示边界。

2. **破坏问题**：玩家可以破坏屏障方块（生存模式下需要足够挖掘速度）。建议配合 `gamerule doTileDrops false` 和 `gamerule mobGriefing false`。

3. **不灵活**：改变区域大小需要重新执行 fill 命令，不适合动态边界。

4. **性能**：大量屏障方块可能影响区块加载性能。

## 方案四：基于 scoreboard + 坐标运算（精确控制）

### 原理

将玩家的坐标存储到 scoreboard 中，通过数学运算判断是否超出边界。这种方法可以实现非常精确的控制，如渐变传送或边界反弹效果。

### 版本要求

1.13+（scoreboard 系统）

### 完整实现

#### 1. 初始化 scoreboard

`data/<namespace>/function/load.mcfunction`
```mcfunction
scoreboard objectives add <namespace>.x dummy
scoreboard objectives add <namespace>.z dummy
```

#### 2. 每 tick 检测

`data/<namespace>/function/tick.mcfunction`
```mcfunction
# 存储玩家坐标到 scoreboard
execute as @a at @s run function <namespace>:boundary/check
```

`data/<namespace>/function/boundary/check.mcfunction`
```mcfunction
# 获取玩家坐标（注意：坐标是 double，需要取整）
execute store result score @s <namespace>.x run data get entity @s Pos[0]
execute store result score @s <namespace>.z run data get entity @s Pos[2]

# 判断是否超出边界（假设边界为 -100 到 100）
execute if score @s <namespace>.x matches -100..100 if score @s <namespace>.z matches -100..100 run return 0

# 超出边界，执行传送
function <namespace>:boundary/pull_back
```

### 陷阱与注意事项

1. **坐标精度**：`data get entity @s Pos[0]` 返回的是 double 值，但 `store result` 会取整（截断小数）。这意味着玩家在边界附近时，取整可能导致误判。例如，玩家在 x=100.5 时，取整后为 100，会被判定为在区域内。

2. **解决方案**：使用 `store success` 配合条件判断，或使用更精确的坐标比较方法。

3. **性能**：每 tick 对所有玩家执行 `data get` 操作，性能开销中等。

## 方案对比

| 方案 | 版本要求 | 检测延迟 | 性能开销 | 精确度 | 适用场景 |
|------|---------|---------|---------|-------|---------|
| 谓词检测 + 传送 | 1.16+ | 1 tick | 中（每 tick 执行） | 高 | 需要即时响应的场景 |
| 进度触发器 | 1.16+ | 1秒（20 tick） | 低（事件驱动） | 高 | 非即时场景，如探索限制 |
| 屏障方块 | 1.13+ | 即时 | 低（物理阻挡） | 中 | 简单边界，不需要逻辑 |
| scoreboard 运算 | 1.13+ | 1 tick | 中高 | 中（取整问题） | 需要复杂逻辑的场景 |

## 推荐方案

对于大多数场景，推荐使用**方案一（谓词检测 + 传送）**，因为它：
- 检测延迟低（1 tick）
- 配置灵活（可以轻松修改边界范围）
- 性能可接受（使用 `@a[predicate=...]` 优化）
- 支持完整的坐标检测（X、Y、Z）

如果对性能有极致要求且可以接受 1 秒延迟，可以选择**方案二（进度触发器）**。
