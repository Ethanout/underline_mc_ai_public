# 如何做全局计时器

## 一、核心挑战

在 Minecraft 数据包开发中，全局计时器用于实现定时任务（如每 5 秒刷怪、每 30 秒检查天气、倒计时系统等）。核心挑战在于：
1. **无原生定时器**：原版没有内置的全局 tick 计数器，需要自行实现
2. **性能开销**：高频检测（如每 tick 执行）可能影响服务器性能
3. **持久化**：服务器重启后计时器需要能恢复
4. **多玩家兼容**：全局计时器不应依赖单个玩家在线

## 二、方案一：Scoreboard 循环累加（最推荐）

### 原理

利用 `scoreboard players add` 每 tick 对全局虚拟玩家（如 `#global_timer`）的分数加 1，当达到目标值时触发事件并重置。这是最直接、性能最优的方案。

### 版本要求

- 1.13+（scoreboard 系统稳定）
- 1.20.5+ 无变化

### 完整实现

#### 1. 初始化 (load)

```mcfunction
# load.mcfunction
scoreboard objectives add timer dummy
scoreboard players set #global_timer timer 0
```

#### 2. 每 tick 累加 (tick)

```mcfunction
# tick.mcfunction
scoreboard players add #global_timer timer 1
execute if score #global_timer timer matches 100.. run function namespace:timer/trigger
```

#### 3. 触发事件并重置

```mcfunction
# namespace:function/timer/trigger.mcfunction
# 这里执行你的定时任务
say 100 ticks passed!

# 重置计时器
scoreboard players set #global_timer timer 0
```

### 陷阱与注意事项

1. **分数溢出**：`scoreboard` 分数范围是 -2,147,483,648 到 2,147,483,647。如果计时器周期很长（如 1 小时 = 72,000 ticks），不会溢出，但若周期超过 2^31 ticks（约 124 天），会溢出。实际场景中几乎不可能。
2. **多计时器冲突**：如果同时运行多个计时器，需要为每个计时器创建独立的 objective 或使用不同的虚拟玩家名。
3. **服务器 tick 率**：Minecraft 服务器默认 20 ticks/秒，但若服务器卡顿，tick 率会下降，计时器会变慢。这是所有基于 tick 的计时器的共同问题。
4. **重启恢复**：scoreboard 数据在服务器重启后会自动保存，无需额外处理。

## 三、方案二：进度（Advancement）计时器

### 原理

利用 `minecraft:tick` 触发器的进度，每 tick 触发一次，通过进度奖励函数执行逻辑。这种方式将计时逻辑与进度系统绑定，适合需要与玩家进度联动的场景。

### 版本要求

- 1.13+（`tick` 触发器引入于 1.13）

### 完整实现

#### 1. 创建进度

```json
// data/namespace/advancement/timer_tick.json
{
  "criteria": {
    "tick": {
      "trigger": "minecraft:tick"
    }
  },
  "rewards": {
    "function": "namespace:timer/tick_handler"
  }
}
```

#### 2. 处理函数

```mcfunction
# data/namespace/functions/timer/tick_handler.mcfunction
# 注意：这个函数每 tick 对每个玩家执行一次
# 使用虚拟玩家 #global_timer 来计数
scoreboard players add #global_timer timer 1
execute if score #global_timer timer matches 100.. run function namespace:timer/trigger

# 撤销进度，以便下次 tick 再次触发
advancement revoke @s only namespace:timer_tick
```

#### 3. 触发事件

```mcfunction
# data/namespace/functions/timer/trigger.mcfunction
say 100 ticks passed!
scoreboard players set #global_timer timer 0
```

### 陷阱与注意事项

1. **性能开销**：每个玩家每 tick 都会触发一次进度，如果有 100 个玩家，就是 100 次/ tick。远高于方案一的 1 次/ tick。**不推荐用于高频计时器**。
2. **玩家离线问题**：如果没有玩家在线，进度不会触发，计时器会暂停。不适合需要持续运行的全局计时器。
3. **进度撤销**：必须每 tick 撤销进度，否则进度只会触发一次。这增加了额外的命令开销。
4. **多玩家同步**：多个玩家同时触发时，`#global_timer` 的累加会重复，需要额外逻辑确保只累加一次（如使用 `execute if entity @s[scores={timer=0}]` 限制）。

## 四、方案三：Storage + Schedule（持久化计时器）

### 原理

利用 `data modify` 在 storage 中存储计时器值，配合 `schedule` 命令实现定时触发。这种方式适合需要精确时间控制（如 5 秒后执行）且需要持久化的场景。

### 版本要求

- 1.14+（`schedule` 命令引入于 1.14）
- 1.20.5+（storage 系统稳定）

### 完整实现

#### 1. 初始化 (load)

```mcfunction
# load.mcfunction
data modify storage namespace:timer Timer set value 0
```

#### 2. 启动计时器

```mcfunction
# 启动一个 100 tick 后触发的计时器
schedule function namespace:timer/trigger 100t
```

#### 3. 触发事件

```mcfunction
# data/namespace/functions/timer/trigger.mcfunction
# 读取 storage 中的值
data get storage namespace:timer Timer

# 执行任务
say Timer triggered!

# 如果需要循环，重新调度
schedule function namespace:timer/trigger 100t
```

### 陷阱与注意事项

1. **schedule 限制**：`schedule` 命令的最小单位是 1 tick，最大延迟为 2,147,483,647 ticks（约 124 天）。但 `schedule` 在服务器重启后**不会保留**，需要重新调度。
2. **持久化问题**：storage 数据在服务器重启后会丢失。如果需要持久化，需要将计时器值写入 scoreboard 或 NBT 文件。
3. **多计时器管理**：每个 `schedule` 调用都是独立的，如果需要多个计时器，需要为每个计时器创建独立的函数和 storage 路径。
4. **schedule 堆积**：如果计时器周期很短（如 1 tick），大量 `schedule` 调用可能导致性能问题。建议周期至少 20 ticks 以上。

## 五、方案四：实体计时器（利用 Age 标签）

### 原理

生成一个标记实体（如 `minecraft:marker`），利用其 `Age` 标签（每 tick 自动增加）作为计时器。当 `Age` 达到目标值时触发事件。

### 版本要求

- 1.17+（`minecraft:marker` 实体引入于 1.17）
- 1.13+（可使用 `minecraft:armor_stand` 替代，但性能较差）

### 完整实现

#### 1. 生成计时器实体 (load)

```mcfunction
# load.mcfunction
summon minecraft:marker ~ ~ ~ {Tags:["global_timer"]}
```

#### 2. 每 tick 检查 (tick)

```mcfunction
# tick.mcfunction
execute as @e[tag=global_timer,type=minecraft:marker] if score @s timer matches 100.. run function namespace:timer/trigger
```

#### 3. 触发事件

```mcfunction
# data/namespace/functions/timer/trigger.mcfunction
# 重置计时器
scoreboard players set @s timer 0
say 100 ticks passed!
```

### 陷阱与注意事项

1. **实体数量**：每个计时器需要一个实体，大量计时器会消耗实体数量上限（默认 200）。
2. **Age 标签限制**：`Age` 标签是实体自带的，但无法直接用于 scoreboard 操作。需要先将其复制到 scoreboard 中。
3. **性能开销**：每 tick 需要遍历所有计时器实体，性能低于方案一。
4. **持久化**：实体在服务器重启后会自动保存，但需要确保实体不会被意外清除（如 `/kill @e`）。

## 六、方案对比

| 方案 | 版本要求 | 性能开销 | 持久化 | 多计时器 | 适用场景 |
|------|----------|----------|--------|----------|----------|
| Scoreboard 循环累加 | 1.13+ | 极低（1 次命令/tick） | 自动 | 容易（不同虚拟玩家） | 通用，推荐 |
| 进度计时器 | 1.13+ | 高（每玩家每 tick） | 自动 | 复杂 | 玩家相关计时器 |
| Storage + Schedule | 1.14+ | 低（schedule 触发） | 需手动 | 中等 | 精确定时任务 |
| 实体计时器 | 1.17+ | 中（遍历实体） | 自动 | 容易（不同实体） | 需要实体交互的场景 |

## 七、最佳实践建议

1. **通用场景**：使用方案一（Scoreboard 循环累加），性能最优，实现简单。
2. **需要精确时间**：使用方案三（Storage + Schedule），但注意重启后需重新调度。
3. **玩家相关**：使用方案二（进度计时器），但注意性能开销。
4. **需要实体交互**：使用方案四（实体计时器），但注意实体数量限制。

## 八、完整示例：每 5 秒刷怪

### 使用方案一

```mcfunction
# load.mcfunction
scoreboard objectives add timer dummy
scoreboard players set #spawn_timer timer 0

# tick.mcfunction
scoreboard players add #spawn_timer timer 1
execute if score #spawn_timer timer matches 100.. run function namespace:spawn/mob

# namespace:function/spawn/mob.mcfunction
# 刷怪逻辑
summon minecraft:zombie ~ ~ ~
scoreboard players set #spawn_timer timer 0
```

### 使用方案三

```mcfunction
# load.mcfunction
schedule function namespace:spawn/mob 100t

# namespace:function/spawn/mob.mcfunction
summon minecraft:zombie ~ ~ ~
schedule function namespace:spawn/mob 100t
```
