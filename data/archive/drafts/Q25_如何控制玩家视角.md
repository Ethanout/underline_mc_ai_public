# 如何控制玩家视角

## 核心挑战

控制玩家视角在数据包开发中是一个经典难题。原版 Minecraft 没有提供直接设置玩家视角（即头部旋转角度 `Rotation`）的简单命令。`/teleport` 可以改变实体朝向，但会同时移动位置；`/data merge entity` 可以修改 `Rotation` NBT，但服务端修改后客户端会立即被覆盖回客户端预测的位置，导致视角"弹回"。因此，实现稳定的视角控制需要理解客户端-服务端同步机制，并利用特定的触发时机。

## 方案一：使用 `/teleport` 的朝向参数（最稳定，但会移动位置）

### 原理

`/teleport` 命令的 `facing` 参数可以强制设置实体的朝向（即视角方向），但副作用是会将玩家传送到指定坐标。通过将玩家传送到其当前位置，可以"原地"改变视角。

### 适用版本

1.13+（`/teleport` 的 `facing` 语法）

### 完整代码

```mcfunction
# 将玩家 @s 的视角强制朝向坐标 (100, 64, 200)
execute as @s at @s run teleport @s ~ ~ ~ facing 100 64 200
```

### 陷阱与注意事项

1. **位置抖动**：由于浮点数精度和客户端预测，`~ ~ ~` 传送到当前位置可能导致玩家位置发生微小偏移（约 0.0001 格），在连续高频调用时可能产生可见的抖动。
2. **触发时机**：必须在服务端 tick 中执行，且客户端会立即响应。但如果玩家正在移动（如按住 W 键），客户端预测会尝试修正视角，导致短暂"弹回"。
3. **性能**：开销较低。每次执行仅涉及一次实体查找和坐标计算。

## 方案二：使用 `/data merge entity` 修改 Rotation（无位置副作用，但有弹回问题）

### 原理

直接修改玩家的 `Rotation` NBT 标签（格式为 `[yaw, pitch]`，单位为度）。服务端修改后，客户端会在下一个 tick 收到更新，但客户端预测系统会尝试将视角"拉回"到玩家鼠标输入对应的方向，导致明显的弹回。

### 适用版本

1.13+（`/data merge entity` 命令）

### 完整代码

```mcfunction
# 将玩家 @s 的视角设置为 yaw=90.0, pitch=30.0
data merge entity @s {Rotation: [90.0f, 30.0f]}
```

### 陷阱与注意事项

1. **严重弹回**：这是最核心的问题。客户端预测会覆盖服务端设置的 Rotation，导致视角闪烁。仅在玩家完全静止（不移动鼠标、不按任何移动键）时可能短暂生效。
2. **NBT 格式**：`Rotation` 是浮点数数组，必须使用 `f` 后缀（如 `90.0f`），否则命令会报错。
3. **性能**：开销较低。但弹回问题使其几乎不可用，除非配合其他机制（如强制客户端暂停预测，但原版无法做到）。

## 方案三：利用 `player` 实体类型与 `look_at` 触发器（1.20.5+ 推荐）

### 原理

从 1.20.5 开始，Minecraft 引入了 `player` 实体类型和 `look_at` 触发器（用于进度/战利品表）。通过进度系统，可以在特定条件下触发函数，并在函数中修改视角。但直接修改 `Rotation` 仍然有弹回问题。

**更实用的方法**：结合 `player` 实体的 `look_at` 组件（通过 `item_modifier` 或 `entity_component` 设置）来强制视角朝向。但 `look_at` 组件是实体行为的一部分，通常用于生物，对玩家无效。

**实际可行方案**：使用 `execute on` 和 `facing` 参数，但避免位置移动。

### 适用版本

1.20.5+

### 完整代码

```mcfunction
# 使用 execute 的 facing 参数，不移动位置
execute as @s at @s anchored eyes facing entity @e[type=minecraft:marker,limit=1] eyes run tp @s ~ ~ ~ ~ ~
```

### 陷阱与注意事项

1. **`anchored eyes` 需验证**：`anchored` 子命令在 1.20.5 中是否支持 `eyes` 参数？根据文档，`anchored` 支持 `feet` 和 `eyes`，但 `eyes` 在 1.20.5 中可能未实现。⚠️ 需验证。
2. **位置移动**：`tp @s ~ ~ ~ ~ ~` 中的 `~ ~ ~` 仍然会触发位置同步，但因为是原地，抖动较小。
3. **性能**：开销较低。

## 方案四：使用 `spectate` 命令（1.15+，间接控制）

### 原理

`/spectate` 命令可以让旁观模式玩家跟随一个实体，视角会自动朝向该实体。通过控制被跟随实体的位置和旋转，可以间接控制玩家视角。

### 适用版本

1.15+

### 完整代码

```mcfunction
# 创建一个标记实体作为视角目标
summon minecraft:marker ~ ~ ~ {Tags:["view_target"]}

# 让玩家旁观该标记
spectate @e[tag=view_target,limit=1] @s

# 控制标记实体的位置和旋转来影响玩家视角
tp @e[tag=view_target] ~ ~ ~ facing 100 64 200
```

### 陷阱与注意事项

1. **仅限旁观模式**：玩家必须在旁观模式（`/gamemode spectator`）下才能使用 `/spectate`。生存模式玩家无法使用。
2. **视角延迟**：玩家视角会平滑跟随目标实体，但存在约 1-2 tick 的延迟。
3. **退出问题**：玩家退出旁观模式后，视角控制失效，需要重新设置。
4. **性能**：开销较低。但需要额外维护一个标记实体。

## 方案五：利用 `inventory_changed` 进度 + 高频强制设置（1.13+，最实用）

### 原理

结合方案一（`/teleport` 朝向）和进度系统，在玩家物品栏变化时强制设置视角。通过高频触发（如每 tick 触发进度），可以持续压制客户端预测，实现稳定的视角控制。

### 适用版本

1.13+

### 完整代码

#### 1. 创建进度（每 tick 触发）

`data/<namespace>/advancement/lock_view.json`
```json
{
  "criteria": {
    "tick": {
      "trigger": "minecraft:tick"
    }
  },
  "rewards": {
    "function": "<namespace>:lock_view"
  }
}
```

#### 2. 视角锁定函数

`data/<namespace>/function/lock_view.mcfunction`
```mcfunction
# 将玩家视角锁定为朝向 (100, 64, 200)
execute as @s at @s run teleport @s ~ ~ ~ facing 100 64 200

# 重新授予进度，确保下个 tick 继续触发
advancement revoke @s only <namespace>:lock_view
```

#### 3. 初始化（Load）

`data/<namespace>/function/load.mcfunction`
```mcfunction
# 授予所有在线玩家进度
advancement grant @a only <namespace>:lock_view
```

### 陷阱与注意事项

1. **性能开销**：每 tick 对所有玩家执行一次 `/teleport` 和一次 `advancement revoke`，开销中等。对于 20 名玩家，每 tick 约 40 条命令，对服务器性能影响较小。
2. **位置抖动**：同方案一，存在微小位置偏移。可通过在 `teleport` 中使用精确坐标（如 `~ ~ ~` 改为 `^ ^ ^0`）缓解，但 `^` 语法在 1.13+ 可用。
3. **进度触发延迟**：`tick` 进度在每个玩家 tick 触发，但 `advancement revoke` 和重新授予之间存在 1 tick 的间隔，可能导致偶尔的视角弹回。
4. **玩家加入**：新加入的玩家需要手动授予进度，可通过 `player_joined` 进度或 `tick` 函数检测。

## 方案对比

| 方案 | 版本要求 | 位置副作用 | 视角稳定性 | 性能开销 | 适用场景 |
|------|----------|------------|------------|----------|----------|
| 方案一：`/teleport` 朝向 | 1.13+ | 微小抖动 | 高（单次） | 低 | 一次性视角设置 |
| 方案二：`/data merge` | 1.13+ | 无 | 极低（弹回） | 低 | 几乎不可用 |
| 方案三：`execute facing` | 1.20.5+ | 微小抖动 | 中 | 低 | 需要精确朝向 |
| 方案四：`/spectate` | 1.15+ | 无 | 高（有延迟） | 低 | 旁观模式视角控制 |
| 方案五：进度高频锁定 | 1.13+ | 微小抖动 | 高（持续） | 中 | 需要持续锁定视角 |

## 推荐方案

- **一次性视角设置**：方案一（`/teleport` 朝向）最稳定，代码最简单。
- **持续锁定视角**：方案五（进度高频锁定）最实用，兼容性好。
- **旁观模式视角控制**：方案四（`/spectate`）体验最佳，无抖动。
- **1.20.5+ 新项目**：方案三（`execute facing`）值得尝试，但需验证 `anchored eyes` 的可用性。

## 陷阱总结

1. **客户端预测**：所有直接修改 `Rotation` 的方法都会受到客户端预测的影响，导致弹回。只有通过 `/teleport` 或 `/spectate` 这类服务端强控制命令才能稳定生效。
2. **位置抖动**：`/teleport` 的 `~ ~ ~` 语法会导致微小位置偏移，在需要精确位置的场景（如瞄准）中可能造成问题。可使用 `^ ^ ^0` 或精确坐标缓解。
3. **性能权衡**：高频触发（方案五）虽然稳定，但会增加服务器负载。对于少量玩家（<10），影响可忽略；对于大型服务器（>50），建议使用方案一配合条件触发。
4. **版本兼容**：`/spectate` 在 1.15 引入，`execute facing` 的 `anchored eyes` 在 1.20.5 中可能不完整。开发前请确认目标版本。
