# 如何做延迟执行

## 一、核心挑战

Minecraft 数据包本质上是**同步单帧执行**的——一个函数调用链在同一个 tick 内完成，无法直接“等待 N tick 后再执行”。要实现延迟执行，必须借助游戏内建的异步机制（如进度、计划刻、实体 tick 等）来“跨 tick 传递执行信号”。

## 二、方案一：进度（Advancement）触发法

### 原理

利用进度（advancement）的 `tick` 触发条件，配合 `rewards` 字段在指定 tick 后执行函数。核心思路是：创建一个进度，其触发条件为 `minecraft:tick`，并设置 `interval` 参数，使进度每 N tick 触发一次。通过 `rewards.function` 在触发时执行目标函数。

### 完整代码

#### 1. 创建进度文件

`data/<namespace>/advancement/delayed_task.json`
```json
{
  "criteria": {
    "tick": {
      "trigger": "minecraft:tick",
      "conditions": {
        "interval": 20
      }
    }
  },
  "rewards": {
    "function": "<namespace>:delayed_task"
  }
}
```

#### 2. 创建目标函数

`data/<namespace>/function/delayed_task.mcfunction`
```mcfunction
say 延迟 20 tick 后执行！
```

#### 3. 授予玩家进度

在需要启动延迟时执行：
```mcfunction
advancement grant @s only <namespace>:delayed_task
```

### 陷阱与注意事项

- **进度只能授予一次**：进度触发后会自动 revoke（因为 `tick` 触发条件默认只触发一次），如果需要重复延迟，必须在每次触发后重新 grant。
- **间隔精度**：`interval` 参数从进度被 grant 的时刻开始计数，不是从世界启动开始。但注意：如果玩家在 tick 间隔中间被 grant，第一次触发可能不是精确的 N tick 后，而是下一个 tick 间隔的整数倍。例如 `interval: 20`，玩家在第 5 tick 被 grant，则第一次触发在第 20 tick（15 tick 后），第二次在第 40 tick，以此类推。
- **多玩家问题**：进度是玩家独立的，每个玩家需要单独 grant 和 revoke。
- **版本要求**：`minecraft:tick` 触发条件在 1.16.2 引入，`interval` 参数在 1.20.5 引入。⚠️ 需验证：1.20.5 之前是否支持 `interval`？根据 Minecraft Wiki，`interval` 是 1.20.5 新增的，之前版本只能通过其他方式（如 `random` 条件）模拟。

## 三、方案二：计划刻（Scheduled Tick）法

### 原理

利用 `schedule function` 命令，将函数调用安排在指定 tick 后执行。这是最直接、最精确的延迟执行方式。

### 完整代码

#### 1. 启动延迟

在需要开始延迟的地方执行：
```mcfunction
schedule function <namespace>:delayed_task 20 replace
```

#### 2. 目标函数

`data/<namespace>/function/delayed_task.mcfunction`
```mcfunction
say 延迟 20 tick 后执行！
```

### 陷阱与注意事项

- **重复调度**：`schedule` 命令默认是 `replace` 模式，会覆盖同一函数的已有调度。如果需要多个并发的延迟实例，必须使用不同的函数名或使用 `append` 模式（1.21+ 引入）。
- **调度上限**：每个函数最多同时有 1 个调度（`replace` 模式）或无限个（`append` 模式）。但大量调度可能影响性能。
- **世界卸载**：如果调度时目标维度被卸载，调度会丢失。建议在调度前确保目标维度已加载。
- **版本要求**：`schedule` 命令在 1.15 引入，`append` 模式在 1.21 引入。

## 四、方案三：实体 Tick 法

### 原理

利用实体（如 armor stand、marker）的 `Age` 标签或自定义计分板，在实体 tick 时递减计数器，当计数器归零时执行目标函数。

### 完整代码

#### 1. 创建实体并设置计数器

`data/<namespace>/function/start_delay.mcfunction`
```mcfunction
# 生成一个 marker 实体，并设置计分板
summon marker ~ ~ ~ {Tags:["delayed_task"]}
scoreboard players set @e[tag=delayed_task,limit=1] delay_counter 20
```

#### 2. 每 tick 递减计数器

`data/<namespace>/function/tick.mcfunction`
```mcfunction
# 在 load 中注册到 tick 循环
execute as @e[tag=delayed_task,scores={delay_counter=1..}] run scoreboard players remove @s delay_counter 1
execute as @e[tag=delayed_task,scores={delay_counter=0}] run function <namespace>:delayed_task
```

#### 3. 目标函数

`data/<namespace>/function/delayed_task.mcfunction`
```mcfunction
say 延迟 20 tick 后执行！
# 清理实体
kill @s
```

### 陷阱与注意事项

- **性能开销**：每 tick 需要遍历所有带 `delayed_task` 标签的实体，如果数量很大（>100），性能开销会显著增加。
- **实体数量限制**：Minecraft 对实体数量有硬性限制（默认约 2000），大量延迟任务可能占用实体上限。
- **维度问题**：实体只在所在维度 tick，如果玩家切换维度，实体不会跟随。
- **版本要求**：`marker` 实体在 1.17 引入，之前版本可用 `armor_stand` 替代（需设置 `Marker:1b` 和 `Invisible:1b`）。

## 五、方案四：计分板定时器法

### 原理

利用计分板（scoreboard）的 `dummy` 目标，在 tick 循环中递减所有玩家的计数器，当计数器归零时执行目标函数。

### 完整代码

#### 1. 初始化计分板

`data/<namespace>/function/load.mcfunction`
```mcfunction
scoreboard objectives add delay_counter dummy
```

#### 2. 启动延迟

`data/<namespace>/function/start_delay.mcfunction`
```mcfunction
scoreboard players set @s delay_counter 20
```

#### 3. 每 tick 递减计数器

`data/<namespace>/function/tick.mcfunction`
```mcfunction
# 递减所有正数计数器
scoreboard players remove @a[scores={delay_counter=1..}] delay_counter 1
# 对归零的玩家执行目标函数
execute as @a[scores={delay_counter=0}] run function <namespace>:delayed_task
```

#### 4. 目标函数

`data/<namespace>/function/delayed_task.mcfunction`
```mcfunction
say 延迟 20 tick 后执行！
# 重置计数器（可选）
scoreboard players set @s delay_counter -1
```

### 陷阱与注意事项

- **玩家离线问题**：如果玩家在延迟期间离线，计数器会保留，但玩家重新上线时可能已经过了预期时间。
- **多实例冲突**：所有延迟任务共享同一个计分板目标，无法区分不同任务的延迟时间。如果需要多个并发的不同延迟，需要为每个任务类型创建独立的计分板目标。
- **性能开销**：每 tick 需要遍历所有在线玩家，开销较低（O(n) 其中 n 为玩家数）。
- **版本要求**：所有版本均支持。

## 六、方案对比

| 方案 | 版本要求 | 精度 | 性能开销 | 适用场景 |
|------|---------|------|---------|---------|
| 进度触发法 | 1.20.5+（interval） | 中等（受 grant 时机影响） | 低 | 单次、低频延迟任务 |
| 计划刻法 | 1.15+（replace）/ 1.21+（append） | 高（精确到 tick） | 极低 | 任何需要精确延迟的场景 |
| 实体 Tick 法 | 1.17+（marker） | 高 | 中（实体数量相关） | 需要实体上下文（如位置）的延迟任务 |
| 计分板定时器法 | 所有版本 | 高 | 低（玩家数量相关） | 玩家相关的延迟任务 |

## 七、推荐方案

### 推荐：计划刻法（方案二）

- **版本要求**：1.15+（基本覆盖所有现代版本）
- **精度**：精确到 tick，无偏差
- **性能**：几乎零开销（游戏原生支持）
- **陷阱**：注意 `replace` 和 `append` 模式的区别，以及维度卸载问题

### 备选：计分板定时器法（方案四）

- **版本要求**：所有版本
- **适用场景**：需要玩家上下文的延迟任务（如玩家技能冷却）
- **陷阱**：注意多实例冲突和玩家离线问题
