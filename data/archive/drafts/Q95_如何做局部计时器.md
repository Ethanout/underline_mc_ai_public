# 如何做局部计时器

## 一、核心挑战

在 Minecraft 数据包开发中，"局部计时器"指的是**针对特定实体或位置**的计时器，而非全局 tick 计数。核心挑战在于：

1. **原版没有内置的实体级计时器**——`scoreboard` 是全局的，`schedule` 是全局的
2. **需要区分不同实体/位置的计时状态**——不能用一个分数板记录所有计时
3. **性能与精度的平衡**——高频检测开销大，低频检测可能错过触发时机

## 二、方案一：实体分数板计时器（最推荐）

### 原理

利用 `scoreboard` 为每个需要计时的实体分配一个分数，在 tick 函数中统一递减。当分数归零时触发回调。

### 适用版本

1.13+（scoreboard 系统成熟版本）

### 完整实现

#### 1. 初始化（load）

```mcfunction
# load.mcfunction
scoreboard objectives add timer dummy
scoreboard objectives add timer_flag dummy
```

#### 2. 启动计时器（给实体设置计时）

```mcfunction
# function: namespace:start_timer
# 用法：execute as @e[type=zombie] run function namespace:start_timer
# 参数：通过 storage 传入 duration（tick数）

# 设置计时分数
scoreboard players set @s timer 100  # 100 ticks = 5秒
# 标记为活跃计时器
scoreboard players set @s timer_flag 1
```

#### 3. tick 函数（每秒20次执行）

```mcfunction
# function: namespace:tick
# 在 #minecraft:tick 函数标签中调用

# 递减所有活跃计时器
scoreboard players remove @e[scores={timer_flag=1..}] timer 1

# 触发归零回调
execute as @e[scores={timer=0,timer_flag=1..}] run function namespace:timer_expired
```

#### 4. 计时器到期回调

```mcfunction
# function: namespace:timer_expired
# 计时器归零时执行

# 执行自定义逻辑
say 计时器到期！

# 清除计时器状态
scoreboard players set @s timer_flag 0
scoreboard players set @s timer 0
```

### 陷阱与注意事项

1. **实体死亡后分数不会自动清除**——需要在实体死亡时手动清理，否则新生成的同名实体可能继承旧分数
   ```mcfunction
   # 在实体死亡检测中
   scoreboard players reset @e[type=zombie] timer
   scoreboard players reset @e[type=zombie] timer_flag
   ```

2. **分数板是全局的**——不同维度的同名实体共享分数，需要配合 `dimension` 选择器区分

3. **性能问题**——`@e[scores={timer_flag=1..}]` 选择器在实体数量多时性能下降，建议限制实体类型

4. **精度问题**——每 tick 递减 1，最小精度为 1 tick（50ms）

## 三、方案二：Storage 计时器（1.20.5+）

### 原理

利用 `data modify` 和 `data get` 操作 storage 中的 NBT 数据，通过 `$` 宏函数实现参数化计时器。每个计时器是一个独立的 storage 条目，通过 UUID 或自定义 ID 区分。

### 适用版本

1.20.5+（需要宏函数和 storage 的完整支持）

### 完整实现

#### 1. 初始化（load）

```mcfunction
# load.mcfunction
# 创建计时器 storage
data modify storage namespace:timer data set value []
```

#### 2. 启动计时器

```mcfunction
# function: namespace:start_timer
# 用法：function namespace:start_timer {id:"my_timer",duration:100}

# 添加计时器条目
$data modify storage namespace:timer data append value {id:"$(id)",remaining:$(duration),callback:"namespace:timer_callback"}
```

#### 3. tick 函数

```mcfunction
# function: namespace:tick
# 在 #minecraft:tick 函数标签中调用

# 递减所有计时器
data modify storage namespace:timer data[].remaining set value -1

# 查找并触发到期计时器
execute store result score #index timer run data get storage namespace:timer data 0.remaining
execute if score #index timer matches ..0 run function namespace:process_expired
```

#### 4. 处理到期计时器

```mcfunction
# function: namespace:process_expired
# 处理第一个到期的计时器

# 获取回调函数名
$data get storage namespace:timer data[0].callback

# 执行回调（需要宏函数）
$function $(callback)

# 移除已处理的计时器
data remove storage namespace:timer data[0]

# 继续检查下一个
execute store result score #index timer run data get storage namespace:timer data 0.remaining
execute if score #index timer matches ..0 run function namespace:process_expired
```

### 陷阱与注意事项

1. **⚠️ 需验证**：`data modify storage namespace:timer data[].remaining set value -1` 的语法在 1.20.5 中是否支持对所有元素批量操作？如果不支持，需要循环处理

2. **宏函数限制**：回调函数名必须是静态字符串，不能动态生成

3. **性能问题**：每次 tick 都需要遍历整个 storage 数组，计时器数量多时性能下降

4. **数据持久化**：storage 在服务器重启后会丢失，需要额外处理

## 四、方案三：进度触发计时器（1.16+）

### 原理

利用 `minecraft:tick` 触发器的进度，配合 `rewards` 中的函数调用，实现基于玩家 tick 的计时器。每个玩家独立计时。

### 适用版本

1.16+（tick 触发器引入版本）

### 完整实现

#### 1. 创建进度

```json
// advancement: namespace:timer_tick.json
{
  "criteria": {
    "tick": {
      "trigger": "minecraft:tick"
    }
  },
  "rewards": {
    "function": "namespace:timer_tick"
  }
}
```

#### 2. 计时器函数

```mcfunction
# function: namespace:timer_tick
# 每 tick 对玩家执行一次

# 递减玩家计时器
scoreboard players remove @s timer 1

# 触发到期
execute if score @s timer matches ..0 run function namespace:player_timer_expired
```

#### 3. 启动计时器

```mcfunction
# function: namespace:start_player_timer
# 给玩家设置计时器
scoreboard players set @s timer 100
# 授予进度（如果尚未拥有）
advancement grant @s only namespace:timer_tick
```

#### 4. 停止计时器

```mcfunction
# function: namespace:stop_player_timer
# 撤销进度停止计时
advancement revoke @s only namespace:timer_tick
scoreboard players reset @s timer
```

### 陷阱与注意事项

1. **仅限玩家**——无法用于其他实体

2. **进度触发延迟**——`tick` 触发器在玩家 tick 时触发，但进度系统的执行时机可能晚于主 tick 函数

3. **进度重复授予问题**——如果玩家已经拥有该进度，再次 `grant` 不会触发回调，需要在启动时先 `revoke` 再 `grant`

4. **性能开销**——每个玩家每 tick 都会执行函数，玩家数量多时开销较大

## 五、方案对比

| 方案 | 版本要求 | 适用对象 | 精度 | 性能 | 复杂度 | 适用场景 |
|------|---------|---------|------|------|--------|---------|
| 实体分数板 | 1.13+ | 所有实体 | 1 tick | 中（实体数量相关） | 低 | 通用计时，实体数量<100 |
| Storage 计时器 | 1.20.5+ | 任意（通过ID） | 1 tick | 中（计时器数量相关） | 高 | 需要参数化回调，计时器数量<50 |
| 进度触发 | 1.16+ | 仅玩家 | 1 tick | 中（玩家数量相关） | 中 | 玩家专属计时，玩家数量<20 |

## 六、最佳实践建议

1. **实体数量 < 100**：使用实体分数板方案，最简单可靠
2. **需要参数化回调**：使用 Storage 方案，但注意性能限制
3. **仅玩家计时**：使用进度触发方案，但注意玩家数量
4. **高精度需求**：所有方案精度均为 1 tick，如需更高精度需使用 `schedule` 配合红石刻

## 七、陷阱总结

1. **实体死亡后分数残留**——务必在实体死亡时清理分数
2. **维度隔离**——不同维度的实体共享分数板，需要额外处理
3. **宏函数限制**——Storage 方案的回调函数名必须是静态字符串
4. **进度重复授予**——进度触发方案需要先 revoke 再 grant
5. **性能监控**——建议在开发环境中测试计时器数量上限
