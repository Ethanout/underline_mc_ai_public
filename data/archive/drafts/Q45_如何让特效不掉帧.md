# 如何让特效不掉帧

## 核心挑战

Minecraft 原版数据包制作特效（粒子、实体、声音）时，性能瓶颈主要来自：
1. **实体数量过多**：每个实体都有 AI、碰撞箱、Tick 开销，大量实体瞬间拉低 TPS
2. **粒子命令执行频率过高**：`particle` 命令本身开销较低，但高频执行（如每 tick 对所有玩家）会累积
3. **命令链过长**：复杂的 `execute` 链和函数调用栈增加单 tick 耗时
4. **选择器性能**：`@e` 选择器遍历实体列表，范围越大越慢

核心优化思路：**减少实体数量、合并粒子命令、避免不必要的计算**。

---

## 方案一：粒子流优化 —— 合并与批量执行

### 原理

`particle` 命令本身开销很低（约 0.01-0.05ms/次），但每 tick 执行数百次就会累积。优化方式：
- 将多个粒子合并到一条命令中（使用 `particle <粒子名> <x> <y> <z> <dx> <dy> <dz> <速度> <数量>` 的批量模式）
- 减少不必要的粒子更新频率（如从每 tick 改为每 2-3 tick）
- 使用 `execute as @a at @s` 代替 `execute at @a` 避免重复计算位置

### 完整代码

**优化前（低效）**：
```mcfunction
# 每 tick 对每个玩家执行 10 次粒子命令
execute as @a at @s run particle minecraft:flame ~ ~1 ~ 0 0 0 0.1 1
execute as @a at @s run particle minecraft:flame ~ ~1.5 ~ 0 0 0 0.1 1
# ... 重复 8 次
```

**优化后（高效）**：
```mcfunction
# 合并为一条命令，一次生成 10 个粒子
execute as @a at @s run particle minecraft:flame ~ ~1 ~ 0 0.5 0 0.1 10
```

**更进一步的优化——降低频率**：
```mcfunction
# tick.mcfunction
scoreboard players add #tick_counter global 1
execute if score #tick_counter global matches 0 run function namespace:spawn_particles
execute if score #tick_counter global matches 2 run scoreboard players set #tick_counter global -1
```

### 陷阱

1. **批量粒子的分布**：`particle` 的 `dx dy dz` 参数控制的是**散布范围**，不是精确位置。如果需要精确排列（如环形），必须用多条命令。
2. **粒子数量上限**：单条 `particle` 命令的 `count` 参数最大为 32767（`int` 上限），但实际建议不超过 1000，否则可能造成瞬间卡顿。
3. **粒子类型差异**：某些粒子（如 `minecraft:block`、`minecraft:item`）需要额外参数，批量模式可能不支持所有粒子类型。⚠️ 需验证：`minecraft:block` 在批量模式下是否正常工作。

## 方案二：实体特效优化 —— 使用 Marker 与 AreaEffectCloud

### 原理

实体特效（如旋转的粒子环、跟随玩家的光效）通常需要实体作为载体。不同实体的性能开销差异巨大：

| 实体类型 | 性能开销 | 适用场景 |
|---------|---------|---------|
| `minecraft:marker` | 极低（无 AI、无碰撞箱、无渲染） | 纯逻辑标记、位置锚点 |
| `minecraft:area_effect_cloud` | 低（无 AI、无碰撞箱、可携带粒子） | 持续粒子效果、范围效果 |
| `minecraft:armor_stand` | 中（有碰撞箱、可装备物品） | 需要显示物品或自定义模型 |
| `minecraft:item_display` | 中（1.19.4+，可显示物品模型） | 需要精确的 3D 模型展示 |
| `minecraft:text_display` | 中（1.19.4+，可显示文字） | 文字特效 |

**核心优化**：尽量使用 `marker` 或 `area_effect_cloud` 代替 `armor_stand`。

### 完整代码

**使用 AreaEffectCloud 制作持续粒子光环**：

```mcfunction
# summon.mcfunction — 生成光环实体
summon minecraft:area_effect_cloud ~ ~1 ~ {Duration:2147483647,WaitTime:0,Radius:2f,Particle:{type:"minecraft:flame"},Tags:["aura_effect"]}
```

**使用 Marker 作为粒子发射锚点**：

```mcfunction
# summon.mcfunction — 生成标记实体
summon minecraft:marker ~ ~1 ~ {Tags:["particle_emitter"]}

# tick.mcfunction — 每 tick 从标记位置发射粒子
execute as @e[tag=particle_emitter] at @s run particle minecraft:end_rod ~ ~ ~ 0.5 0.5 0.5 0.1 5
```

**使用 AreaEffectCloud 的 `Particle` 字段自动生成粒子（零命令开销）**：

```json
// 生成命令
summon minecraft:area_effect_cloud ~ ~1 ~ {Duration:100,WaitTime:0,Radius:1.5f,Particle:{type:"minecraft:end_rod"},Tags:["auto_particle"]}
```

这个实体每 tick 自动在其半径范围内生成粒子，**不需要任何 tick 函数**。

### 陷阱

1. **AreaEffectCloud 的 Duration 上限**：`Duration` 最大为 `2147483647`（约 68 年），但 `WaitTime` 必须为 0 才能立即生效。如果 `WaitTime > 0`，实体在等待期间不会生成粒子。
2. **AreaEffectCloud 的粒子类型限制**：`Particle` 字段只支持简单的粒子类型，不支持 `block`、`item` 等需要额外参数的粒子。⚠️ 需验证：`minecraft:dust` 是否支持。
3. **Marker 实体的局限性**：`marker` 没有位置更新逻辑，如果需要移动，必须用 `tp` 或 `data merge` 修改其位置。它也不响应 `@e[type=!marker]` 选择器（因为 type 是 marker）。
4. **实体数量控制**：即使使用轻量实体，超过 500 个仍可能造成性能问题。建议使用 `scoreboard` 或 `storage` 控制实体总数。

## 方案三：命令链优化 —— 减少执行次数与选择器范围

### 原理

复杂的 `execute` 链和选择器是性能杀手。优化方向：
- 使用 `execute if` 条件提前过滤，避免不必要的执行
- 使用 `@e[tag=...,limit=1]` 限制选择器范围
- 使用 `execute store` 代替 `data get` 获取 NBT（后者更慢）
- 避免在 tick 函数中使用 `@e` 选择器遍历所有实体

### 完整代码

**优化前（低效）**：
```mcfunction
# 每 tick 遍历所有 armor_stand，检查 tag
execute as @e[type=minecraft:armor_stand] at @s if entity @s[tag=effect_emitter] run particle minecraft:flame ~ ~ ~ 0 0 0 0.1 1
```

**优化后（高效）**：
```mcfunction
# 使用 tag 直接选择，避免 type 过滤
execute as @e[tag=effect_emitter] at @s run particle minecraft:flame ~ ~ ~ 0 0 0 0.1 1
```

**使用 scoreboard 代替 NBT 检测**：
```mcfunction
# 低效：每 tick 检查 NBT
execute as @e[tag=effect_emitter] if data entity @s {Active:1b} run ...

# 高效：使用 scoreboard
scoreboard players add @e[tag=effect_emitter] active_timer 1
execute as @e[tag=effect_emitter,scores={active_timer=1..}] run ...
```

**使用 `execute if` 提前过滤玩家**：
```mcfunction
# 低效：对所有玩家执行
execute as @a at @s run particle minecraft:flame ~ ~ ~ 0 0 0 0.1 1

# 高效：只对在特定区域的玩家执行
execute as @a[predicate=namespace:in_effect_zone] at @s run particle minecraft:flame ~ ~ ~ 0 0 0 0.1 1
```

### 陷阱

1. **`@e` 选择器的性能**：`@e` 会遍历**所有已加载区块中的实体**。即使使用 `tag=...` 过滤，Minecraft 仍然会先获取所有实体列表再过滤。建议配合 `type=...` 或 `limit=1` 使用。
2. **`execute if entity` 的开销**：`if entity` 本身也是一个选择器操作，如果条件复杂（如 `@e[tag=a,tag=b]`），开销可能比直接执行命令还高。
3. **scoreboard 的局限性**：scoreboard 只能存储整数，无法存储浮点数或复杂状态。如果需要精确位置或 NBT 数据，仍需使用 `data` 命令。

## 方案四：视觉欺骗 —— 减少实际渲染

### 原理

玩家看不到的特效就不需要生成。利用 `predicate` 和 `distance` 条件，只对近距离玩家生成粒子。

### 完整代码

**距离过滤**：
```mcfunction
# 只对 32 格内的玩家生成粒子
execute as @a[distance=..32] at @s run particle minecraft:flame ~ ~ ~ 0 0 0 0.1 1
```

**视线检测（1.20.5+）**：
```json
// predicate: namespace:can_see.json
{
  "condition": "minecraft:entity_properties",
  "entity": "this",
  "predicate": {
    "type_specific": {
      "type": "player",
      "can_see": true
    }
  }
}
```
```mcfunction
# 只对能看到特效位置的玩家生成
execute as @a[predicate=namespace:can_see] at @s run particle minecraft:flame ~ ~ ~ 0 0 0 0.1 1
```

**使用 `area_effect_cloud` 的 `Radius` 自动控制范围**：
```mcfunction
# 生成一个半径为 5 格的光环，只有 5 格内的玩家能看到粒子
summon minecraft:area_effect_cloud ~ ~1 ~ {Duration:100,WaitTime:0,Radius:5f,Particle:{type:"minecraft:end_rod"},Tags:["auto_particle"]}
```

### 陷阱

1. **`can_see` 谓词的性能**：`can_see` 需要执行射线检测，本身有一定开销。如果每 tick 对大量玩家使用，可能得不偿失。
2. **距离过滤的粒度**：`distance=..32` 是**欧几里得距离**，不是曼哈顿距离。如果特效在封闭房间内，32 格外的玩家通过墙壁仍然看不到，但命令仍会执行。
3. **AreaEffectCloud 的 Radius 限制**：`Radius` 最大为 128，超过此值不会报错但不会生效。⚠️ 需验证：1.20.5 后是否有变化。

## 方案对比

| 方案 | 版本要求 | 性能提升 | 适用场景 | 复杂度 |
|------|---------|---------|---------|-------|
| 粒子流优化 | 1.13+ | 中（减少命令数） | 大量粒子特效 | 低 |
| 实体特效优化 | 1.13+（marker 1.17+） | 高（减少实体开销） | 持续光环、跟随特效 | 中 |
| 命令链优化 | 1.13+ | 中（减少选择器开销） | 复杂逻辑的特效系统 | 中 |
| 视觉欺骗 | 1.13+（can_see 1.20.5+） | 高（减少无效渲染） | 大范围特效 | 低 |

**推荐组合**：
- 简单粒子特效：方案一 + 方案四（距离过滤）
- 持续光环特效：方案二（AreaEffectCloud）+ 方案四
- 复杂粒子系统（如粒子环、轨迹）：方案二（Marker）+ 方案一 + 方案三
- 高性能要求场景：方案二（AreaEffectCloud 自动粒子）+ 方案四

## 陷阱总结

1. **不要过度优化**：在实体少于 50 个时，优化带来的收益可能不如代码可维护性重要。
2. **AreaEffectCloud 不是万能的**：它的粒子类型有限，且无法精确控制粒子位置。
3. **`@e` 选择器是性能杀手**：即使使用 tag 过滤，Minecraft 仍会遍历所有实体。建议配合 `type=...` 或 `limit=1`。
4. **粒子命令的批量模式有局限**：`dx dy dz` 控制的是散布范围，不是精确位置。需要精确排列时，必须用多条命令。
5. **测试环境与生产环境不同**：单机测试的 TPS 可能远高于服务器。建议在模拟多人环境（至少 10 个假玩家）下测试。
