# 如何做多人兼容

## 核心挑战

多人兼容是数据包开发中最容易被忽视但影响最大的问题。核心挑战在于：

1. **状态隔离**：每个玩家的进度、计分板、标签、数据存储必须互不干扰
2. **并发执行**：多个玩家同时触发同一函数时，不能出现竞态条件
3. **资源竞争**：全局实体、Storage、计分板目标等共享资源需要合理分配
4. **性能开销**：多人环境下，O(n) 的遍历操作会放大为 O(n²)

## 方案一：基于 @s 的上下文感知模式（推荐）

### 原理

利用 `execute as @a` 将执行上下文切换到每个玩家，所有操作都通过 `@s` 引用当前玩家。这是最基础也最安全的多人兼容方式。

### 核心机制

- 使用 `execute as @a at @s` 遍历所有玩家
- 所有计分板操作、标签、数据存储都基于 `@s` 的 UUID 或自定义标识
- 避免使用全局实体（如 `@e[type=minecraft:marker]`）存储玩家状态

### 完整代码

#### 目录结构
```
data/
  namespace/
    function/
      load.mcfunction
      tick.mcfunction
      player/
        init.mcfunction
        process.mcfunction
        cleanup.mcfunction
    advancement/
      player_join.json
```

#### load.mcfunction
```mcfunction
# 创建计分板目标
scoreboard objectives add <namespace>.cooldown dummy
scoreboard objectives add <namespace>.state dummy

# 为已在线玩家初始化
execute as @a run function <namespace>:player/init
```

#### tick.mcfunction
```mcfunction
# 每 tick 遍历所有玩家
execute as @a at @s run function <namespace>:player/process
```

#### player/init.mcfunction
```mcfunction
# 为每个玩家分配唯一的状态槽位
scoreboard players set @s <namespace>.state 0
scoreboard players set @s <namespace>.cooldown 0
```

#### player/process.mcfunction
```mcfunction
# 示例：处理玩家冷却
scoreboard players remove @s <namespace>.cooldown 1

# 条件判断：只有冷却为0时才执行
execute if score @s <namespace>.cooldown matches 0 run function <namespace>:player/action
```

#### player/action.mcfunction
```mcfunction
# 执行具体操作
say 执行动作！
scoreboard players set @s <namespace>.cooldown 20
```

#### player_join.json
```json
{
  "criteria": {
    "join": {
      "trigger": "minecraft:tick"
    }
  },
  "rewards": {
    "function": "<namespace>:player/init"
  }
}
```

### 陷阱与注意事项

1. **@s 的上下文丢失**：在函数调用链中，如果使用了 `execute as @e` 或 `execute at @p`，会改变 `@s` 的指向。必须在子函数开头重新设置上下文。
   ```mcfunction
   # 错误示例
   execute as @a run function <namespace>:sub
   # sub.mcfunction 中 @s 仍然是玩家，但如果 sub 内部有 execute as @e，则 @s 会改变
   
   # 正确做法：在 sub 开头保存上下文
   # sub.mcfunction
   execute as @s run say 当前玩家是 @s
   ```

2. **计分板目标命名冲突**：不同数据包使用相同名称的计分板目标会导致冲突。建议使用命名空间前缀，如 `<namespace>.cooldown`。

3. **进度触发并发问题**：多个玩家同时触发同一个进度时，奖励函数会被多次调用。如果奖励函数中有全局操作（如 `say`），会输出多条消息。解决方案是在奖励函数中使用 `@s` 而不是 `@a`。

## 方案二：基于 UUID 的 Storage 隔离模式

### 原理

使用 `data modify` 和 `data merge` 在 Storage 中为每个玩家创建独立的数据条目，通过玩家的 UUID 作为键来索引。

### 适用版本

1.20.2+（`data modify` 支持 `from storage` 和 `value` 参数）

### 完整代码

#### 目录结构
```
data/
  namespace/
    function/
      load.mcfunction
      tick.mcfunction
      player/
        save_state.mcfunction
        load_state.mcfunction
        cleanup.mcfunction
```

#### load.mcfunction
```mcfunction
# 初始化 Storage
data modify storage <namespace>:player_data players set value []

# 为已在线玩家创建数据条目
execute as @a run function <namespace>:player/save_state
```

#### tick.mcfunction
```mcfunction
# 每 tick 处理所有玩家
execute as @a run function <namespace>:player/load_state
execute as @a run function <namespace>:player/process
execute as @a run function <namespace>:player/save_state
```

#### player/save_state.mcfunction
```mcfunction
# 保存玩家状态到 Storage
# 使用玩家的 UUID 作为唯一标识
data modify storage <namespace>:player_data players append value {UUID:"",cooldown:0,state:0}

# 更新具体玩家的数据
execute store result storage <namespace>:player_data players[{UUID:"<玩家的UUID>"}].cooldown int 1 run scoreboard players get @s <namespace>.cooldown
```

#### player/load_state.mcfunction
```mcfunction
# 从 Storage 加载玩家状态
execute store result score @s <namespace>.cooldown run data get storage <namespace>:player_data players[{UUID:"<玩家的UUID>"}].cooldown
```

#### player/cleanup.mcfunction
```mcfunction
# 玩家离开时清理数据
data remove storage <namespace>:player_data players[{UUID:"<玩家的UUID>"}]
```

### 陷阱与注意事项

1. **UUID 获取**：在 1.20.5 之前，无法直接通过命令获取玩家的 UUID 字符串。需要使用 `data get entity @s UUID` 获取整数数组，然后手动转换为字符串格式。⚠️ 需验证：1.20.5+ 是否有更简便的方法。

2. **Storage 大小限制**：Storage 没有明确的大小限制，但大量数据（如 100+ 玩家）会导致性能下降。建议定期清理无效数据。

3. **并发写入问题**：多个玩家同时执行 `data modify storage ... append` 可能导致数据错乱。解决方案是使用 `execute store` 配合计分板来确保原子性操作。

## 方案三：基于计分板的多维索引模式

### 原理

利用计分板的 `dummy` 目标类型，为每个玩家分配一个唯一的索引值，然后通过索引值在多个计分板目标之间建立关联。

### 适用版本

1.13+（所有版本）

### 完整代码

#### 目录结构
```
data/
  namespace/
    function/
      load.mcfunction
      tick.mcfunction
      player/
        assign_index.mcfunction
        get_index.mcfunction
        process.mcfunction
```

#### load.mcfunction
```mcfunction
# 创建计分板目标
scoreboard objectives add <namespace>.index dummy
scoreboard objectives add <namespace>.data1 dummy
scoreboard objectives add <namespace>.data2 dummy

# 为已在线玩家分配索引
execute as @a run function <namespace>:player/assign_index
```

#### player/assign_index.mcfunction
```mcfunction
# 为玩家分配唯一索引（使用玩家的实体ID作为索引）
scoreboard players operation @s <namespace>.index = @s <namespace>.entity_id

# 或者使用自定义计数器
# 注意：这种方法需要全局计数器，存在并发问题
# scoreboard players add #counter <namespace>.index 1
# scoreboard players operation @s <namespace>.index = #counter <namespace>.index
```

#### player/process.mcfunction
```mcfunction
# 通过索引访问数据
# 假设 data1 存储冷却时间，data2 存储状态
scoreboard players get @s <namespace>.data1
scoreboard players get @s <namespace>.data2

# 示例：如果 data1 > 0，则减少
execute if score @s <namespace>.data1 matches 1.. run scoreboard players remove @s <namespace>.data1 1
```

### 陷阱与注意事项

1. **索引冲突**：如果使用实体ID作为索引，玩家重新登录后ID会改变。如果使用计数器，需要确保计数器在服务器重启后仍然有效（使用 `scoreboard players set #counter <namespace>.index 0` 在 load 中重置）。

2. **计分板目标数量限制**：每个计分板目标可以存储所有玩家的数据，但目标数量有限（约 256 个）。如果需要存储大量数据，建议使用方案二。

3. **数据关联性差**：计分板只能存储整数，无法存储复杂数据结构。如果需要存储字符串或 NBT 数据，必须使用方案二。

## 方案对比

| 特性 | 方案一：@s 上下文模式 | 方案二：Storage 隔离模式 | 方案三：计分板索引模式 |
|------|----------------------|------------------------|----------------------|
| 最低版本 | 1.13 | 1.20.2 | 1.13 |
| 性能开销 | 低 | 中（大量玩家时高） | 低 |
| 数据复杂度 | 低（仅整数） | 高（支持 NBT） | 低（仅整数） |
| 并发安全性 | 高 | 中（需注意原子性） | 高 |
| 实现难度 | 低 | 高 | 中 |
| 适用场景 | 大多数通用场景 | 需要复杂数据存储 | 简单状态管理 |

## 最佳实践总结

1. **优先使用方案一**：对于 90% 的场景，基于 `@s` 的上下文模式已经足够。它简单、高效、安全。

2. **避免全局实体**：不要使用 `@e[type=minecraft:marker]` 来存储玩家状态，这会导致实体数量膨胀和性能问题。

3. **合理使用计分板**：计分板是 Minecraft 中最快的状态存储方式，适合存储整数数据。

4. **Storage 用于复杂数据**：当需要存储字符串、列表、复合标签时，使用 Storage 配合 UUID 索引。

5. **定期清理**：无论使用哪种方案，都要在玩家离开时清理相关数据，避免内存泄漏。

6. **测试多人场景**：在开发过程中，至少用 3-5 个玩家同时测试，检查是否存在状态串扰或并发问题。
