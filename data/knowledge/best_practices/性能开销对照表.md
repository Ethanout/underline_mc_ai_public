# 性能开销对照表

## 操作开销层级（1 scb = 一次 scoreboard add）
```
scoreboard add/remove:          1 scb (基准单位)
storage modify:                 2-10 scb
entity data modify:            30-60 scb
block entity data modify:      40-80 scb
player data modify:           100-200 scb (最慢的 NBT 源)
```

## 数据存储性能排序（从快到慢）
```
玩家(计分板) > 方块实体 > 实体 > marker > storage
```
- storage 层数越少性能越好
- marker 只有固定 UUID 才能体现优势
- 少量物品存储可用固定位置的唱片机

## 选择器性能层级
```
UUID 直接访问:     O(1) — 哈希直接查找
玩家名称:          O(1) — 哈希查找
@s:                instant
@a / @p / @r:      只扫玩家
@e + type=:        类型索引，快
@e 无 type:        扫所有实体（最慢）
```

## 命令消耗对比
```
return, 计分板操作, 单层 storage, if item, if block:  最低
data get list:              比 if data list[] 快
execute store result:       比 execute store success 有额外转换
宏函数:                     非宏行加载时解析，宏行每次调用解析
展示实体矩阵分解:           消耗很大，没必要别用
```

## 选择器参数执行顺序（不是你写的顺序）
```
type → level → gamemode → team → scores → tag → name → nbt(最后!)
x_rotation → y_rotation → Box → distance → sort → limit(最后)
```
- `nbt=` 放在选择器中会复制所有实体 NBT，永远别用
- `distance=..` 限定了维度搜索范围，即使无范围也建议加上

## 频率分层优化策略
```
#tick 函数:      极端优化—每 tick 都跑
schedule 循环:    中度优化—周期性执行
事件处理:         最低优化需求—触发频率低
视觉更新:         可降到 1/2/5 Hz—玩家察觉不到
```
