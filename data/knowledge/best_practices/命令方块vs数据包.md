# 命令方块 vs 数据包

## 命令方块的问题

| 问题 | 细节 |
|------|------|
| 加载区块依赖 | 区块不加载即不运行 |
| 无线程安全 | `@r` 在链中可能重复选取 |
| 无类型安全 | 拼写错误到运行时才暴露 |
| 性能差 | 无 execute 链式优化，每步都重开 |
| 热重载困难 | 改一个命令方块就得手动拆/敲 |
| 版本迁移痛苦 | 每次大版本都要手动改 |

## 数据包的优势
- 使用 JSON 谓词/配方/战利品表等声明式系统
- 函数可模块化、可叠加、有 I/O 约定
- 所有文件可用 git 管理
- `/reload` 热重载（函数/配方/战利品表/谓词）
- overlay 多版本兼容
- 函数标签：`#load` `#tick` 自动执行

## 何时仍用命令方块
- 快速原型（先跑起来再迁移到数据包）
- 无数据包权限的服务器（部分服主不开放数据包）
- 配合数据包做"连锁调试触发器"（只在调试用，上线前删）
- 地图特定区域的局部逻辑（但数据包 + predicate 通常更好）

## 迁移策略
1. 用命令方块做原型
2. 将逻辑抽象为函数
3. 将条件用谓词/标签替代
4. 用 `schedule` 替代 `repeat` 命令方块
5. 用 advancement 替代 `testfor` 检测

## 命令方块常见易错点
- `run execute` 在任何情况下都是多余的，直接写子命令即可（`return run execute` 除外）
- 命令方块中游标默认为方块中心，必须 `at @s` 才能移到玩家位置
- 找不到文件扩展名时去"查看"→"勾选显示文件扩展名"
